버튼을 누르면 화면 구석에 "저장되었습니다" 토스트가 잠깐 떴다 사라집니다. 눈으로 보는 사용자에겐 충분한 피드백이죠. 그런데 **스크린리더 사용자**는요? 화면 어딘가에 조용히 나타난 이 메시지를, 보조기기는 어떻게 알아챌까요?

기본적으론 **모릅니다.** 스크린리더는 보통 포커스된 곳을 읽는데, 토스트는 포커스를 뺏지 않으니까요. 이 간극을 메우는 게 **라이브 리전(live region)** 입니다.

## aria-live — "여기 바뀌면 알려줘"

라이브 리전은 특정 영역에 `aria-live` 속성을 붙여 만듭니다. 그 안의 내용이 바뀌면, 스크린리더가 **현재 하던 걸 마치고(또는 즉시)** 새 내용을 읽습니다.

```jsx
<div aria-live="polite">
  {toast && <div role="status">{toast.message}</div>}
</div>
```

- **`aria-live="polite"`**: 사용자가 하던 말이 끝나면 읽음. 대부분의 알림(저장 완료, 항목 추가)에 적합.
- **`aria-live="assertive"`**: 하던 걸 **끊고 즉시** 읽음. 긴급한 것(에러, 세션 만료 경고)에만. 남용하면 정신없습니다.

## 결정적 함정 — 영역이 미리 있어야 한다

가장 흔한 실수입니다. **라이브 리전은 콘텐츠가 바뀌기 전부터 DOM에 존재**해야 합니다. 스크린리더가 그 영역을 "감시 대상"으로 미리 등록하기 때문이죠.

```jsx
// ✗ 나쁨: 토스트가 뜰 때 라이브 리전째로 새로 생성 → 안 읽힘
{toast && <div aria-live="polite">{toast.message}</div>}

// ✓ 좋음: 빈 라이브 리전을 항상 두고, 안의 내용만 바꿈
<div aria-live="polite">
  {toast && <div>{toast.message}</div>}
</div>
```

빈 컨테이너를 처음부터 렌더해 두고, **그 안의 자식만** 추가·교체해야 안정적으로 읽힙니다.

## role로 의미까지 얹기

편의를 위한 표준 역할도 있습니다. 이들은 암묵적으로 라이브 리전이 됩니다.

- **`role="status"`** = `aria-live="polite"` + 의미("상태 메시지"). 일반 알림에.
- **`role="alert"`** = `aria-live="assertive"` + 의미("경고"). 에러에.

```jsx
<div role="status">저장되었습니다</div>   {/* 정중하게 읽힘 */}
<div role="alert">삭제에 실패했습니다</div> {/* 즉시 끊고 읽힘 */}
```

## aria-atomic — 일부만 바뀔 때

`aria-atomic="true"`면 영역이 바뀔 때 **전체를 통째로** 다시 읽고, `false`(기본)면 **바뀐 부분만** 읽습니다. 예컨대 "3개 중 1개 완료" → "3개 중 2개 완료"처럼 일부만 갱신될 때, `atomic="true"`면 문장 전체를 다시 읽어 맥락이 유지됩니다.

## 눈에 안 보여도 알려야 할 것들

토스트만이 아닙니다. 라이브 리전이 필요한 순간은 많습니다.

- 검색 자동완성 결과 개수 ("결과 12개")
- 폼 제출 후 성공/실패 메시지
- 장바구니 담기, 좋아요 같은 즉각 피드백
- 로딩 완료 알림

시각적 피드백을 만들 때마다 "이걸 **못 보는 사용자**는 어떻게 알지?"를 한 번 물으면, 자연스럽게 라이브 리전이 떠오릅니다. ([웹 접근성](/posts/web-accessibility)의 핵심 습관이죠.)

라이브 리전의 교훈은 "**동적 변화는 시각만으로 전달되지 않는다**"입니다. `aria-live` 영역을 미리 심어 두고 그 안의 내용을 바꾸는 것만으로, 화면을 못 보는 사용자에게도 같은 정보가 전해집니다. 다음 글에서는 [정규식 테스터](/posts/regex-tester)를 직접 만들어 봅니다.
