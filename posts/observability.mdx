프론트는 문제가 나면 **화면에 보입니다**. 버튼이 안 눌리고, 레이아웃이 깨지죠. 그런데 서버는 어딘가 먼 곳에서 조용히 돕니다. **"지금 잘 돌고 있나? 느려진 건가? 왜 에러가 났나?"** 를 눈으로 볼 수 없어요. 이 "안 보이는 것을 보이게" 만드는 게 **옵저버빌리티(observability)** 입니다.

## 세 기둥 — 로그·메트릭·트레이스

관측은 보통 세 가지 신호로 이뤄집니다.

- **로그(Logs)**: "무슨 일이 있었나"의 기록. 개별 사건.
- **메트릭(Metrics)**: "얼마나"의 수치. 요청 수, 지연 시간, 에러율 — 시간에 따른 추세.
- **트레이스(Traces)**: "요청 하나가 어디를 거쳤나"의 경로. 여러 서비스를 넘나드는 흐름.

로그로 **원인**을 파고, 메트릭으로 **징후**를 감지하고, 트레이스로 **경로**를 따라갑니다.

## 구조화 로깅 — console.log를 넘어

`console.log("user login")` 같은 로그는 사람 눈엔 읽히지만, 수백만 줄에서 **검색·집계가 안 됩니다**. 그래서 서버 로그는 **구조화(JSON)** 합니다.

```js
// 나쁨: 문자열 — 파싱·검색 어려움
console.log(`user ${id} login failed from ${ip}`);

// 좋음: 구조화 — 필드로 검색·필터·집계 가능
logger.warn({ event: "login_failed", userId: id, ip, reason: "bad_password" });
```

`event: "login_failed"` 로 필터하고, `userId` 로 특정 사용자를 추적하고, 시간대별로 집계할 수 있죠. 로그가 **데이터**가 됩니다.

로그 레벨(`debug`/`info`/`warn`/`error`)도 나눠, 운영에선 `info` 이상만 남기는 식으로 소음을 줄입니다.

## 메트릭과 알람

메트릭은 "정상이 무엇인지"를 알게 하고, 벗어나면 **알람**을 울립니다. 대표적으로 보는 것들:

- **처리량**: 초당 요청 수(RPS).
- **지연**: 응답 시간 — 평균보다 **p95·p99**(느린 쪽 꼬리)가 중요. 평균은 착시를 주거든요.
- **에러율**: 5xx 비율. 이게 튀면 알람.
- **자원**: CPU·메모리 — [이벤트 루프](/posts/nodejs-event-loop)가 막히면 여기서 티가 남.

"에러율이 1%를 넘으면 알림" 같은 규칙으로, 사용자가 항의하기 **전에** 안다는 게 핵심입니다.

## 헬스 체크

로드 밸런서와 [배포 파이프라인](/posts/ci-cd)이 "이 인스턴스가 살아있나"를 물어보는 창구입니다. 보통 `GET /health` 가 DB 연결 등을 확인하고 `200`을 돌려주죠. 죽은 인스턴스는 [트래픽에서 제외](/posts/scalability-stateless)되고 교체됩니다.

## 분산 추적과 상관 ID

요청 하나가 여러 서비스(게이트웨이 → 인증 → 주문 → 결제)를 거치면, "어디서 느려졌나"를 찾기 어렵습니다. 그래서 요청 시작점에서 **상관 ID(correlation/trace ID)** 를 하나 발급해, 거쳐가는 모든 서비스의 로그에 **같은 ID를 심습니다**.

```js
// 요청마다 고유 ID를 부여하고 모든 로그에 포함
const traceId = req.headers["x-trace-id"] ?? crypto.randomUUID();
logger.info({ traceId, service: "order", msg: "created" });
```

나중에 그 ID로 검색하면 **한 요청의 전 여정**이 한 줄로 꿰집니다. [메시지 큐](/posts/message-queue)로 비동기 처리된 작업까지 이 ID를 넘기면 끝까지 추적되죠.

---

옵저버빌리티의 핵심은 "**측정할 수 없으면 개선할 수 없다**"입니다. 구조화된 로그, 추세를 보는 메트릭, 경로를 잇는 트레이스 — 이 셋이 있어야 장애가 났을 때 **추측이 아니라 증거로** 대응합니다. 그런데 관측만으로는 부족하죠. 다음 편에서는 애초에 [장애에 강하게 만드는 복원력 패턴](/posts/resilience-patterns)을 봅니다. 그 전에, 팀과 API를 나눠 쓰는 언어인 [API 문서화](/posts/api-documentation)를 먼저 짚습니다.
