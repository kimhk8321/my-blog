지난주에 [검색을 붙이면서](/posts/blog-search) 한 가지를 알게 됐습니다. **검색은 찾을 마음을 먹은 사람만 씁니다.** 대부분의 방문자는 글 하나를 읽고 그대로 나가죠. 129편을 쌓아뒀는데 그중 한 편만 보고 떠나는 게 아까웠습니다.

그래서 글 끝에 **"함께 읽을 만한 글"** 을 붙이기로 했습니다. 마침 검색용으로 만들어 둔 역색인이 있으니, 그걸 그대로 재활용하면 되겠더군요.

## 검색과 추천은 무엇이 다른가

둘 다 "관련 있는 글 찾기"지만 맞추는 대상이 다릅니다.

- **검색**: 짧은 **질문**과 긴 **글**을 맞춘다
- **추천**: 긴 **글**과 긴 **글**을 맞춘다

질문은 단어 몇 개뿐이라 "이 단어가 어디에 있나(제목이냐 본문이냐)"가 중요했습니다. 반면 글끼리 비교할 땐 양쪽 다 수천 개의 단어를 갖고 있으니, **전체적으로 얼마나 닮았는지**를 재야 합니다.

## 글을 벡터로 만들기

각 글을 **단어 가중치의 목록**, 즉 벡터로 표현합니다. 값은 검색에서 쓰던 것과 같습니다 — 제목·태그 가중치에 [IDF](/posts/blog-search)를 곱한 [TF-IDF](/posts/query-performance)죠.

```ts
// 역색인을 한 번 훑으며 글별 가중치를 모은다
for (const [token, byDoc] of postings) {
  const weight = idf(byDoc.size, docs.length);
  for (const [docId, posting] of byDoc) {
    raw[docId].set(token, weight * (posting.topical + posting.support + bm25Tf(...)));
  }
}
```

여기서 두 가지를 정리했습니다.

- **한글 한 글자는 버린다.** 지난번에 "리액트"의 `트`가 "컴포넌트"에 걸리던 그 문제입니다. 유사도에서는 더 치명적이라 아예 뺐습니다.
- **글마다 비중 큰 150개만 남긴다.** 계산도 줄고, 어쩌다 한 번 나온 단어의 잡음도 줄어듭니다.

## 코사인 유사도 — 길이를 지운다

두 벡터가 닮았는지는 **코사인 유사도**로 잽니다. 두 벡터가 이루는 각도를 보는 건데, 핵심은 **크기(길이)를 나눠서 없앤다**는 점입니다.

```ts
const similarity = dot / (target.norm * other.norm);
```

이게 왜 중요하냐면, 그냥 내적만 쓰면 **긴 글이 무조건 이깁니다**. 단어가 많으니 겹치는 것도 많거든요. 크기로 나누면 "얼마나 많이 겹치나"가 아니라 **"어느 방향을 보고 있나"** 를 재게 됩니다. 짧은 글도 주제가 같으면 높은 점수를 받죠.

[검색에서 BM25로 길이를 보정](/posts/blog-search)했던 것과 같은 고민이, 여기선 정규화라는 다른 형태로 나타난 셈입니다.

## 삽질 — Docker 글에 CSS 글이 추천됐다

만들고 나서 결과를 쭉 훑어보는데, 대부분 괜찮았습니다.

| 글 | 추천된 글 |
| --- | --- |
| 트랜잭션과 격리 수준 | 데이터베이스 심화 — 인덱스, 트랜잭션, 정규화 |
| 방명록을 만들며 배우는 백엔드 | 조회수 붙이기, 데이터 저장소 선택 |
| 타입스크립트 유틸리티 타입 | 타입 레벨 프로그래밍, 제네릭 심화 |

그런데 하나가 이상했습니다.

> **컨테이너와 Docker** → 2위: **CSS 컨테이너 쿼리**

Docker 컨테이너와 CSS 컨테이너 쿼리는 **'컨테이너'라는 말만 같을 뿐 아무 상관이 없습니다.** 전형적인 **다의어(polysemy)** 문제죠. 단어를 세는 방식은 뜻을 모르니까요.

문제를 키운 건 두 글 다 그 단어를 **엄청나게 반복**한다는 점이었습니다. Docker 글은 "컨테이너"를 수십 번 쓰고, CSS 글도 그렇습니다. 그래서 유사도가 0.202까지 올라가 있었어요.

### 시도 1 — 사람이 붙인 분류를 믿자

먼저 **카테고리와 태그**를 신호로 더했습니다. 같은 카테고리면 ×1.25, 태그가 겹치면 조금 더. 기계가 모르는 걸 사람이 이미 분류해뒀으니까요.

결과는 **절반의 성공**이었습니다. 다른 글들의 순서는 나아졌는데, 정작 CSS 글은 여전히 2위였어요. 0.202가 너무 높아서 1.25배 정도로는 뒤집히지 않았습니다.

### 시도 2 — 몇 갈래로 겹치는지 세자

다시 보니 차이가 보였습니다.

- Docker ↔ **CI/CD와 컨테이너**: 컨테이너, 이미지, 배포, 쿠버네티스… **여러 갈래**로 겹침
- Docker ↔ **CSS 컨테이너 쿼리**: 오직 '컨테이너' **한 갈래**

**관련이 있다면 여러 갈래로 겹쳐야 한다.** 한 단어만 겹치는데 그 단어를 서로 많이 반복해서 점수가 높은 건, 관련이 아니라 우연입니다.

그래서 겹치는 **토큰의 가짓수**를 세서, 적으면 점수를 깎았습니다.

```ts
// 겹치는 갈래가 적으면 = 우연히 같은 단어를 쓴 것
similarity *= Math.min(1, overlap / ENOUGH_OVERLAP);
```

CSS 글은 **0.202 → 0.078**로 내려갔고, 그 자리를 "CI/CD — 빌드부터 배포까지"가 채웠습니다. 다른 글들도 같이 좋아졌어요. [복원력 패턴](/posts/resilience-patterns) 글은 추천이 [메시지 큐](/posts/message-queue)·[확장성](/posts/scalability-stateless)으로 정리됐습니다.

## 억지로 세 편을 채우지 않기

마지막으로 하나 더. 1위가 0.35인데 3위가 0.07이면, 그 3위는 **관련 글이 아니라 그냥 남은 것**입니다.

한 편이라도 엉뚱한 게 섞이면 추천 전체가 못 미더워 보입니다. 그래서 **1위의 25%에 못 미치면 아예 빼도록** 했습니다.

129편을 돌려보니 이렇게 나왔습니다.

| 추천 편 수 | 글 수 |
| --- | --- |
| 3편 | 102 |
| 2편 | 18 |
| 1편 | 9 |
| 0편 | 0 |

대부분은 3편을 채우고, 애매한 글은 솔직하게 적게 보여줍니다. Docker 글은 이제 확실한 2편만 뜨고, [트랜잭션](/posts/transactions-isolation) 글은 정말 가까운 1편만 뜹니다. **적게 보여주는 게 틀리게 보여주는 것보다 낫다**고 봤어요.

## 배운 것

- **같은 재료로 다른 걸 만들 수 있다** — 검색용 역색인이 그대로 추천의 기반이 됐다. 하루면 될 일이 반나절로 줄었다.
- **단어를 세는 방식은 뜻을 모른다** — '컨테이너'가 두 세계에서 다른 뜻이라는 걸 통계는 알 수 없다. 임베딩 같은 게 왜 필요한지 몸으로 알게 됐다.
- **사람이 남긴 힌트를 쓰자** — 카테고리·태그는 이미 있는 정답지였다. 기계가 못 하는 판단을 사람이 해둔 것이니 안 쓸 이유가 없다.
- **우연과 관련을 가르는 건 '갈래의 수'** — 한 단어가 많이 겹치는 것보다, 여러 단어가 조금씩 겹치는 게 진짜 관련이다.
- **빈칸을 억지로 채우지 말자** — [검색에서도](/posts/blog-search) 그랬듯, 애매하면 정직한 쪽이 낫다.
