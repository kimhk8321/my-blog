지난주에 [글 목차](/posts/blog-toc-popular)를 붙이면서 "글 **안에서** 이동"은 해결됐는데, "글 **사이의** 이동"이 여전히 아쉬웠습니다. 연재물이 17편이나 되는데 이전/다음 글이 **날짜순**으로만 이어져 있었거든요. 오늘은 그것과, 미뤄뒀던 방명록 관리 기능을 만들었습니다.

## 1부. 시리즈를 무엇으로 알아볼까

이 블로그엔 두 개의 연재물이 있습니다 — 모던 자바스크립트 Deep Dive 10편, 모던 리액트 7편. 제목이 이렇게 생겼죠.

```
모던 리액트 (3) — 배열 상태 관리와 useReducer
```

제목에 이미 `(3)`이 있으니 **거기서 뽑아내면 되지 않나** 싶었습니다. 정규식 한 줄이면 되고 파일을 고칠 필요도 없고요.

그런데 [목차를 만들며 배운 것](/posts/blog-toc-popular)이 떠올랐습니다 — **추측에 기대는 규칙은 언젠가 어긋난다.** 나중에 `(2026)` 같은 게 제목에 들어간 글을 쓰면 엉뚱하게 묶일 테고, 그 사고는 조용히 일어납니다.

그래서 frontmatter에 **명시**하기로 했습니다.

```yaml
title: "모던 리액트 (3) — 배열 상태 관리와 useReducer"
series: "모던 리액트"
seriesOrder: 3
```

17편에 넣는 건 스크립트로 한 번에 했습니다. 제목에서 뽑아 쓰되 **그 결과를 파일에 새겨** 이후로는 추측하지 않게 한 거죠. 한 번은 자동으로, 그 다음부터는 선언적으로.

> 여기서 걸린 게 하나 있었습니다. 이미 `order` 필드가 있었는데, 그건 **같은 날짜 글의 정렬용**이지 시리즈 번호가 아니었습니다. Deep Dive (1)편의 `order`가 5였거든요. 이름이 비슷하다고 재활용했으면 순서가 뒤죽박죽이 됐을 겁니다.

## 아카이브 — 시간순으로 훑기

140편이 되니 "그때 그 글" 을 찾는 방법이 하나 더 필요했습니다. 검색·카테고리·태그·추천이 있지만 전부 **주제 기반**이라, **시간 기반** 통로가 없었죠.

연·월로 묶는 건 단순합니다. 이미 최신순으로 정렬된 목록을 순서대로 훑으며 `Map`에 담기만 하면 됩니다.

```ts
for (const post of posts) {
  const [year, month] = post.date.split("-");
  // 정렬은 이미 돼 있으니, 순서를 유지한 채 묶기만 한다
}
```

정렬을 다시 하지 않고 **묶기만 한다**는 게 요령이었습니다. `Map`은 삽입 순서를 유지하니 그대로 연·월 순서가 됩니다.

## 2부. 관리자 자물쇠 — 계정 체계가 아니라

방명록에 이상한 글이 올라오면 **Upstash 콘솔을 직접 열어야** 했습니다. 진짜 구멍이었죠.

그런데 여기서 먼저 정리할 게 있었습니다. 이 블로그는 [댓글을 giscus](/posts/guestbook-backend)로 쓰는데, 그건 **GitHub 로그인**을 씁니다. 여기에 블로그 자체 계정을 또 만들면 한 사이트에 신원 체계가 둘이 되죠. 방문자 입장에선 "여기 가입은 왜 또 해?"가 됩니다.

그래서 만든 건 **계정 체계가 아니라 자물쇠 하나**입니다. 가입도, 사용자 목록도 없습니다. 비밀번호 하나로 나만 들어가는 문이죠.

## 세션을 어디에 둘까

[세션 vs JWT](/posts/auth-session-jwt)에서 이론으로 정리했던 선택을 실제로 하게 됐습니다.

**JWT**라면 서버가 아무것도 기억하지 않아도 되지만, **로그아웃이 어렵습니다.** 토큰 자체가 통행증이라 만료 전엔 회수할 방법이 마땅치 않죠.

**세션**은 서버가 기억해야 하지만, **지우면 즉시 무효**가 됩니다. 관리자 자물쇠에는 이게 맞다고 봤습니다. 어차피 Redis가 있으니 보관 비용도 없고요.

```ts
// 로그인: 임의 토큰을 만들어 저장소에 심고, 쿠키로 내려준다
const token = randomBytes(32).toString("hex");
await redis.set(`admin:session:${token}`, "1", { ex: SESSION_TTL });
```

로그아웃할 때 **쿠키만 지우면 안 됩니다.** 토큰이 저장소에 남아 있으면 그 값을 아는 사람은 계속 쓸 수 있으니, 서버 쪽도 함께 지웁니다.

## 쿠키에 붙인 세 가지

```ts
{
  httpOnly: true,   // 자바스크립트가 못 읽는다
  secure: true,     // HTTPS에서만 전송
  sameSite: "lax",  // 남의 사이트에서 온 요청엔 안 실린다
}
```

- **`httpOnly`** — [XSS](/posts/web-security)가 나더라도 세션을 훔쳐 가지 못하게. 쿠키를 `localStorage`에 두지 않는 이유가 이것입니다.
- **`secure`** — [HTTPS](/posts/https-tls)에서만. 평문으로 새어 나가지 않게.
- **`sameSite: lax`** — 외부 사이트가 몰래 요청을 보내도 쿠키가 안 붙어 CSRF가 크게 완화됩니다.

세 줄인데 각각이 다른 공격을 막습니다.

## 비밀번호 비교에서 시간이 샌다

여기가 오늘 가장 재밌었던 부분입니다. 비밀번호 확인은 이렇게 쓰기 쉽죠.

```ts
if (input === process.env.ADMIN_PASSWORD) { /* 통과 */ }
```

동작은 맞습니다. 그런데 문자열 비교는 **다른 글자가 나오는 순간 멈춥니다.** 첫 글자부터 틀리면 즉시, 앞 다섯 글자가 맞으면 조금 더 오래 걸리죠. 그 차이는 아주 작지만, **수없이 재서 평균을 내면 드러납니다.** 앞에서부터 한 글자씩 맞춰 나갈 수 있는 거죠(타이밍 공격).

해법은 **입력이 무엇이든 같은 시간이 걸리게** 만드는 것입니다.

```ts
const a = createHash("sha256").update(input).digest();
const b = createHash("sha256").update(expected).digest();
return timingSafeEqual(a, b);
```

먼저 해시로 **길이를 똑같이** 맞춥니다(길이 자체도 힌트니까요). 그리고 `timingSafeEqual`은 다른 값을 만나도 **끝까지** 비교합니다.

현실적으로 개인 블로그를 이렇게 공격할 사람은 없을 겁니다. 하지만 "비교는 그냥 `===`" 이라는 습관이 진짜 중요한 곳에서도 나올 테니, 여기서 익혀 두는 게 낫다고 봤어요.

## 비밀번호가 하나뿐이라 더 위험하다

계정이 하나면 공격자는 **아이디를 맞출 필요가 없습니다.** 비밀번호만 계속 던지면 되죠. 그래서 [방명록에 썼던 레이트 리밋](/posts/guestbook-backend)을 로그인에도 걸었습니다 — IP당 5분에 5회.

```ts
const attempts = await redis.incr(attemptKey);
if (attempts === 1) await redis.expire(attemptKey, WINDOW_SECONDS);
if (attempts > MAX_ATTEMPTS) return 429;
```

그리고 실패 메시지는 **뭉뚱그립니다.** "비밀번호가 틀렸다"고만 하고, 무엇이 얼마나 맞았는지는 알려주지 않습니다.

## 리스트에서 하나만 지우기

방명록은 [Redis List](/posts/guestbook-backend)에 담겨 있습니다. 그런데 리스트에는 **"3번째를 지워라"가 없습니다.** 값으로만 지울 수 있죠(`LREM`).

표준 우회법이 있습니다 — **지울 자리에 표식을 넣고, 그 표식을 지우는 것.**

```ts
await redis.lset(KEY, index, "__deleted__"); // 그 자리를 표식으로 덮고
await redis.lrem(KEY, 1, "__deleted__");     // 표식을 제거
```

자료구조가 못 하는 일을 **두 단계로 나눠** 해내는 방식이 인상적이었습니다. [방명록을 만들 때](/posts/guestbook-backend) List를 고른 게 최신순 정렬에는 딱 맞았는데, 삭제에서는 이런 대가를 치르는 거죠. **공짜인 선택은 없다**는 걸 다시 확인했습니다.

## 정적으로 굳어버린 관리자 페이지

거의 다 만들고 빌드했더니 이런 결과가 나왔습니다.

```
├ ○ /admin      ← 정적
```

`○`는 **빌드 시점에 미리 만들어 두는 페이지**라는 뜻입니다. 그런데 관리자 페이지는 **쿠키를 봐야** 로그인 여부를 알 수 있죠. 빌드할 땐 쿠키가 없으니, "로그인 폼" 화면이 그대로 굳어 배포되는 겁니다. 배포하고 나서야 "왜 로그인이 안 되지?" 하고 헤맸을 상황이었어요.

원인은 제 코드였습니다. 비밀번호가 설정돼 있는지 먼저 확인하고 있었는데, 빌드 시점엔 그게 없어서 **쿠키를 읽는 코드까지 가지도 못했습니다.** 쿠키를 읽어야 Next.js가 "이건 요청마다 그려야 하는 페이지"라고 판단하는데 말이죠.

```ts
export const dynamic = "force-dynamic";
```

한 줄로 해결했지만, **빌드 로그의 `○`와 `ƒ` 표시를 읽을 줄 알아야** 잡을 수 있는 문제였습니다. 통과했다고 다 된 게 아니더군요.

## 검증하면서 조심한 것

테스트하다 하나 배웠습니다. 로그인 실패를 7번 시도해 레이트 리밋을 확인했더니, **그 다음부터 올바른 비밀번호로도 로그인이 안 됐습니다.** 당연하죠, 제가 만든 잠금이 걸린 거니까요. 잠깐 "왜 안 되지?" 하고 코드를 의심했는데, 기능이 의도대로 동작한 것이었습니다.

카운터 키를 찾아보니 `rl:admin-login:::1` — IP가 `::1`(IPv6 로컬호스트)이더군요. 처음엔 `unknown`일 거라 짐작하고 엉뚱한 키를 지우고 있었습니다. **짐작한 키 이름으로 지우고 안 지워졌는데 넘어갔다면** 원인을 한참 못 찾았을 겁니다.

방명록 삭제도 실제 데이터를 건드리지 않도록, 테스트용 글을 **직접 만들어서 그것만** 지웠습니다.

## 배운 것

- **추측 대신 선언** — 제목에서 시리즈를 뽑아낼 수 있어도, 한 번 뽑은 뒤엔 파일에 새겨 둔다.
- **비슷한 이름을 재활용하지 말자** — `order`가 있다고 시리즈 번호로 쓸 뻔했다. 뜻이 다르면 필드도 달라야 한다.
- **로그아웃이 필요하면 서버가 기억해야 한다** — JWT와 세션의 선택은 취향이 아니라 요구사항에서 나온다.
- **`===` 하나에도 정보가 샌다** — 맞고 틀리고만이 아니라 **얼마나 걸렸는지**도 단서가 된다.
- **빌드 결과의 정적/동적 표시를 읽자** — 통과했다고 의도대로 동작하는 건 아니다.
