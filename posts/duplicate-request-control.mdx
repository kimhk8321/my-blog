결제 버튼을 한 번 눌렀는데 주문이 두 건 생겼다는 버그를 만났다고 해봅시다. 가장 먼저 떠오르는 해결책은 버튼을 비활성화하거나 debounce를 거는 것입니다. 사용자 경험은 좋아지지만 **서버가 한 번만 처리한다는 보장**은 생기지 않습니다.

중복 요청은 사용자의 빠른 클릭 말고도 여러 경로에서 만들어집니다.

## 같은 요청은 어디서 두 번 생기나

- 사용자가 버튼을 연속으로 누른다.
- 응답을 기다리다 새로고침한다.
- 모바일 네트워크가 끊긴 뒤 앱이나 중간 계층이 재시도한다.
- 응답은 유실됐지만 서버 처리는 이미 끝났다.
- 메시지 큐가 처리 확인을 받지 못해 메시지를 다시 전달한다.

마지막 두 경우가 까다롭습니다. 클라이언트는 실패로 보지만 서버에서는 성공했을 수 있습니다. 클라이언트가 같은 요청을 다시 보내는 건 합리적인 행동이고, 버튼 비활성화로는 막을 수 없습니다.

## debounce는 입력 빈도를 줄인다

```ts
const submit = debounce((payload) => {
  fetch("/api/orders", {
    method: "POST",
    body: JSON.stringify(payload),
  });
}, 300);
```

검색어 입력처럼 **마지막 값만 중요할 때**는 잘 맞습니다. 주문 생성처럼 클릭 한 번마다 의미가 있는 작업에서는 네트워크 재전송까지 통제하지 못하고, 300ms가 지난 뒤 다시 누르면 별도 요청이 됩니다.

## pending 잠금은 UI의 책임이다

```tsx
const [pending, setPending] = useState(false);

async function submit() {
  if (pending) return;
  setPending(true);

  try {
    await createOrder();
  } finally {
    setPending(false);
  }
}
```

요청 중 버튼을 잠그면 사용자가 상태를 이해하기 쉽고 불필요한 트래픽도 줄어듭니다. 하지만 탭을 두 개 열거나, 응답 유실 뒤 재시도하면 여전히 두 건이 들어옵니다. UI 잠금은 **좋은 UX와 부하 감소**, 서버의 중복 제어는 **데이터 무결성**을 맡습니다.

## HTTP 메서드의 멱등성

멱등하다는 것은 같은 요청을 여러 번 실행해도 최종 상태가 한 번 실행했을 때와 같다는 뜻입니다.

- `GET /orders/1`은 몇 번 읽어도 서버 상태가 같아야 합니다.
- `PUT /profiles/1`에 같은 전체 값을 보내면 최종 상태가 같습니다.
- `DELETE /items/1`은 두 번째 응답이 달라도 삭제된 상태는 같습니다.
- `POST /orders`는 호출할 때마다 새 주문을 만들 수 있으므로 기본적으로 멱등하지 않습니다.

POST가 나쁜 게 아닙니다. 새 리소스를 생성하는 의미에 맞습니다. 다만 결제나 주문처럼 중복 생성의 비용이 큰 작업에는 애플리케이션 수준의 장치가 더 필요합니다.

## 서버에서는 제약조건부터 건다

이메일당 계정 하나처럼 비즈니스 키가 분명하다면 DB의 UNIQUE 제약이 가장 강합니다.

```sql
CREATE UNIQUE INDEX users_email_unique ON users (email);
```

```ts
try {
  return await db.user.create({ data: { email } });
} catch (error) {
  if (isUniqueViolation(error)) {
    return db.user.findUnique({ where: { email } });
  }
  throw error;
}
```

`SELECT`로 존재 여부를 보고 `INSERT`하는 방식만 쓰면 두 요청이 동시에 조회를 통과할 수 있습니다. 마지막 방어선은 원자적으로 판정하는 데이터베이스여야 합니다.

주문처럼 자연스러운 UNIQUE 키가 없다면 클라이언트가 **이번 논리적 작업을 식별하는 키**를 만들고 서버가 기억해야 합니다. 이것이 다음 글에서 구현할 Idempotency Key입니다.

## 실패를 세 종류로 나눈다

| 상황 | 의미 | 보통의 대응 |
| --- | --- | --- |
| 연결 전에 실패 | 서버에 도달하지 않았을 가능성이 큼 | 재시도 가능 |
| 처리 중 5xx | 성공 여부가 불확실할 수 있음 | 같은 식별자로 재시도 |
| 4xx 검증 실패 | 같은 입력으로 다시 해도 실패 | 입력 수정 전 재시도하지 않음 |

타임아웃은 서버 처리가 실패했다는 뜻이 아니라 **정해진 시간 안에 답을 못 받았다**는 뜻입니다. 그래서 안전한 재시도에는 동일한 작업임을 증명할 식별자가 필요합니다.

---

중복 요청은 클릭 이벤트 문제가 아니라 분산된 두 시스템 사이의 불확실성 문제입니다. 클라이언트에서는 진행 상태를 보여주고 불필요한 전송을 줄이되, 데이터가 한 번만 바뀌어야 한다면 서버와 저장소에서 보장해야 합니다. 다음 글에서는 [Idempotency Key](/posts/idempotency-key)를 이용해 그 경계를 직접 구현합니다.
