그리디는 매번 좋아 보이는 선택을 합니다. 어려운 부분은 코드를 쓰는 것이 아니라, **그 선택을 나중에 후회하지 않아도 되는지** 설명하는 겁니다. 정렬하고 하나씩 고르는 코드가 짧다고 해서 정답인 것은 아닙니다.

## 회의를 가장 많이 잡으려면

회의는 `[시작, 종료]` 쌍으로 주어집니다. 시작은 종료보다 작고, 같은 시각에 한 회의가 끝나고 다음 회의가 시작하는 것은 허용합니다. 회의실 하나에 겹치지 않게 배치할 수 있는 최대 회의 수를 구합니다.

가능한 기준을 몇 가지 생각해 봅니다.

- 가장 먼저 시작하는 회의: `[0, 100]`을 먼저 고르면 짧은 회의를 여럿 놓칩니다.
- 길이가 가장 짧은 회의: `[3, 5]`를 먼저 고르면 `[0, 4]`, `[4, 8]` 두 개를 선택할 기회를 잃을 수 있습니다.
- 가장 먼저 끝나는 회의: 뒤에 남기는 시간을 최대한 확보합니다.

세 번째 기준으로 코드를 작성합니다.

```js
function selectMeetings(meetings) {
  const sorted = [...meetings].sort((a, b) => a[1] - b[1] || a[0] - b[0]);
  const selected = [];
  let lastEnd = -Infinity;

  for (const meeting of sorted) {
    if (meeting[0] < lastEnd) continue;
    selected.push(meeting);
    lastEnd = meeting[1];
  }
  return selected;
}

console.log(selectMeetings([[0, 4], [3, 5], [4, 8], [8, 9]]));
```

선택 결과는 `[[0, 4], [4, 8], [8, 9]]`입니다. 반환한 회의 배열은 원본의 내부 배열을 참조하지만 함수 안에서 수정하지 않습니다. 음수 시간도 허용할 수 있도록 첫 종료 시각은 0 대신 `-Infinity`로 뒀습니다.

정렬을 O(n log n)으로 가정하면 전체 시간 O(n log n), 입력 복사와 결과 저장에 O(n) 공간을 씁니다. `sort()`를 원본에 바로 호출하면 호출자의 입력 순서까지 바뀌므로 복사했습니다.

## 가장 먼저 끝나는 선택이 안전한 이유

최적 일정 하나의 첫 회의를 O, 전체 후보 중 가장 먼저 끝나는 회의를 G라고 합시다. G는 O보다 늦게 끝나지 않습니다.

최적 일정의 첫 회의 O를 G로 바꿔도 그 뒤 회의들은 그대로 들어갑니다. 뒤의 회의는 O가 끝난 다음에 시작하고, G는 그보다 일찍 또는 같은 시각에 끝나기 때문입니다. 회의 수를 잃지 않으면서 첫 선택을 G로 맞춘 최적 일정이 존재합니다.

G 뒤에 들어갈 수 있는 회의만 남기면 같은 문제가 다시 생깁니다. 이 교환을 반복하므로 그리디 결과도 최적입니다. “빨리 끝나니 좋아 보인다”보다 이 설명이 중요한 부분입니다.

단, 회의마다 보상이 다르면 이야기가 달라집니다. 회의 두 개의 보상이 각각 1이고 긴 회의 하나의 보상이 100이라면 개수를 최대화하는 선택은 최대 보상을 보장하지 않습니다. 문제의 목적 함수가 바뀌면 증명도 다시 해야 합니다.

## 큰 동전부터 쓰면 항상 맞을까

다음 함수는 큰 동전부터 최대한 사용하는 단순한 그리디입니다. 동전은 양의 정수이며 개수 제한이 없습니다.

```js
function greedyCoinCount(coins, amount) {
  const sorted = [...new Set(coins)].sort((a, b) => b - a);
  let remaining = amount;
  let count = 0;

  for (const coin of sorted) {
    const used = Math.floor(remaining / coin);
    count += used;
    remaining -= used * coin;
  }
  return remaining === 0 ? count : -1;
}

console.log(greedyCoinCount([1, 3, 4], 6));
console.log(greedyCoinCount([3, 4], 6));
```

첫 결과는 `4 + 1 + 1`로 3개지만 최적은 `3 + 3`인 2개입니다. 두 번째는 -1을 반환하지만 역시 `3 + 3`으로 만들 수 있습니다. 이 함수의 -1은 **그리디 경로에서 만들지 못했다**는 뜻일 뿐, 가능한 조합이 없다는 증명이 아닙니다.

모든 동전 체계에 이 풀이를 쓰면 안 됩니다. 각 단위가 다음 단위의 정수배가 되는 체계처럼 별도의 성질이 있거나, 그리디가 최적인 체계임이 증명돼야 합니다. 임의의 동전 집합에서는 [다음 편의 DP](/posts/algorithm-08-dynamic-programming)를 사용하겠습니다.

## 정렬 기준을 검증하는 순서

후보 기준이 떠오르면 먼저 작은 반례를 찾아봅니다. 시작이 빠른 것, 길이가 짧은 것, 보상이 큰 것 같은 기준을 일부러 깨 보는 겁니다. 그다음 최적해의 선택을 내 선택으로 바꿔도 손해가 없는지 확인합니다.

작은 입력의 완전 탐색 결과와 비교하는 것도 도움이 됩니다. 하지만 테스트가 많이 통과했다는 사실만으로 모든 입력에 대한 증명이 되지는 않습니다. 테스트는 틀린 주장을 빠르게 찾는 도구이고, 교환 논증은 왜 항상 성립하는지 설명하는 도구입니다.

그리디가 확실하지 않은데 풀이가 너무 복잡해진다면, 선택 결과를 상태로 남겨 비교하는 쪽으로 돌아갈 때입니다. [동적 계획법 편](/posts/algorithm-08-dynamic-programming)에서 그 차이를 보겠습니다.
