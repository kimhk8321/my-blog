HTTP는 **무상태(stateless)** 입니다. 요청 하나하나가 독립적이라, 서버는 방금 로그인한 사람이 이번 요청의 그 사람인지 **기본적으로 모릅니다.** "로그인 상태 유지"는 이 무상태 위에 상태를 얹는 장치죠. 그 방법이 크게 **세션**과 **토큰(JWT)** 둘입니다.

## 먼저 — 인증 vs 인가

자주 뭉뚱그리지만 다릅니다.

- **인증(Authentication)**: **누구인가?** (로그인) → 실패 시 `401 Unauthorized`
- **인가(Authorization)**: **무엇을 할 수 있는가?** (권한) → 실패 시 `403 Forbidden`

로그인은 됐지만(인증 O) 남의 글을 지우려 하면(인가 X) `403`입니다. ([상태 코드](/posts/rest-api-design)의 그 구분이죠.)

## 세션 기반 — 서버가 기억한다

전통적 방식입니다. 로그인하면 **서버가 세션을 만들어 저장**하고, 클라이언트엔 **세션 ID**만 쿠키로 줍니다.

```
로그인 → 서버가 세션 저장(예: Redis에 { sessionId → userId })
       → 쿠키에 sessionId 전달
이후 요청 → 쿠키의 sessionId로 서버가 "누구"인지 조회
```

- **장점**: 서버가 세션을 쥐고 있어 **즉시 무효화**(로그아웃·강제 로그아웃)가 쉽다.
- **단점**: 서버가 상태를 저장해야 함 → 서버가 여러 대면 세션 저장소를 공유([Redis](/posts/data-store-selection) 등)해야 확장 가능.

## 토큰 기반 — 서버가 기억하지 않는다 (JWT)

**JWT(JSON Web Token)** 는 로그인 정보를 **토큰 자체에 담아 서명**해 클라이언트에게 줍니다. 서버는 저장하지 않고, 요청마다 토큰의 **서명만 검증**합니다.

```
헤더.페이로드.서명
eyJhbGc...  .  eyJ1c2VySWQiOjF9  .  서명
```

- **페이로드**: `userId` 등 정보 (누구나 디코드 가능 — **비밀 정보 넣지 말 것**)
- **서명**: 서버의 비밀키로 만든 것. 변조하면 서명이 안 맞아 거부됨.

```
로그인 → 서버가 JWT 서명해 발급
이후 요청 → Authorization: Bearer <token> → 서버는 서명만 검증(저장소 조회 없음)
```

- **장점**: **무상태**라 서버 확장이 쉽다(저장소 조회 불필요). 마이크로서비스 간 전달도 편함.
- **단점**: 발급한 토큰을 **즉시 무효화하기 어렵다**(서버가 기억을 안 하니까). 그래서 **짧은 만료 + 리프레시 토큰** 조합을 씁니다 — 액세스 토큰은 짧게(분 단위), 갱신용 리프레시 토큰은 길게 두고 서버에서 관리.

## 토큰을 어디에 저장하나 — 쿠키 vs localStorage

프론트엔드 개발자에게 가장 중요한 결정입니다. [웹 보안](/posts/web-security)에서 다룬 XSS·CSRF가 여기서 충돌합니다.

- **localStorage**: 쓰기 쉽지만 **XSS에 취약**. 스크립트가 주입되면 토큰이 탈취됩니다.
- **httpOnly 쿠키**: JS로 못 읽어 **XSS엔 안전**하지만, 자동 전송되므로 **CSRF 방어**(SameSite 속성, CSRF 토큰)가 필요.

일반적으로 **httpOnly + Secure + SameSite 쿠키**가 권장됩니다. "편한 localStorage"의 유혹이 보안 사고로 이어지는 대표 사례예요.

## OAuth — 남의 인증을 빌리기

"구글로 로그인" 같은 것. 우리 서버가 비밀번호를 직접 받지 않고, **신뢰할 수 있는 제공자(구글 등)에게 인증을 위임**받아 토큰을 받는 흐름입니다. 비밀번호를 저장·관리하는 부담과 위험을 덜죠.

## 세션 vs JWT, 무엇을?

| | 세션 | JWT |
| --- | --- | --- |
| 상태 | 서버가 저장(stateful) | 무상태(stateless) |
| 무효화 | 즉시 가능 | 어려움(만료로 대응) |
| 확장 | 저장소 공유 필요 | 쉬움 |
| 적합 | 웹 앱, 즉시 로그아웃 중요 | API·MSA·모바일 |

정답은 없고 트레이드오프입니다. 하나의 서버 웹앱이면 세션이 단순하고 안전하며, 여러 서비스·클라이언트가 얽히면 JWT가 유연합니다.
