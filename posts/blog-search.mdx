글이 어느새 **128편**이 됐습니다. 그런데 정작 제가 예전에 쓴 글을 못 찾겠더군요. 카테고리와 태그로만 훑어야 하니까요. "그 캐시 얘기 어디에 썼더라?" 하고 목록을 위아래로 스크롤하는 저를 발견하고, 검색을 만들기로 했습니다.

마침 [인덱스 이론](/posts/query-performance)을 막 정리한 참이라, 이번엔 그 인덱스를 **직접 만들어보기로** 했습니다.

## 왜 서버에서, 왜 색인인가

가장 쉬운 방법은 클라이언트에서 배열을 `filter`로 훑는 것입니다. 실제로 많은 블로그가 그렇게 하죠. 그런데 두 가지가 걸렸습니다.

- 128편의 **본문 전체**를 브라우저로 내려보내야 함(수백 KB).
- 검색할 때마다 128편 × 본문 길이를 처음부터 훑음 — 전형적인 **풀 스캔**.

DB에서 인덱스 없이 `WHERE`를 걸면 전체 행을 훑는 것과 똑같은 상황입니다. 글이 늘수록 선형으로 느려지죠. 그래서 서버에 **역색인(inverted index)** 을 만들기로 했습니다.

역색인의 발상은 책 뒤 "찾아보기"와 같습니다. 책을 처음부터 읽으며 단어를 찾는 대신, 색인에서 단어를 찾아 **페이지 번호로 바로 점프**하는 거죠.

```
일반적인 방향:  글1 → [캐시, 무효화, TTL, ...]
역색인의 방향:  "캐시" → [글1, 글7, 글23, ...]   ← 뒤집었다
```

검색어가 들어오면 128편을 훑는 게 아니라, **해시 조회 한 번**으로 후보 글 목록을 얻습니다.

## 첫 번째 벽 — 한글은 공백으로 안 갈린다

영어 검색은 쉽습니다. `"event loop"`를 공백으로 쪼개면 `event`, `loop`라는 깔끔한 단어가 나오죠. 그런데 한글은 다릅니다.

> "이벤트 루프**를** 막으면 안 되는 이유"

여기서 "루프를"을 통째로 색인하면, 사용자가 **"루프"** 라고 검색했을 때 안 잡힙니다. 조사가 붙어버리니까요. 한국어는 교착어라 명사 뒤에 은/는/이/가/을/를/의가 줄줄이 붙습니다.

제대로 하려면 **형태소 분석기**(mecab-ko 등)로 "루프 + 를"을 분리해야 합니다. 하지만 사전 데이터가 무겁고, 서버리스 환경에 올리기 부담스러웠어요. 그래서 **n-gram**을 선택했습니다.

n-gram은 그냥 **글자 단위로 잘게 쪼개는** 방식입니다.

```
"이벤트루프" → 유니그램: 이, 벤, 트, 루, 프
              → 바이그램: 이벤, 벤트, 트루, 루프
```

이렇게 색인해두면 "루프"로 검색할 때 바이그램 `루프`가 그대로 맞아떨어집니다. 조사가 붙어 있든 말든 상관없어요. 형태소 분석보다 부정확하지만, **사전 없이 동작하고 신조어에도 강합니다**.

```ts
if (run.charCodeAt(0) >= 0xac00) {
  // 한글 색인: 유니그램 + 바이그램 (검색할 땐 조금 다르게 — 아래 삽질 3)
  for (let i = 0; i < run.length; i++) {
    out.push(run[i]);
    if (i + 1 < run.length) out.push(run.slice(i, i + 2));
  }
}
```

## 두 번째 발견 — 색인할 때와 검색할 때는 다르게 쪼갠다

영문은 단어 단위로 색인하면 되는데, 문제가 하나 있었습니다. 검색창에 타이핑하는 도중에는 **단어가 완성되지 않았다**는 것.

`docke`까지 쳤을 때 "Docker" 글이 나와야 자연스럽죠. 그런데 색인에 `docker`만 있으면 `docke`는 못 찾습니다.

해결은 **색인할 때 접두사도 함께 넣는 것**입니다(edge n-gram).

```
색인: "docker" → docker, do, doc, dock, docke   ← 접두사까지 저장
검색: "docke"  → docke                          ← 입력한 그대로만
```

여기서 배운 게 재밌었습니다. **색인 시점(index-time)과 검색 시점(query-time)의 토큰화가 달라도 된다** — 아니, 달라야 합니다. 저는 막연히 "같은 함수로 쪼개면 되겠지" 생각했는데, 실제 검색엔진(Elasticsearch 등)도 index analyzer와 search analyzer를 따로 설정하더군요.

```ts
function tokenize(text: string, mode: "index" | "query"): string[]
```

## 세 번째 문제 — "의", "이"가 모든 글에 있다

n-gram으로 쪼개니 새 문제가 생겼습니다. **조사와 흔한 글자가 전부 토큰이 됩니다.** "서버의 캐시"를 검색하면 `의`라는 유니그램이 128편 전부에 매칭되죠. 검색 결과가 엉망이 됩니다.

보통은 **불용어(stopword) 목록**을 만들어 "은/는/이/가/의는 무시"라고 하드코딩합니다. 그런데 한국어 불용어 목록을 직접 관리하는 건 끝이 없어 보였어요.

그래서 **IDF(역문서빈도)** 를 썼습니다. 발상은 단순합니다 — **"많은 글에 나오는 토큰일수록 변별력이 없다."**

```ts
function idf(docFreq: number, total: number): number {
  return Math.log(1 + total / docFreq);
}
```

- `의` → 128편 전부에 등장 → `log(1 + 128/128)` = **0.69** (거의 무시)
- `서킷` → 2편에만 등장 → `log(1 + 128/2)` = **4.17** (강하게 반영)

불용어 목록이 **한 줄도 없이** 조사 문제가 해결됐습니다. "흔한 건 안 중요하다"는 원리만으로요. 이게 이번 구현에서 제일 감탄한 부분입니다.

## 랭킹 — 어디에 나왔는지가 중요하다

같은 단어라도 **제목**에 있는 것과 **본문 구석**에 있는 건 무게가 다릅니다. 필드별 가중치를 줬어요.

| 필드 | 가중치 |
| --- | --- |
| 제목 | 12 |
| 태그 | 8 |
| 설명 | 4 |
| 본문 | 1 |

그리고 검색어 토큰이 **전부 들어있는 글(AND)** 을 우선 보여주되, 그런 글이 하나도 없으면 일부만 맞는 글이라도 보여주도록(OR 폴백) 했습니다. "결과 없음"보다는 비슷한 거라도 주는 게 낫죠.

여기까지 만들고 "됐다" 싶었는데, 실제로 써보니 순위가 이상했습니다. 진짜 어려운 건 지금부터였어요.

## 삽질 1 — 단어를 많이 반복한 글이 이긴다

`React`로 검색했더니 **"React Native 입문"** 이 1위였습니다. React Native는 엄밀히 다른 프레임워크인데요. 세어보니 답이 나왔습니다.

| 글 | `react` 등장 |
| --- | --- |
| React Native 입문 | **22회** |
| React Query | 12회 |
| React Context API | 7회 |

"React Native"를 반복해서 쓰다 보니 `react`가 22번 나왔고, 그 빈도로 1위를 먹은 겁니다. 본문 등장 횟수(tf)를 그대로 점수에 더한 게 원인이었어요. 로그로 눌렀는데도 부족했습니다.

이건 검색 분야의 고전적인 문제고, 해법도 정해져 있습니다 — **BM25**입니다.

```ts
function bm25Tf(tf: number, docLength: number, avgLength: number): number {
  const norm = 1 - B + B * (docLength / avgLength);
  return (tf * (K1 + 1)) / (tf + K1 * norm);
}
```

핵심은 두 가지입니다.

- **포화(k1)**: 반복의 가치가 금방 한계에 다다릅니다. 5번이든 50번이든 점수 차이가 거의 없어요. "한 번 나왔다 → 열 번 나왔다"는 큰 차이지만, "50번 → 100번"은 별 의미가 없다는 직관을 수식으로 옮긴 겁니다.
- **길이 보정(b)**: 긴 글은 그만큼 할인합니다. 길어서 많이 나온 것과, 짧은데도 자주 나온 것을 구분하죠.

## 삽질 2 — 시리즈 순서가 제멋대로

BM25로 고쳤더니 이번엔 다른 게 눈에 띄었습니다. "리액트"로 검색하니 시리즈물이 이렇게 나오더군요.

```
모던 리액트 (2) → (1) → (4) → (7) → (5) → (3) → (6)
```

7편짜리 연재인데 순서가 뒤죽박죽입니다. 원인을 파보니 **설명(description)에 "리액트"가 들어간 (1)(2)(4)만 점수가 높았고**, 나머지는 본문 빈도로 미세하게 갈리고 있었어요.

생각해보면 이 7편은 **관련도가 사실상 동일합니다**. 제목이 다 "모던 리액트 (n)"이니까요. 이렇게 우열을 가릴 수 없을 때 소수점 차이로 줄을 세우면, 사용자 눈에는 그냥 **무작위**로 보입니다.

그래서 점수를 두 갈래로 나눴습니다.

- **주제 점수**(제목·태그): "이 글이 그 주제인가"
- **보조 점수**(설명·본문): "얼마나 언급했나"

**주제 점수로 등급을 나누고, 같은 등급 안에서는 글 목록과 똑같은 순서**를 씁니다.

```ts
if (tierA !== tierB) return tierB - tierA;
// 주제 관련도가 같으면 글 목록과 같은 순서로 (시리즈가 이어지도록)
return a - b;
```

이제 시리즈가 (7)→(1)로 목록과 같은 순서로 이어집니다. **애매할 땐 예측 가능한 순서가 낫다** — 이게 이번에 배운 것 중 제일 실용적이었어요. 검색 품질은 정확도만이 아니라 **납득 가능성**의 문제이기도 하더군요.

## 삽질 3 — '트'가 '컴포넌트'에 걸린다

시리즈 문제를 파다가 곁가지로 하나 더 찾았습니다. "리액트"를 검색하면 토큰이 `리`, `액`, `트`, `리액`, `액트`로 쪼개지는데, 이 중 **유니그램 `트`가 "컴포넌트", "이벤트", "테스트"에 전부 걸리고 있었습니다.**

한 글자 검색("훅")을 지원하려고 유니그램을 넣었는데, 그게 노이즈가 된 거죠. 해결은 간단했습니다 — **색인할 땐 유니그램을 넣되, 검색할 땐 두 글자 이상이면 빼는 것.**

```ts
if (run.length === 1) { out.push(run); continue; }  // "훅" 같은 한 글자 검색
for (let i = 0; i < run.length; i++) {
  if (mode === "index") out.push(run[i]);           // 색인에만 유니그램
  if (i + 1 < run.length) out.push(run.slice(i, i + 2));
}
```

여기서도 **색인과 검색을 다르게 다룬다**는 원칙이 또 나왔습니다. 이 글을 쓰며 세어보니, 이번 구현에서 그 원칙이 세 번 등장하네요.

## 색인은 언제 만드나

색인을 매 검색마다 새로 만들면 본말전도입니다. 글은 **배포 시점에 고정된 파일**이니, 한 번 만들고 계속 재사용하면 됩니다.

```ts
let cachedIndex: SearchIndex | null = null;

function getIndex(): SearchIndex {
  // 개발 중엔 글을 고칠 때마다 반영되도록 매번 새로 만든다
  if (process.env.NODE_ENV !== "production") return buildIndex();
  return (cachedIndex ??= buildIndex());
}
```

[Next.js 16의 `use cache`](/posts/nextjs-caching)를 쓸까 했는데, 그건 `cacheComponents` 옵션을 켜야 하는 기능이라 이번엔 단순한 모듈 레벨 메모이제이션으로 갔습니다. [캐싱 전략](/posts/server-caching)에서 정리한 "비싼 계산을 반복하지 않는다"의 가장 소박한 형태죠.

## API — 여기서도 입력을 믿지 않는다

[Route Handler](/posts/nextjs-route-handlers)로 `GET /api/search?q=` 하나를 열었습니다. 검색은 상태를 바꾸지 않으니 `GET`이 맞고요.

```ts
if (query.length > MAX_QUERY_LENGTH) {
  return NextResponse.json({ error: "검색어는 50자 이하로..." }, { status: 400 });
}
```

프론트 `input`에 `maxLength={50}`을 걸어놨지만, **서버에서 다시** 막습니다. [방명록](/posts/guestbook-backend)에서 배운 그대로예요 — 프론트 검증은 UX용, [서버 검증은 보안용](/posts/server-security).

## 프론트에서 챙긴 세 가지

**1. 디바운스** — 한 글자 칠 때마다 요청을 보내면 낭비입니다. 200ms 쉬었다 보냅니다.

**2. 요청 취소** — 이게 은근히 중요했습니다. 빠르게 타이핑하면 요청이 여러 개 날아가는데, **먼저 보낸 게 나중에 도착**할 수 있습니다. 그러면 `docke`를 다 쳤는데 `doc` 결과가 화면에 남죠. `AbortController`로 이전 요청을 취소해서 막았습니다.

```ts
const controller = new AbortController();
fetch(url, { signal: controller.signal });
return () => controller.abort(); // 다음 입력이 오면 이전 요청 취소
```

**3. 강조 표시** — 검색어와 겹치는 부분을 `mark` 태그로 감쌉니다. 여기서도 [XSS](/posts/web-security)를 조심해야 하죠. `dangerouslySetInnerHTML` 없이 **문자열을 쪼개 React 엘리먼트로** 만들면 자동 이스케이프되어 안전합니다. 사용자 입력을 정규식에 넣기 전에 특수문자 이스케이프도 잊지 않고요.

주소창에 `?q=` 로 검색어를 남겨서, 검색 결과 링크를 공유할 수 있게도 했습니다.

그리고 작은 것 하나 — 영문을 **한 글자만** 치면 결과가 안 나옵니다(접두사를 두 글자부터 색인했으니까요). 여기에 "결과가 없습니다"를 띄우면 사용자는 **없는 줄 알고 포기합니다**. 그래서 "영문·숫자는 두 글자 이상 입력해 주세요"라고 안내를 바꿨어요. 같은 빈 화면이라도, **막다른 길인지 한 걸음 더 가면 되는 길인지**를 알려주는 건 다릅니다.

## 배운 것

이론으로 읽은 [인덱스](/posts/query-performance)를 직접 만들어보니 감각이 달라졌습니다.

- **인덱스는 마법이 아니라 자료구조다** — "미리 뒤집어 놓은 map"일 뿐이고, 그래서 조회가 빠른 대신 **만드는 비용과 메모리**를 낸다. 트레이드오프가 손에 잡혔다.
- **색인과 검색은 대칭이 아니어도 된다** — 같은 텍스트라도 넣을 때와 찾을 때 다르게 다룬다. 이번 구현에서만 세 번 써먹은 원칙.
- **통계가 규칙을 대신할 수 있다** — 불용어 목록(사람이 만든 규칙) 대신 IDF(데이터에서 나온 통계)로 더 깔끔하게 해결됐다.
- **애매하면 예측 가능한 쪽으로** — 우열을 가릴 수 없는 글들을 소수점 차이로 줄 세우면 사용자에겐 무작위로 보인다. 차라리 목록과 같은 순서가 낫다.
- **검색은 만드는 것보다 튜닝이 어렵다** — 동작하게 만드는 데는 반나절, 납득 가능한 순위를 만드는 데는 그 몇 배가 들었다.

물론 이건 128편짜리 개인 블로그니까 가능한 방식입니다. 글이 수만 편이 되면 메모리에 색인을 다 올릴 수 없어 [전용 검색엔진](/posts/data-store-selection)이 필요하겠죠. 하지만 "왜 그런 게 필요한가"를 이제는 직접 겪어서 압니다.
