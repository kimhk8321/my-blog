[Jest](/posts/jest-testing)로 함수를, [React Testing Library](/posts/react-testing)로 컴포넌트를 테스트해도 남는 불안이 있습니다. **"그래서 실제로 브라우저에서 눌러보면 되나?"**

컴포넌트 테스트는 jsdom이라는 가짜 브라우저 위에서 돕니다. 실제 렌더링도, 실제 네트워크도, 실제 라우팅도 아니죠. E2E 테스트는 **진짜 브라우저를 띄워** 사용자가 하는 그대로 눌러봅니다.

## 무엇을 잡아주나

E2E가 아니면 놓치는 것들입니다.

- **여러 페이지에 걸친 흐름** — 로그인 → 목록 → 상세 → 작성
- **실제 라우팅** — 새로고침, 뒤로가기, 주소 직접 입력
- **진짜 CSS** — 버튼이 다른 요소에 가려져 클릭이 안 되는 상황
- **빌드된 결과물** — 개발 서버에선 되는데 프로덕션 빌드에서 깨지는 것
- **브라우저 차이** — 크롬에선 되는데 사파리에선 안 되는 것

반대로 말하면, 이런 게 걱정 없는 로직은 E2E로 검증할 이유가 없습니다.

## Playwright 기본

```ts
import { test, expect } from "@playwright/test";

test("방명록을 남기면 목록에 나타난다", async ({ page }) => {
  await page.goto("/guestbook");

  await page.getByPlaceholder("이름").fill("테스터");
  await page.getByPlaceholder(/한마디/).fill("안녕하세요");
  await page.getByRole("button", { name: "남기기" }).click();

  await expect(page.getByText("안녕하세요")).toBeVisible();
});
```

읽어 보면 **사용자가 하는 말 그대로**입니다. "이름 칸에 채우고, 남기기 버튼을 누르고, 화면에 보이는지 본다."

## 선택자 — 무엇으로 요소를 찾을까

E2E가 깨지는 가장 흔한 이유는 **선택자가 구현에 묶여 있어서**입니다. 우선순위는 이렇습니다.

1. **역할과 이름** — `getByRole("button", { name: "저장" })`. 사용자가 인식하는 방식 그대로라 가장 안정적이고, [접근성](/posts/web-accessibility)이 잘 돼 있으면 자연히 잘 잡힙니다.
2. **라벨·플레이스홀더** — 폼 요소에 적합
3. **테스트 전용 id** — `data-testid`. 위로 안 될 때의 탈출구
4. **CSS 선택자** — `.btn-primary.mt-4` 같은 건 최후의 수단. 스타일을 고치면 테스트가 깨집니다

"버튼의 클래스가 바뀌었다고 테스트가 깨지면 그건 테스트가 잘못된 것"이라는 감각이 중요합니다.

## 자동 대기 — sleep을 쓰지 마라

E2E 초보의 함정이 `waitForTimeout(2000)` 같은 코드입니다. 느린 기기에선 여전히 실패하고, 빠른 기기에선 쓸데없이 느려지죠.

Playwright의 `expect`와 `locator`는 **조건이 만족될 때까지 자동으로 기다립니다.**

```ts
// 나쁨: 시간에 걸기 — 언젠가 반드시 깨진다
await page.waitForTimeout(2000);
expect(await page.locator(".result").count()).toBe(3);

// 좋음: 상태에 걸기 — 준비되면 즉시 통과
await expect(page.getByRole("listitem")).toHaveCount(3);
```

**시간이 아니라 상태를 기다리는 것** — E2E의 제1원칙입니다.

## 불안정한 테스트(flaky)를 다루기

E2E가 미움받는 이유는 대개 **가끔 실패**하기 때문입니다. 신뢰를 잃으면 사람들은 빨간불을 무시하게 되고, 그러면 테스트가 있으나 마나가 되죠.

흔한 원인과 처방:

- **애니메이션** — 전환 중에 클릭이 빗나감 → 테스트 환경에서 애니메이션 끄기
- **네트워크 변동** — 외부 API에 의존 → 응답을 가로채 고정([테스트 더블](/posts/test-doubles))
- **시간·랜덤** — 실행할 때마다 다름 → 고정하기
- **테스트 간 간섭** — 앞 테스트가 남긴 데이터 → 각 테스트가 **자기 데이터를 만들고 치우게**
- **경쟁 상태** — 요청이 끝나기 전에 단언 → 자동 대기에 맡기기

```ts
// 외부 응답을 고정해 흔들림을 없앤다
await page.route("**/api/search*", (route) =>
  route.fulfill({ json: { results: [] } }),
);
```

가끔 실패하는 테스트는 **고치거나 지우거나** 해야 합니다. 방치가 가장 나쁩니다.

## 얼마나 쓸 것인가

E2E는 느리고 깨지기 쉽습니다. [테스트 피라미드](/posts/backend-testing)에서 맨 위에 놓이는 이유죠.

- **핵심 흐름 몇 개만** — 가입, 결제, 글 작성처럼 "깨지면 서비스가 죽는" 것
- 세세한 분기·경계값은 **아래층(단위·통합)** 에서
- [CI](/posts/ci-cd)에서 자동 실행하되, 시간이 오래 걸리면 병렬 실행이나 배포 전 단계로 분리

## 디버깅이 편하다

Playwright가 좋은 점은 실패했을 때의 단서입니다 — **스크린샷, 동영상, 그리고 전체 조작을 되감아 보는 트레이스**를 남깁니다. CI에서 난 실패도 로컬에서 그대로 재생해 볼 수 있어요.

E2E는 "**진짜로 되는지**"를 확인하는 유일한 층입니다. 대신 비싸고 깨지기 쉬우니 **핵심 흐름만, 상태를 기다리게, 사용자가 보는 방식으로** 쓰는 게 요령입니다. 다음 글에서는 그 과정에서 자주 쓰게 되는 [테스트 더블](/posts/test-doubles)을 정리합니다.
