"CSS 우선순위는 어떻게 결정되나요?"라는 질문에 보통 "id가 클래스보다 세고, 클래스가 태그보다 세다"고 답합니다. 틀린 말은 아니지만, 그건 전체 규칙 중 **한 단계**일 뿐입니다. 명시도가 더 높은데도 지는 경우, `!important`끼리 붙었을 때, `@layer`를 쓸 때를 설명하려면 전체 순서를 알아야 합니다.

## 캐스케이드란

한 요소의 한 속성(예: `color`)에 값을 주는 규칙이 여러 개일 때, **어떤 값을 최종으로 쓸지 정하는 알고리즘**이 캐스케이드(Cascade, 폭포)입니다. 이름처럼 위 단계부터 차례로 비교하고, **앞 단계에서 승부가 나면 뒤 단계는 보지 않습니다.**

CSS Cascading 명세(레벨 5) 기준 비교 순서는 이렇습니다.

1. **출처와 중요도** (Origin and Importance)
2. **컨텍스트** (Shadow DOM 안팎)
3. **요소에 직접 붙은 스타일** (style 속성)
4. **레이어** (`@layer`)
5. **명시도** (Specificity)
6. **선언 순서** (Order of Appearance)

명시도는 다섯 번째입니다. 앞의 네 단계에서 이미 승부가 나면 명시도는 계산조차 하지 않습니다.

## 1단계. 출처와 중요도

CSS는 세 군데서 옵니다.

| 출처 | 예 |
| --- | --- |
| 브라우저 기본(user-agent) | `h1`이 굵고 큰 이유, `a`가 파란 이유 |
| 사용자(user) | 사용자가 브라우저 설정으로 지정한 글꼴 크기 등 |
| 작성자(author) | 우리가 작성한 CSS |

평소에는 **작성자 > 사용자 > 브라우저 기본** 순서로 이깁니다. 그래서 우리 CSS가 브라우저 기본 스타일을 덮어씁니다.

그런데 `!important`가 붙으면 순서가 **뒤집힙니다.** 우선순위를 높은 것부터 나열하면 이렇습니다.

1. 진행 중인 transition
2. `!important` 브라우저 기본
3. `!important` 사용자
4. `!important` 작성자
5. 진행 중인 animation
6. 일반 작성자
7. 일반 사용자
8. 일반 브라우저 기본

왜 뒤집을까요? 시력이 약한 사용자가 "모든 글자를 크게"를 `!important`로 지정했다면, 사이트 작성자의 `!important`보다 사용자의 설정이 이겨야 하기 때문입니다. `!important`는 "내가 이기겠다"가 아니라 **"이 값은 꼭 지켜야 한다"는 표시**이고, 지켜야 할 우선권은 사용자 쪽에 있다는 설계입니다.

## 2단계. 컨텍스트

Shadow DOM을 쓰는 웹 컴포넌트에서, 바깥 문서의 스타일과 컴포넌트 안쪽 스타일이 부딪힐 때의 규칙입니다. 일반적인 화면에서는 거의 만나지 않으니 "이런 단계가 있다" 정도만 알면 됩니다.

## 3단계. 요소에 직접 붙은 style 속성

```html
<p class="title" style="color: red">빨간색</p>
```

`style` 속성으로 직접 준 값은, 선택자로 쓴 규칙보다 이깁니다. 흔히 "인라인 스타일은 명시도가 (1, 0, 0, 0)"이라고 외우는데, 지금 명세에서는 명시도 계산의 일부가 아니라 **명시도보다 앞선 별도의 단계**로 정의돼 있습니다. 결과는 같습니다. 선택자를 아무리 구체적으로 써도 인라인 스타일을 이길 수 없고, 이기려면 `!important`가 필요합니다(1단계에서 승부가 나니까요).

## 4단계. 레이어 (@layer)

`@layer`는 스타일을 층으로 나누고 **층의 순서**로 우선순위를 정하는 기능입니다.

```css
@layer reset, base, components;   /* 나중에 선언한 층이 이김 */

@layer reset {
  #app .title { color: gray; }    /* 명시도 높음 */
}

@layer components {
  .title { color: blue; }         /* 명시도 낮음 */
}
```

결과는 **파란색**입니다. `components` 층이 `reset` 층보다 뒤에 선언돼서, 4단계에서 이미 이깁니다. 5단계 명시도까지 가지 않으니 `#app .title`의 높은 명시도는 의미가 없습니다.

레이어의 규칙은 두 가지만 기억하면 됩니다.

- **레이어 밖의 일반 스타일은 모든 레이어보다 이깁니다.** 레이어를 쓰지 않은 기존 CSS가 갑자기 지는 일이 없게 하려는 설계입니다.
- **`!important`가 붙으면 순서가 뒤집힙니다.** 1단계와 같은 원리로, 앞에 선언한 층의 `!important`가 뒤 층의 `!important`를 이기고, 레이어 안의 `!important`가 레이어 밖의 `!important`를 이깁니다.

디자인 시스템에서 `@layer reset, base, components, utilities`처럼 층을 정해 두면, 선택자를 길게 쓰는 명시도 경쟁 없이 "유틸리티가 컴포넌트를 덮는다" 같은 규칙을 확실하게 만들 수 있습니다.

## 5단계. 명시도

여기까지 승부가 안 나면 드디어 명시도를 비교합니다. 명시도는 선택자를 **세 칸짜리 점수 (A, B, C)** 로 바꾼 것입니다.

| 칸 | 세는 것 |
| --- | --- |
| A | id 선택자 (`#app`) |
| B | 클래스(`.title`), 속성 선택자(`[type="text"]`), 가상 클래스(`:hover`) |
| C | 태그(`p`), 가상 요소(`::before`) |

`*`와 결합자(`>`, `+`, `~`, 공백)는 점수가 없습니다.

| 선택자 | 명시도 |
| --- | --- |
| `p` | (0, 0, 1) |
| `.title` | (0, 1, 0) |
| `p.title:hover` | (0, 2, 1) |
| `#app .title` | (1, 1, 0) |
| `#app #header p` | (2, 0, 1) |

### 더하는 게 아니라 칸별로 비교한다

명시도는 합계가 아니라 **A칸부터 차례로 비교**합니다. A칸에서 승부가 나면 B, C는 보지 않습니다.

```css
.a.b.c.d.e.f.g.h.i.j.k { color: blue; }   /* (0, 11, 0) */
#app { color: red; }                       /* (1, 0, 0) */
```

클래스가 11개여도 id 하나를 못 이깁니다. 결과는 **빨간색**입니다. "id는 100점, 클래스는 10점"으로 더하면 틀린 답이 나옵니다.

### 함수형 가상 클래스

| 선택자 | 명시도 계산 |
| --- | --- |
| `:where(...)` | 괄호 안과 상관없이 **항상 0** |
| `:is(...)`, `:not(...)`, `:has(...)` | 괄호 안 선택자 중 **가장 높은 것** |

```css
:is(#app, .title) p { }    /* #app 기준 → (1, 0, 1) */
:where(#app, .title) p { } /* 0 + p → (0, 0, 1) */
```

`:where()`는 명시도가 0이라서, 쓰는 사람이 쉽게 덮어쓸 수 있어야 하는 라이브러리 기본 스타일에 좋습니다.

## 6단계. 선언 순서

명시도까지 같으면 **나중에 나온 선언이 이깁니다.** 같은 파일이면 아래쪽, 여러 파일이면 나중에 불러온 파일입니다. 그래서 CSS 파일을 불러오는 순서가 바뀌면 화면이 달라질 수 있고, 이런 불안정함을 없애려고 4단계의 레이어를 씁니다.

## 상속은 캐스케이드와 다르다

헷갈리기 쉬운 부분이 하나 더 있습니다. `color`, `font-size` 같은 속성은 부모의 값을 자식이 물려받습니다(상속). 그런데 **상속된 값은 캐스케이드 경쟁에 참가하지 않습니다.** 요소에 직접 걸린 규칙이 하나라도 있으면, 그 규칙의 명시도가 아무리 낮아도 상속된 값을 이깁니다.

```html
<div id="app">
  <p>무슨 색일까요?</p>
</div>
```

```css
#app { color: red; }   /* 부모에 걸린 규칙, 명시도 (1, 0, 0) */
p { color: blue; }     /* p에 직접 걸린 규칙, 명시도 (0, 0, 1) */
```

결과는 **파란색**입니다. `#app`의 빨간색은 `p`에게 상속으로만 전달되는데, `p`에는 직접 걸린 규칙(`p { color: blue }`)이 있기 때문입니다. 상속은 "직접 걸린 규칙이 하나도 없을 때 쓰는 기본값"에 가깝습니다.

이 원리를 이용하는 키워드도 있습니다.

| 키워드 | 뜻 |
| --- | --- |
| `inherit` | 부모 값을 물려받음 |
| `initial` | 명세의 초기값으로 |
| `unset` | 상속되는 속성이면 `inherit`, 아니면 `initial` |
| `revert` | 브라우저 기본 스타일로 되돌림 |
| `revert-layer` | 이전 레이어의 값으로 되돌림 |

## 실전에서 디버깅하는 순서

스타일이 생각대로 안 먹으면 Chrome 개발자 도구 Elements 패널의 **Styles 탭**을 봅니다. 줄이 그어진 선언이 진 규칙이고, 맨 위에 있는 게 이긴 규칙입니다. 이유를 찾을 때는 캐스케이드 순서대로 확인합니다.

1. 상대 쪽에 `!important`가 있나?
2. 인라인 `style` 속성이 있나?
3. 서로 다른 `@layer`에 있나?
4. 명시도가 다른가?
5. 불러오는 순서가 다른가?
6. 애초에 규칙이 이 요소에 걸려 있나, 아니면 상속된 값인가?

## 정리

> "CSS 우선순위는 캐스케이드라는 알고리즘으로 정해지고, 출처와 중요도, 인라인 스타일, 레이어, 명시도, 선언 순서 차례로 비교해서 앞에서 승부가 나면 뒤는 보지 않습니다. 명시도는 id, 클래스·속성·가상 클래스, 태그 순으로 칸별 비교하며 더하지 않습니다. !important는 출처 순서를 뒤집어 사용자 설정을 보호하는 장치이고, 상속된 값은 경쟁에 참가하지 않아서 요소에 직접 걸린 규칙이 하나라도 있으면 그 규칙이 이깁니다."
