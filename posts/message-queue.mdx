회원가입 API를 생각해 봅시다. 사용자를 저장하고, **환영 이메일을 보내고**, 응답을 돌려줍니다. 그런데 이메일 서버가 느려서 3초가 걸린다면? 사용자는 가입 버튼을 누르고 **3초를 멍하니** 기다립니다. 저장은 이미 끝났는데도요. 이 문제를 푸는 게 **메시지 큐**입니다.

## 동기 처리의 한계

한 요청 안에서 모든 걸 처리하면, **가장 느린 작업이 전체 응답 시간을 결정**합니다.

```js
app.post("/signup", async (req, res) => {
  const user = await db.createUser(req.body); // 빠름 (50ms)
  await sendWelcomeEmail(user);               // 느림 (3000ms) — 여기서 발목
  res.json({ ok: true });                     // 사용자는 3초 뒤에야 응답 받음
});
```

이메일 전송, 이미지 리사이징, PDF 생성, 외부 API 호출 — 이런 **느리고, 당장 응답에 필요 없는** 작업이 요청을 붙잡습니다. 게다가 이메일 서버가 죽으면 가입 자체가 실패하죠.

## 큐로 분리하기 — 생산자와 소비자

핵심 발상: **"할 일을 큐에 적어두고, 응답은 바로 준다. 실제 처리는 별도 워커가 나중에."**

- **생산자(Producer)**: API 서버. "이메일 보내기"를 **큐에 넣기만** 하고 즉시 응답.
- **큐(Queue)**: 할 일 목록(예: Redis, RabbitMQ, SQS).
- **소비자(Consumer/Worker)**: 큐에서 작업을 꺼내 실제로 처리하는 별도 프로세스.

```js
app.post("/signup", async (req, res) => {
  const user = await db.createUser(req.body);
  await queue.add("welcome-email", { userId: user.id }); // 큐에 적재만 (5ms)
  res.json({ ok: true });                                // 즉시 응답!
});

// 별도 워커 프로세스에서
worker.process("welcome-email", async (job) => {
  await sendWelcomeEmail(job.data.userId); // 백그라운드에서 처리
});
```

응답은 55ms로 끝나고, 이메일은 뒤에서 조용히 나갑니다.

## 무엇이 좋아지나

- **응답이 빨라진다**: 느린 일을 기다리지 않음.
- **부하 평탄화**: 갑자기 요청이 몰려도 큐에 쌓아두고 워커가 **자기 속도로** 처리.
- **재시도**: 이메일 전송이 실패하면 워커가 다시 시도. 요청은 이미 성공했으니 사용자는 영향 없음.
- **결합도 감소**: API 서버와 이메일 처리가 분리돼 각자 배포·확장 가능. ([계층 분리](/posts/backend-layered-architecture)의 발상이 프로세스 단위로 확장된 셈.)

## 멱등성 — 같은 작업이 두 번 와도 괜찮게

대부분의 큐는 **"적어도 한 번(at-least-once)"** 전달을 보장합니다. 뒤집으면 **같은 작업이 두 번 처리될 수 있다**는 뜻이죠(네트워크 문제로 재전송 등). 그래서 소비자는 **멱등(idempotent)** 해야 합니다.

같은 작업을 두 번 해도 결과가 같도록 — 예를 들어 "이미 보낸 이메일인지 확인하고 보낸다". [REST의 멱등성](/posts/rest-api-design)이 여기서도 그대로 중요합니다.

## pub/sub — 하나의 사건, 여러 청취자

큐가 "일을 하나의 워커가 처리"라면, **pub/sub**은 "하나의 사건을 여러 구독자에게 방송"입니다. "주문 완료"라는 이벤트 하나에 **재고 차감·영수증 발송·통계 집계**가 각각 반응하죠. 서비스들을 이벤트로 느슨하게 잇는 방식입니다.

메시지 큐의 본질은 "**지금 당장 필요 없는 일은 요청에서 떼어내 나중에**"입니다. 응답은 빨라지고, 실패에 강해지고, 부하에 유연해집니다. Node라면 [이벤트 루프를 막는](/posts/nodejs-event-loop) 무거운 작업을 워커로 빼는 통로이기도 하죠. 다음 글에서는 그 서버를 여러 대로 늘리는 [확장성과 무상태 서버](/posts/scalability-stateless)를 봅니다.
