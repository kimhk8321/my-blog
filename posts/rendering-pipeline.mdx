[브라우저 렌더링 과정](/posts/js-deep-dive-browser-rendering)에서 HTML이 화면이 되는 큰 흐름을 봤습니다. 이번엔 그 다음 질문입니다 — **화면이 이미 그려진 뒤, 무언가를 바꾸면 무슨 일이 벌어지는가?**

애니메이션이 버벅이거나 스크롤이 끊기는 문제는 대부분 여기서 갈립니다. 같은 "움직임"이라도 어떤 속성을 건드리느냐에 따라 비용이 수십 배 차이 나거든요.

## 화면을 갱신하는 네 단계

무언가 바뀌면 브라우저는 필요한 만큼만 다시 합니다.

1. **스타일 계산(Style)** — 어떤 규칙이 어떤 요소에 적용되는지 계산
2. **레이아웃(Layout)** — 각 요소의 **크기와 위치**를 계산. 리플로우라고도 부름
3. **페인트(Paint)** — 색·그림자·텍스트 등 **픽셀을 칠함**
4. **합성(Composite)** — 칠해진 레이어들을 **순서대로 겹쳐** 최종 화면을 만듦

핵심은 **어디서 시작하느냐**입니다. 레이아웃부터 다시 하면 그 아래 페인트·합성도 전부 다시 해야 하죠. 합성만 다시 하면 훨씬 쌉니다.

## 속성마다 비용이 다르다

| 바꾸는 속성 | 다시 하는 단계 | 비용 |
| --- | --- | --- |
| `width`, `height`, `top`, `margin`, `font-size` | 레이아웃 → 페인트 → 합성 | 비쌈 |
| `color`, `background-color`, `box-shadow` | 페인트 → 합성 | 중간 |
| `transform`, `opacity` | **합성만** | 쌈 |

**"애니메이션은 `transform`과 `opacity`로"** 라는 조언이 여기서 나옵니다. 마법이 아니라, 그 둘만이 레이아웃과 페인트를 건너뛰고 합성 단계에서 처리되기 때문이에요.

```css
/* 나쁨: 매 프레임 레이아웃을 다시 계산 */
.box { transition: left 0.3s; }

/* 좋음: 합성만 — GPU가 레이어를 옮길 뿐 */
.box { transition: transform 0.3s; }
```

같은 "오른쪽으로 100px 이동"인데 전자는 매 프레임 레이아웃이 돌고, 후자는 이미 그려둔 레이어의 위치만 바뀝니다.

## 레이아웃 스래싱 — 읽기와 쓰기를 번갈아 하면

가장 흔한 성능 사고입니다. 자바스크립트에서 **레이아웃 값을 읽는 코드**와 **스타일을 바꾸는 코드**를 번갈아 쓰면, 브라우저가 그때마다 레이아웃을 **강제로 즉시** 다시 계산합니다.

```js
// 나쁨: 읽기 → 쓰기 → 읽기 → 쓰기…
for (const el of boxes) {
  const w = el.offsetWidth;      // 읽기: 최신 레이아웃이 필요 → 강제 계산
  el.style.width = w * 2 + "px"; // 쓰기: 레이아웃 무효화
}
```

브라우저는 원래 스타일 변경을 **모아뒀다가 한 번에** 처리합니다. 그런데 `offsetWidth` 같은 값을 읽으려면 "지금 당장 정확한 값"이 필요하니, 밀린 변경을 즉시 반영해야 하죠. 이게 100번 반복되면 레이아웃도 100번 돕니다.

해법은 **읽기를 먼저 다 하고, 쓰기를 나중에 몰아서** 하는 것입니다.

```js
// 좋음: 읽기 일괄 → 쓰기 일괄 (레이아웃 1회)
const widths = boxes.map((el) => el.offsetWidth);
boxes.forEach((el, i) => {
  el.style.width = widths[i] * 2 + "px";
});
```

강제 계산을 유발하는 대표적인 것들: `offsetTop/Left/Width/Height`, `clientWidth/Height`, `scrollTop/Height`, `getBoundingClientRect()`, `getComputedStyle()`.

> [리렌더 최적화](/posts/rerender-optimization)가 "React가 컴포넌트를 다시 그리는 횟수"의 문제라면, 이건 그 아래 **브라우저가 픽셀을 다시 계산하는 횟수**의 문제입니다. 층이 다르니 둘 다 봐야 해요.

## will-change — 아껴 써야 하는 힌트

`will-change`는 "이 요소가 곧 변할 테니 미리 준비해 둬"라는 신호입니다. 브라우저는 보통 그 요소를 **별도 레이어로 승격**시켜 둡니다.

```css
.modal { will-change: transform; }
```

효과는 있지만 **레이어마다 메모리를 씁니다.** 수십 개에 걸어두면 오히려 느려지고, 모바일에선 메모리 부족으로 이어질 수 있어요. 원칙은 이렇습니다.

- **정말 애니메이션되는 요소에만**
- **애니메이션 직전에 켜고, 끝나면 끈다**
- 상시로 CSS에 박아두지 않는다

## contain과 content-visibility — 영향 범위를 가두기

큰 목록이 있으면 항목 하나가 바뀌어도 브라우저가 넓은 범위를 다시 계산할 수 있습니다. `contain`은 "이 요소 안의 변화는 밖에 영향을 주지 않는다"고 약속해서 범위를 좁힙니다.

```css
.card { contain: layout paint; }
```

`content-visibility: auto`는 한 걸음 더 나갑니다 — **화면 밖 요소의 렌더링을 아예 건너뜁니다.**

```css
.section {
  content-visibility: auto;
  contain-intrinsic-size: 0 500px; /* 건너뛴 동안 쓸 예상 크기 */
}
```

긴 문서에서 효과가 큽니다. 다만 `contain-intrinsic-size`를 안 주면 스크롤바가 널뛰니 꼭 함께 쓰세요. [리스트 가상화](/posts/virtual-list-windowing)가 자바스크립트로 하던 일을, 브라우저가 CSS로 해주는 셈입니다.

## 측정하기

추측 대신 확인합니다. DevTools의 **Performance** 패널에서 기록하면 프레임별로 어떤 단계가 얼마나 걸렸는지 색으로 보입니다(보라 = 레이아웃, 초록 = 페인트). 긴 보라 막대가 반복되면 레이아웃 스래싱을 의심하면 됩니다.
