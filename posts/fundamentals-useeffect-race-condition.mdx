12편에서 의존성을 제대로 넣는 방법을 정리했습니다. 그런데 의존성을 완벽하게 넣어도 생기는 버그가 있습니다.

```jsx
function SearchResults({ query }) {
  const [results, setResults] = useState([]);

  useEffect(() => {
    fetch(`/api/search?q=${encodeURIComponent(query)}`)
      .then((res) => res.json())
      .then(setResults);
  }, [query]);

  return <ResultList items={results} />;
}
```

검색창에 "r", "re", "rea", "react"를 빠르게 치면, 마지막에 화면에 남는 결과가 "react"가 아니라 **"re"의 결과**일 때가 있습니다. 검색창에는 "react"가 적혀 있는데 목록은 엉뚱합니다. 의존성도 맞고 린트 경고도 없는데 왜 그럴까요?

## 응답은 보낸 순서대로 오지 않는다

네 글자를 치는 동안 Effect는 네 번 실행되고, 요청도 네 번 나갑니다. 문제는 **응답이 도착하는 순서는 보장되지 않는다**는 점입니다. "re"는 결과가 많아서 서버가 오래 걸렸고, "react"는 금방 끝났다고 해 봅시다.

```text
요청 순서:  r → re → rea → react
응답 순서:  r → rea → react → re   ← "re"가 가장 늦게 도착
화면:       ... react 결과 → re 결과로 덮어씀
```

각 응답은 도착하는 대로 `setResults`를 부르니, **가장 늦게 도착한 응답이 이깁니다.** 이렇게 여러 작업의 결과가 끝나는 순서에 따라 달라지는 상황을 **경쟁 상태(race condition)** 라고 합니다.

직접 재현해 봅시다. 먼저 보낸 요청이 늦게 도착하도록 지연 시간을 줬습니다.

```js
function fakeFetch(query, delay) {
  return new Promise((resolve) => setTimeout(() => resolve(`${query} 결과`), delay));
}

let screen = "";

// 응답이 오는 대로 화면에 반영하는 Effect
function effect(query, delay) {
  fakeFetch(query, delay).then((data) => {
    screen = data;
  });
}

effect("re", 300);      // 먼저 보냈지만 늦게 도착
effect("react", 100);   // 나중에 보냈지만 먼저 도착

setTimeout(() => {
  console.log(screen); // re 결과
}, 400);
```

사용자가 마지막으로 원한 건 "react"인데 화면에는 "re 결과"가 남습니다.

## 왜 클로저가 이 문제를 못 막을까

7편에서 Effect와 이벤트 핸들러는 **자기를 만든 렌더의 값**을 클로저로 기억한다고 했습니다. "re" 렌더에서 만든 Effect의 `.then` 콜백은 여전히 살아 있고, 응답이 오면 아무 의심 없이 `setResults`를 부릅니다. 그 콜백 입장에서는 자기가 이미 **지난 렌더의 Effect**라는 걸 알 방법이 없습니다.

그래서 알려 줘야 합니다. 그 통로가 **cleanup 함수**입니다.

## 해결 1. cleanup에서 ignore 플래그 세우기

React는 의존성이 바뀌어 Effect를 다시 실행하기 **직전에, 이전 Effect의 cleanup을 먼저 실행**합니다. 이 순서를 이용합니다.

```jsx
useEffect(() => {
  let ignore = false;

  fetch(`/api/search?q=${encodeURIComponent(query)}`)
    .then((res) => res.json())
    .then((data) => {
      if (!ignore) setResults(data);   // 지난 Effect라면 무시
    });

  return () => {
    ignore = true;   // 다음 Effect가 실행되기 전에 불림
  };
}, [query]);
```

`ignore`는 Effect가 실행될 때마다 **새로 만들어지는 지역 변수**입니다. "re" Effect의 `ignore`와 "react" Effect의 `ignore`는 서로 다른 변수입니다. 사용자가 "rea"를 치는 순간 "re" Effect의 cleanup이 불려서 "re" 쪽 `ignore`만 `true`가 되고, 나중에 "re" 응답이 와도 무시됩니다.

같은 흐름을 재현하면 이렇습니다.

```js
function fakeFetch(query, delay) {
  return new Promise((resolve) => setTimeout(() => resolve(`${query} 결과`), delay));
}

let screen = "";
let prevCleanup = null;

function effect(query, delay) {
  if (prevCleanup) prevCleanup();   // React가 다음 Effect 전에 이전 cleanup을 실행
  let ignore = false;
  fakeFetch(query, delay).then((data) => {
    if (!ignore) screen = data;
  });
  prevCleanup = () => {
    ignore = true;
  };
}

effect("re", 300);
effect("react", 100);

setTimeout(() => {
  console.log(screen); // react 결과
}, 400);
```

이 방법은 컴포넌트가 화면에서 사라질 때도 동작합니다. 언마운트 때도 cleanup이 불리니, 사라진 컴포넌트의 state를 바꾸려는 일도 생기지 않습니다.

## 해결 2. AbortController로 요청 자체를 취소하기

`ignore`는 응답을 **무시**할 뿐, 요청은 끝까지 진행됩니다. 오래 걸리는 요청이나 큰 응답이라면 **요청 자체를 취소**하는 편이 낫습니다.

```jsx
useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/search?q=${encodeURIComponent(query)}`, { signal: controller.signal })
    .then((res) => res.json())
    .then(setResults)
    .catch((error) => {
      if (error.name === "AbortError") return;   // 우리가 취소한 것은 에러가 아님
      setError(error);
    });

  return () => controller.abort();
}, [query]);
```

`controller.abort()`를 부르면 브라우저가 진행 중인 요청을 끊고, `fetch`의 Promise는 `AbortError`로 거부됩니다. 개발자 도구 Network 탭에서 이전 요청들이 `(canceled)`로 표시되는 걸 볼 수 있습니다.

주의할 점이 두 가지 있습니다.

- **`AbortError`는 따로 걸러야 합니다.** 걸러 내지 않으면 사용자가 글자를 칠 때마다 에러 화면이 깜빡입니다.
- **서버는 이미 요청을 처리하고 있을 수 있습니다.** 취소는 브라우저가 응답을 기다리지 않겠다는 뜻이지, 서버 작업을 되돌리는 게 아닙니다. 그래서 이 방법은 조회(GET)에 씁니다. 결제처럼 상태를 바꾸는 요청을 중간에 끊는다고 그 작업이 취소되지 않습니다.

`await`을 쓰는 코드라면 `await` 다음 줄에서 `signal.aborted`를 확인하거나, 위처럼 `ignore` 플래그를 함께 씁니다.

## Strict Mode에서 요청이 두 번 나가는 이유

개발 모드의 Strict Mode에서는 Effect가 **마운트 → cleanup → 다시 마운트** 순서로 한 번 더 실행됩니다. 요청이 두 번 나가서 당황하기 쉬운데, 바로 이 cleanup을 제대로 썼는지 확인하려는 장치입니다. 위 두 방법을 쓰면 첫 번째 요청은 무시되거나 취소되어, 결과는 한 번만 반영됩니다. 프로덕션 빌드에서는 한 번만 실행됩니다.

## debounce는 해결책이 아니다

"요청이 너무 많이 나가니까 debounce를 걸면 되지 않나" 싶을 수 있습니다. debounce는 **요청 횟수를 줄여 줄 뿐**, 경쟁 상태를 없애지 않습니다. 사용자가 300ms 쉬었다가 다시 치면 요청 두 개가 겹칠 수 있고, 응답 순서는 여전히 보장되지 않습니다. debounce는 서버 부하를 줄이는 용도로 함께 쓰고, 순서 문제는 cleanup으로 막습니다.

## 애초에 Effect로 직접 불러오지 않기

여기까지 오면 Effect로 데이터를 불러오는 코드가 생각보다 손이 많이 간다는 걸 알 수 있습니다. 경쟁 상태, 취소, 로딩과 에러 상태, 캐시, 같은 요청 중복 제거까지 직접 챙겨야 합니다. 그래서 실무에서는 이 일을 대신해 주는 도구를 씁니다.

| 방법 | 경쟁 상태를 어떻게 처리하나 |
| --- | --- |
| TanStack Query, SWR | 쿼리 키(`["search", query]`)별로 결과를 저장하고, 화면은 **현재 키의 결과**만 보여 줌. 늦게 온 이전 응답은 그 키의 캐시에 들어갈 뿐 화면을 덮어쓰지 않음 |
| Server Components | 서버에서 데이터를 불러와 렌더한 결과를 보내므로 클라이언트 Effect가 없음 |
| Next.js의 검색 페이지 | 검색어를 URL(`?q=react`)에 두고 서버에서 렌더. 라우터가 마지막 이동만 반영함 |

직접 Effect로 불러와야 한다면, **요청을 보내는 Effect에는 항상 cleanup을 쓴다**는 규칙 하나만 기억하면 됩니다.

## 정리

> "useEffect로 데이터를 불러오면 의존성이 바뀔 때마다 요청이 새로 나가는데, 응답은 보낸 순서대로 도착하지 않기 때문에 늦게 온 이전 응답이 최신 결과를 덮어쓰는 경쟁 상태가 생깁니다. 이전 Effect의 콜백은 클로저로 자기 렌더의 값을 들고 살아 있어서 스스로 오래된 것인지 알 수 없습니다. React는 다음 Effect를 실행하기 전에 이전 Effect의 cleanup을 부르므로, cleanup에서 ignore 플래그를 세워 늦은 응답을 무시하거나 AbortController로 요청을 취소합니다. debounce는 요청 수를 줄일 뿐 순서 문제를 해결하지 않고, 실무에서는 TanStack Query나 Server Components처럼 이 문제를 대신 처리하는 방법을 많이 씁니다."
