테스트를 **나중에** 쓰면 대개 이렇게 됩니다. 기능을 다 만들고, 돌려보고, 잘 되니까 "이제 테스트를 붙이자" 하고 이미 짜인 코드에 맞춰 테스트를 씁니다. 그러면 테스트는 **코드가 지금 하는 일을 그대로 받아 적는** 것이 되죠.

TDD는 순서를 뒤집습니다. **먼저 실패하는 테스트를 쓰고, 그걸 통과시키는 코드를 씁니다.**

## 레드 · 그린 · 리팩터

한 사이클은 셋으로 이뤄집니다.

1. **레드** — 아직 없는 기능에 대한 테스트를 쓴다. 당연히 **실패한다**
2. **그린** — 통과할 만큼만 최소한으로 구현한다
3. **리팩터** — 초록불을 유지하며 코드를 정리한다

핵심은 **"통과할 만큼만"** 입니다. 처음부터 잘 쓰려 하지 않고, 일단 통과시킨 뒤 정리합니다.

## 실제로 해보면

방명록 입력 검증을 예로 들어 보죠.

```ts
// 1. 레드 — 아직 validate 함수가 없다
test("이름이 비면 거절한다", () => {
  expect(validate({ name: "", message: "안녕" })).toEqual({
    ok: false,
    error: "이름은 1~20자여야 합니다",
  });
});
```

실행하면 실패합니다. **이 실패를 꼭 확인해야 합니다** — 테스트가 애초에 잘못 짜여 항상 통과하는 경우를 여기서 걸러내거든요.

```ts
// 2. 그린 — 통과할 만큼만
export function validate({ name, message }) {
  if (name.length < 1) return { ok: false, error: "이름은 1~20자여야 합니다" };
  return { ok: true };
}
```

메시지 검증은 아직 없습니다. **다음 테스트를 쓸 때 추가**하면 되니까요.

```ts
// 다시 레드 — 다음 경우
test("이름이 20자를 넘으면 거절한다", () => { ... });
```

이렇게 **작은 걸음**으로 나아갑니다.

## 무엇이 달라지나

**1. 테스트가 요구사항이 된다**

테스트를 먼저 쓰려면 "이 함수가 무엇을 해야 하는지"를 먼저 정해야 합니다. 코드를 짜면서 요구사항을 즉흥적으로 만들어 가는 일이 줄어듭니다.

**2. 설계 피드백이 즉시 온다**

테스트를 쓰다가 **쓰기 어렵다**고 느끼면, 그건 대개 설계 신호입니다. 준비 코드가 열 줄씩 필요하거나 [대역을 잔뜩 넣어야](/posts/test-doubles) 한다면, 그 함수가 너무 많은 것에 얽혀 있다는 뜻이죠. 만들고 나서 알면 고치기 어렵지만, 만들기 전이면 방향을 바꾸기 쉽습니다.

**3. 과하게 만들지 않게 된다**

"나중에 필요할 것 같은데" 하며 미리 만드는 걸 막아줍니다. 테스트가 요구하지 않는 코드는 안 씁니다.

**4. 리팩터링이 두렵지 않다**

3단계에서 마음 놓고 정리할 수 있는 건 **초록불이라는 안전망** 때문입니다. [리팩터링](/posts/clean-code-refactoring)이 "동작을 바꾸지 않고 구조만 바꾸는 것"이라면, 그 "동작을 바꾸지 않았음"을 증명해 주는 게 테스트죠.

## 언제 잘 맞고, 언제 부담인가

솔직하게 말하면 TDD가 항상 좋은 건 아닙니다.

**잘 맞는 곳**
- **규칙이 분명한 로직** — 검증, 계산, 파싱, 상태 전이
- **버그 수정** — 버그를 재현하는 테스트를 먼저 쓰면, 고쳤다는 증거와 재발 방지가 동시에 생깁니다
- 입출력이 뚜렷한 함수

**부담스러운 곳**
- **어떻게 만들지 모를 때** — 탐색하며 방향을 찾는 단계에선 테스트가 족쇄가 됩니다
- **화면 레이아웃·시각 디자인** — 눈으로 봐야 아는 것을 테스트로 먼저 쓰긴 어렵습니다
- 요구사항이 계속 뒤집히는 초기 프로토타입

그래서 현실적인 절충은 이렇습니다 — **탐색은 자유롭게 하되, 규칙이 정해진 순간부터는 테스트를 먼저.** 그리고 **버그는 무조건 테스트부터**.

## 커버리지 숫자에 속지 않기

TDD를 하면 커버리지가 자연히 올라가지만, **커버리지가 목표가 되면 이상해집니다.**

```ts
// 커버리지는 올라가지만 아무것도 검증하지 않는 테스트
test("렌더된다", () => {
  render(<Page />);
});
```

줄이 실행됐다고 **옳게 동작한다는 뜻은 아닙니다.** 90%를 채우는 것보다, "이게 깨지면 사용자가 아픈" 경로가 덮여 있는지가 중요합니다.

---

TDD의 값어치는 "테스트가 많아진다"보다 **"만들기 전에 생각하게 된다"** 에 있습니다. 무엇을 해야 하는지 먼저 적고, 최소한으로 만들고, 안심하고 다듬는 것 — 도구라기보다 작업 리듬에 가깝습니다. 전부에 적용할 필요는 없고, **규칙이 분명한 곳과 버그 수정**부터 시작해 보면 효과를 바로 느낄 수 있습니다.
