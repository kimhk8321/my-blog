DB 조회가 100ms, 외부 API가 300ms 걸린다면, 같은 요청이 반복될 때마다 그 비용을 다시 치르는 건 낭비입니다. **캐시**는 "한 번 계산한 결과를 빠른 곳(주로 [메모리, Redis](/posts/data-store-selection))에 저장해 재사용"하는 것입니다. [HTTP 캐싱](/posts/http-caching)이 브라우저~서버 사이라면, 여기선 **서버~DB 사이**의 캐시예요.

## 캐시 어사이드 (Cache-Aside) — 가장 흔한 패턴

애플리케이션이 캐시를 직접 관리합니다. **읽을 때 캐시 먼저, 없으면 DB에서 채운다.**

```js
async function getUser(id) {
  const cached = await redis.get(`user:${id}`);
  if (cached) return cached;                 // 캐시 히트

  const user = await db.findUser(id);        // 캐시 미스 → DB
  await redis.set(`user:${id}`, user, { ex: 3600 }); // 채워 넣기 (1시간)
  return user;
}
```

- **히트**면 DB를 안 감(빠름), **미스**면 DB에서 읽고 캐시에 채움.
- 캐시에 없는 데이터는 자연히 안 들어감(lazy) → 실제 쓰이는 것만 캐시됨.

## 쓰기 전략 — write-through / write-back

데이터가 **바뀔 때** 캐시를 어떻게 할지도 정해야 합니다.

- **Write-through**: 쓸 때 DB와 캐시를 **함께** 갱신. 캐시가 항상 최신이지만 쓰기가 조금 느림.
- **Write-back**: 캐시에만 먼저 쓰고 DB엔 나중에 몰아서. 빠르지만 유실 위험.
- **가장 단순·안전**: 쓸 때 **캐시를 지우기만**(invalidate) 하고, 다음 읽기에서 다시 채우게. (캐시 어사이드와 궁합 좋음)

## TTL과 무효화 — "캐시 무효화는 어렵다"

> "컴퓨터 과학에서 어려운 것 두 가지: 캐시 무효화와 이름 짓기." — 유명한 농담이자 진실.

캐시된 데이터가 **낡으면(stale)** 잘못된 값을 보여줍니다. 두 가지로 다룹니다.

- **TTL(만료)**: `ex: 3600`처럼 시간이 지나면 자동 삭제. 간단하지만 그 사이 낡은 값이 보일 수 있음.
- **명시적 무효화**: 데이터가 바뀌면 관련 캐시 키를 **즉시 삭제**. 정확하지만 "어떤 키들을 지워야 하나"를 관리해야 함. ([Next.js의 `revalidateTag`](/posts/nextjs-caching)가 이 태그 기반 무효화죠.)

무엇을 캐시할지의 기준: **자주 읽고, 드물게 바뀌고, 조금 낡아도 괜찮은** 데이터. 실시간 잔고 같은 건 캐시하면 안 됩니다.

## 캐시 스탬피드 — 동시에 몰리는 미스

인기 캐시가 만료되는 순간, **수많은 요청이 동시에 미스**나서 전부 DB로 몰립니다(thundering herd). DB가 순간적으로 폭격당하죠. 대책:

- **잠금(lock)**: 첫 요청만 DB를 채우게 하고 나머지는 대기.
- **만료 시간 분산(jitter)**: TTL에 랜덤을 더해 동시 만료를 흩뜨림.
- **stale-while-revalidate**: 낡은 값을 일단 주면서 뒤에서 갱신. ([Next.js 캐싱](/posts/nextjs-caching)의 그 개념.)

## 어디에 캐시하나

- **로컬 메모리**: 가장 빠르지만 서버마다 따로라 [여러 대면 불일치](/posts/scalability-stateless).
- **공유 캐시(Redis)**: 모든 서버가 같은 캐시를 봄. 확장에 유리. (이 블로그 조회수·방명록도 여기.)
