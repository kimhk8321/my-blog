글이 135편이 되면서 두 가지가 아쉬웠습니다. 하나는 **글이 길어졌는데 안에서 이동할 방법이 없다**는 것, 다른 하나는 **[조회수를 쌓기만 하고 모아보지 않는다](/posts/blog-view-counter)**는 것이었어요. 오늘은 그 둘을 붙였습니다.

## 1부. 목차 — 문제는 id였다

목차 자체는 간단합니다. 본문에서 `##`, `###`을 뽑아 목록으로 만들고 `#앵커`로 링크하면 되죠. 진짜 문제는 다른 데 있었습니다.

**앵커가 동작하려면 목차의 링크와 실제 헤딩의 `id`가 정확히 같아야 합니다.**

이 블로그는 MDX를 렌더링할 때 `rehype-slug`가 헤딩에 id를 자동으로 붙입니다. 그런데 목차는 **렌더링 전의 원문에서** 뽑으니, 제가 만든 id와 렌더러가 만든 id가 어긋나면 링크가 죽습니다.

### 어긋나기 쉬운 지점들

직접 슬러그를 만들어 보면 함정이 많습니다.

- **마크다운 기호** — `## **굵은** 제목`의 id는 `굵은-제목`일까 `**굵은**-제목`일까? 렌더러는 **그려진 글자**를 기준으로 하니 기호를 지운 쪽입니다.
- **중복 제목** — 한 글에 "정리"가 두 번 나오면 두 번째는 `정리-1`이 됩니다. **몇 번째인지 세고 있어야** 맞출 수 있죠.
- **한글·특수문자** — 공백은 `-`로, `:has()` 같은 건 어떻게 처리되나?

규칙을 추측해서 다시 구현하면 언젠가 어긋납니다. 그래서 **추측하지 않기로** 했습니다.

### 같은 라이브러리를 같은 순서로

`rehype-slug`가 내부에서 무엇을 쓰는지 확인했더니 `github-slugger`였습니다. 그렇다면 답은 간단합니다 — **그걸 그대로 쓰면 됩니다.**

```ts
const slugger = new GithubSlugger();
for (const line of lines) {
  const text = /* 마크다운 기호를 지운 제목 */;
  const id = slugger.slug(text);   // 렌더러와 같은 규칙, 같은 상태
  if (level === 2 || level === 3) items.push({ id, text, level });
}
```

여기서 놓치기 쉬운 게 하나 있습니다. **목차에 넣지 않을 단계(h4 등)도 슬러그는 만들어야 합니다.** `github-slugger`는 중복 번호를 붙이려고 **지금까지 본 제목을 기억**하기 때문에, 건너뛰면 번호가 어긋나거든요. 그래서 모든 헤딩을 순서대로 통과시키되, 목차에는 h2·h3만 담았습니다.

그리고 코드 블록 안의 `# 주석`이 헤딩으로 잡히는 문제가 있어, 펜스 블록을 먼저 걷어냈습니다.

### 추측 대신 대조

맞다고 믿기보다 **확인**했습니다. 임시 라우트를 만들어 "내가 뽑은 id 목록"과 "실제 렌더된 HTML의 heading id 목록"을 135편 전부 비교했어요.

```
일치: 135 / 135
```

이렇게 재고 나니 마음이 놓였습니다. 이런 종류의 버그는 **몇 달 뒤 특정 글에서만 조용히 터지거든요.**

### 현재 위치 표시

읽는 중인 섹션을 목차에서 강조하려면 스크롤을 따라가야 합니다. 여기서 [렌더링 파이프라인 글](/posts/rendering-pipeline)에 쓴 내용을 그대로 적용했습니다.

```js
// 나쁨: 스크롤마다 위치를 재면 그때마다 레이아웃을 다시 계산한다
window.addEventListener("scroll", () => headings.map(h => h.offsetTop));
```

대신 **IntersectionObserver**를 씁니다. 브라우저가 "이 요소가 화면의 이 범위에 들어왔다"고 알려주므로 내가 직접 잴 일이 없죠. 화면 위쪽에 띠를 하나 정해두고, 그 띠에 들어온 헤딩을 현재 섹션으로 삼습니다.

긴 문단을 읽는 중에는 띠에 아무 헤딩도 없는데, 그럴 땐 **직전 값을 유지**합니다. "아무것도 선택 안 됨"보다 자연스러우니까요.

## 2부. 인기 글 — 정렬을 저장소에 맡기기

조회수는 글마다 `views:슬러그` 카운터로 쌓고 있었습니다. 여기서 "많이 읽은 글 5편"을 뽑으려면?

**순진한 방법**: 135개 키를 전부 읽어서 정렬한다. 요청마다 135번 조회에 매번 전체 정렬 — 글이 늘수록 나빠집니다. [N+1 문제](/posts/query-performance)와 같은 냄새죠.

**Redis의 답**: **Sorted Set**을 쓰면 됩니다. 점수를 가진 집합인데, **항상 정렬된 상태로 유지**됩니다.

```ts
// 조회할 때: 카운터와 랭킹을 함께 올린다
await Promise.all([
  redis.incr(`views:${slug}`),
  redis.zincrby("views:rank", 1, slug),
]);

// 읽을 때: 상위 5개를 바로 꺼낸다
redis.zrange("views:rank", 0, 4, { rev: true, withScores: true });
```

핵심은 **읽을 때 정렬하지 않고, 쓸 때 정렬해 둔다**는 것입니다. [인덱스](/posts/query-performance)와 정확히 같은 발상이에요 — 조회가 잦고 쓰기가 드무니, 비용을 쓰기 쪽으로 옮긴 거죠. [방명록에서 List를 골랐던 것](/posts/guestbook-backend)처럼, **자료구조를 잘 고르면 로직이 사라집니다.**

### 지난 데이터를 버리지 않기

문제가 하나 있었습니다. 랭킹은 오늘 도입했으니 **Sorted Set은 비어 있는데**, 카운터에는 그동안 쌓인 조회수가 있습니다. 새로 세기 시작하면 그 데이터가 버려지죠.

그래서 **한 번만 채워 넣는 시딩**을 넣었습니다.

```ts
let ranking = await readRanking();
if (ranking.length === 0) ranking = await seedRanking(); // 기존 카운터로 채움
```

`MGET`으로 135개 카운터를 **한 번에** 읽고, 0이 아닌 것만 `ZADD`로 넣습니다. 이후로는 `ZINCRBY`가 알아서 갱신하니 시딩은 다시 돌지 않습니다. 덕분에 배포하자마자 그동안의 기록이 그대로 반영됐어요.

### 실제 데이터로 확인, 단 오염 없이

여기서 조심할 게 있었습니다. 검증하겠다고 조회 API를 두드리면 **실제 조회수가 부풀어 오릅니다.** 통계가 오염되는 거죠.

그래서 나눠서 확인했습니다.

- **읽기·시딩**은 진짜 저장소로 — 이건 기능이 어차피 해야 할 정상 동작
- **증가(`ZINCRBY`)** 는 `test:` 임시 키에서만 확인하고 **삭제**

```
zrange(rev, withScores): ["post-a", 2, "post-b", 1]
임시 키 삭제: 완료
```

"검증한다고 데이터를 망치지 않기" — 운영 중인 걸 만질 땐 이 구분이 필요하더군요.

## 배운 것

- **렌더러가 만드는 값은 재현하지 말고 같은 도구를 쓰자** — 규칙을 추측해 다시 구현하면 언젠가 어긋난다.
- **"맞을 것 같다"로 넘어가지 말고 대조하자** — 135편 전수 비교가 아니었다면 몰랐을 어긋남이 있었을 수 있다.
- **정렬은 저장소에 맡길 수 있다** — 읽을 때 정렬하는 대신 쓸 때 정렬해 두면 조회가 공짜에 가까워진다.
- **기능을 새로 붙일 땐 기존 데이터를 어떻게 살릴지도 설계다** — 시딩 한 번으로 그동안의 기록이 이어졌다.
- **검증이 운영 데이터를 오염시키지 않게** — 읽기와 쓰기를 나눠 접근했다.
