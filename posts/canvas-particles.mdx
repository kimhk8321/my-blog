점 60개가 떠다니고, 가까운 것끼리 선으로 이어지고, 마우스가 다가가면 흩어진다. 이걸 DOM 요소 60개로 만들면? 매 프레임 60개의 `style`을 갱신하며 레이아웃·페인트가 폭발합니다. 이런 **다수의 시각 요소를 매 프레임 다시 그리는** 일에는 **Canvas**가 답입니다.

DOM은 "요소를 만들어 두면 브라우저가 알아서 그려주는" **유지 모드(retained mode)** 입니다. Canvas는 "매 프레임 내가 직접 다 그리는" **즉시 모드(immediate mode)** 죠. 사고방식이 다릅니다.

## 캔버스 기본 — 컨텍스트에 명령하기

Canvas는 그 자체론 빈 도화지이고, **2D 컨텍스트**에 그리기 명령을 내립니다.

```js
const canvas = ref.current;
const ctx = canvas.getContext("2d");

ctx.clearRect(0, 0, W, H);        // 매 프레임 지우고
ctx.fillStyle = "rgb(99,102,241)";
ctx.beginPath();
ctx.arc(x, y, 2.5, 0, Math.PI * 2); // 원 그리고
ctx.fill();                        // 채운다
```

즉시 모드의 철칙: **매 프레임 `clearRect`로 지우고 처음부터 다시 그린다.** 이전 프레임의 흔적은 남지 않습니다.

## 선명하게 — devicePixelRatio

캔버스를 그냥 만들면 고해상도(레티나) 화면에서 흐릿합니다. CSS 크기와 실제 픽셀 수가 다르기 때문이죠. `devicePixelRatio`로 실제 픽셀을 맞춰야 선명합니다.

```js
const dpr = window.devicePixelRatio || 1;
const rect = canvas.getBoundingClientRect();
canvas.width = rect.width * dpr;    // 실제 픽셀 버퍼는 크게
canvas.height = rect.height * dpr;
ctx.setTransform(dpr, 0, 0, dpr, 0, 0); // 좌표는 CSS 픽셀로 쓰도록 스케일
```

이 처리를 빼먹으면 "왜 내 캔버스만 흐릿하지?"의 90%가 설명됩니다.

## 파티클 = 그냥 객체 배열

파티클은 대단한 게 아니라 **위치·속도를 가진 객체**입니다.

```js
const parts = Array.from({ length: 55 }, () => ({
  x: Math.random() * W, y: Math.random() * H,
  vx: (Math.random() - 0.5) * 0.6, vy: (Math.random() - 0.5) * 0.6,
}));
```

매 프레임 각 파티클의 위치를 속도만큼 옮기고, 벽에 닿으면 튕깁니다. [스프링 애니메이션 글](/posts/spring-animation)에서 본 rAF 루프가 여기서도 심장입니다.

```js
for (const p of parts) {
  // 마우스에서 밀어내기
  const dx = p.x - mouse.x, dy = p.y - mouse.y;
  const dist = Math.hypot(dx, dy);
  if (dist < 90) { p.vx += (dx / dist) * 0.4; p.vy += (dy / dist) * 0.4; }

  p.vx *= 0.98; p.vy *= 0.98;   // 마찰
  p.x += p.vx; p.y += p.vy;
  if (p.x < 0 || p.x > W) p.vx *= -1; // 벽 반사
}
```

## 연결선 — O(n²)의 함정

"가까운 점끼리 잇기"는 모든 쌍을 검사합니다. 55개면 약 1,500쌍, 괜찮습니다. 하지만 **500개면 12만 쌍** — 매 프레임 이걸 돌면 버벅입니다.

```js
for (let i = 0; i < N; i++)
  for (let j = i + 1; j < N; j++) {
    const d = Math.hypot(parts[i].x - parts[j].x, parts[i].y - parts[j].y);
    if (d < 75) { /* 투명도를 거리에 반비례해 선 그리기 */ }
  }
```

파티클이 많아지면 **공간 분할(그리드/쿼드트리)** 로 근처 것만 검사하거나, 아예 계산을 [Web Worker](/posts/web-workers)나 WebGL로 넘깁니다. 데모 규모에선 O(n²)로 충분하지만, 한계를 아는 게 중요하죠.

## 정리 잊지 말기

rAF 루프와 이벤트 리스너는 반드시 정리합니다. React라면 `useEffect`의 정리 함수에서요.

```jsx
return () => {
  cancelAnimationFrame(raf);
  canvas.removeEventListener("pointermove", onMove);
  window.removeEventListener("resize", resize);
};
```

Canvas의 사고방식은 "**상태를 유지하지 않고 매 프레임 전부 다시 그린다**"입니다. DOM으로는 버거운 수백·수천 개의 시각 요소도, 캔버스에선 그냥 배열 순회 + 그리기 명령일 뿐이죠. 다음 글에서는 방향을 틀어, 자기 자신을 호출하는 [재귀 컴포넌트로 트리 뷰](/posts/tree-view)를 만듭니다.
