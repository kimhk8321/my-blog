[트랜잭션과 격리 수준](/posts/transactions-isolation)을 개념으로 정리했었죠. InnoDB가 그걸 어떻게 구현하는지 보면, 개념만 알고 있을 땐 짐작하기 어려운 것들이 나옵니다. 특히 **"인덱스를 잠근다"** 는 사실이 그렇습니다.

## MVCC — 읽기는 기다리지 않는다

가장 먼저 알아야 할 건 **읽기와 쓰기가 서로를 막지 않는다**는 점입니다.

누군가 어떤 행을 수정 중일 때, 다른 트랜잭션이 그 행을 읽으려 하면 어떻게 될까요? 잠겨서 기다릴 것 같지만, InnoDB는 **[언두 로그](/posts/real-mysql-architecture)에 있는 변경 전 값**을 대신 보여줍니다.

이게 **MVCC(다중 버전 동시성 제어)** 입니다. 한 행에 여러 버전이 존재하고, 각 트랜잭션은 **자기 시점에 맞는 버전**을 봅니다.

- **읽기는 잠금이 필요 없다** → 조회가 쓰기 때문에 멈추지 않음
- 대신 **언두 로그가 쌓입니다.** 오래 열려 있는 트랜잭션이 있으면 옛 버전을 계속 보관해야 해서 언두 공간이 부풀죠

> "트랜잭션을 짧게 유지하라"는 조언의 이유가 이것입니다. 잠금 때문만이 아니라 **옛 버전을 계속 붙잡고 있게 되기 때문**이에요.

## 잠금은 행이 아니라 인덱스에 걸린다

여기가 InnoDB의 가장 중요한 특징입니다.

```sql
UPDATE users SET name = 'x' WHERE age = 30;
```

`age`에 인덱스가 **없다면** 어떻게 될까요? InnoDB는 조건에 맞는 행을 찾으려고 전체를 훑고, 그 과정에서 **훑은 행을 전부 잠급니다.** 결과적으로 한 건만 바꾸려 했는데 **테이블 전체가 잠기는 것과 비슷해집니다.**

인덱스가 있으면 해당 인덱스 레코드만 잠그면 되죠.

**"인덱스가 없으면 성능만 나빠지는 게 아니라 동시성까지 망가진다"** — 이건 개념 수준에서는 잘 안 보이던 부분이었습니다.

## 레코드 락 · 갭 락 · 넥스트 키 락

InnoDB의 잠금은 세 가지로 나뉩니다.

- **레코드 락** — 인덱스 레코드 자체를 잠금
- **갭 락** — 레코드와 레코드 **사이의 빈 공간**을 잠금. 그 구간에 **새 행이 끼어드는 것**을 막음
- **넥스트 키 락** — 레코드 락 + 그 앞의 갭 락. InnoDB의 기본 방식

갭 락이 왜 필요할까요? [팬텀 리드](/posts/transactions-isolation)를 막기 위해서입니다. 같은 조건으로 두 번 조회했을 때 **없던 행이 생기는** 현상이죠. 사이 공간을 잠가두면 새 행을 넣을 수 없으니 팬텀이 안 생깁니다.

대신 부작용이 있습니다 — **아직 존재하지 않는 범위까지 잠급니다.** 그래서 예상보다 넓게 잠기고, 서로 다른 행을 다루는 트랜잭션끼리도 [데드락](/posts/transactions-isolation)이 날 수 있습니다.

## 격리 수준이 실제로 바꾸는 것

MySQL의 기본은 **REPEATABLE READ**입니다(PostgreSQL은 READ COMMITTED).

- **READ COMMITTED** — 매 쿼리마다 최신 스냅샷을 봅니다. 같은 트랜잭션 안에서도 두 번 읽으면 값이 다를 수 있죠. 갭 락을 거의 안 써서 **잠금 범위가 좁습니다.**
- **REPEATABLE READ** — 트랜잭션 **시작 시점의 스냅샷**을 끝까지 봅니다. 같은 쿼리는 항상 같은 결과. 대신 갭 락 때문에 **잠금이 넓습니다.**

재밌는 건 **읽기와 쓰기가 다른 것을 본다**는 점입니다. REPEATABLE READ에서 일반 `SELECT`는 스냅샷(옛 버전)을 보지만, `UPDATE`나 `SELECT ... FOR UPDATE`는 **최신 값**을 봅니다(잠금 읽기). 그래서 이런 일이 벌어지죠.

```sql
SELECT COUNT(*) FROM t WHERE a = 1;  -- 10건 (스냅샷)
UPDATE t SET b = 2 WHERE a = 1;      -- 12건이 바뀜 (최신)
```

## 낙관적 잠금은 DB 기능이 아니다

[앞서 정리했던](/posts/transactions-isolation) 비관적/낙관적 잠금 중, **낙관적 잠금은 DB가 제공하는 게 아니라 애플리케이션이 만드는 규칙**입니다.

```sql
UPDATE posts SET content = ?, version = version + 1
WHERE id = ? AND version = ?;   -- 영향받은 행이 0이면 그새 누가 바꿈
```

InnoDB가 제공하는 건 `SELECT ... FOR UPDATE` 같은 **비관적** 잠금이고, 낙관적 방식은 버전 컬럼과 조건절로 **직접 구현**하는 것이죠. 이 구분이 헷갈렸는데 정리하고 나니 명확해졌습니다.
