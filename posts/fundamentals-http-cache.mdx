배포를 마치고 "반영됐어요"라고 했는데, 기획자에게서 이런 답이 옵니다. "제 화면은 그대로인데요?" 새로고침을 해 보라고 하면 그제야 바뀝니다. 심하면 이런 일도 있습니다. 배포 직후 일부 사용자에게만 **빈 화면**이 뜨고, 콘솔에는 `ChunkLoadError`가 찍힙니다.

둘 다 브라우저 캐시가 원인입니다. 캐시를 끄면 해결될 것 같지만, 그러면 매번 모든 파일을 다시 받느라 사이트가 느려집니다. 답은 **파일마다 캐시 규칙을 다르게 주는 것**입니다. 그러려면 브라우저가 캐시를 언제 쓰고 언제 서버에 묻는지부터 알아야 합니다.

## 브라우저는 세 가지 중 하나를 한다

브라우저가 이미 받아 둔 파일을 다시 요청할 때는 셋 중 하나입니다.

| 상태 | 브라우저가 하는 일 | Network 탭 표시 |
| --- | --- | --- |
| **fresh** (아직 신선함) | 서버에 **묻지 않고** 캐시를 그대로 씀 | `(memory cache)`, `(disk cache)` |
| **stale** (유효 기간 지남) | 서버에 "내가 가진 거 아직 맞아?"라고 **확인**. 맞으면 서버가 본문 없이 `304`만 보냄 | `304 Not Modified` |
| 캐시 없음 | 처음부터 새로 받음 | `200` |

핵심은 첫 줄입니다. **fresh인 동안 브라우저는 서버에 아예 묻지 않습니다.** 서버에 새 버전을 올렸어도 브라우저는 그걸 알 방법이 없습니다. "배포했는데 그대로"의 정체가 이것입니다.

## Cache-Control: 얼마나 신선한지 정한다

서버는 응답 헤더 `Cache-Control`로 캐시 규칙을 알려 줍니다.

| 지시어 | 뜻 |
| --- | --- |
| `max-age=600` | 받은 뒤 600초 동안 fresh. 그동안은 서버에 묻지 않음 |
| `no-cache` | 저장은 하되 **쓸 때마다 서버에 확인**. 이름과 달리 "캐시하지 마"가 아님 |
| `no-store` | 아예 저장하지 않음. 개인정보가 담긴 응답에 씀 |
| `private` / `public` | 브라우저에만 저장 / CDN 같은 공유 캐시에도 저장 가능 |
| `s-maxage=600` | CDN 같은 공유 캐시용 `max-age`. 브라우저는 무시 |
| `immutable` | 이 파일은 절대 바뀌지 않으니 fresh인 동안 새로고침해도 확인하지 말 것 |
| `stale-while-revalidate=60` | 기간이 지나도 60초 동안은 일단 옛 것을 보여 주고 뒤에서 새로 확인 |

`no-cache`와 `no-store`는 가장 많이 헷갈리는 짝입니다. `no-cache`는 "매번 확인하고 써라"이고, `no-store`는 "저장하지 마라"입니다.

## ETag와 304: 다시 받지 않고 확인만 하기

stale이 된 파일을 매번 처음부터 받으면 낭비입니다. 그래서 서버는 파일의 버전 표시를 함께 보냅니다.

```text
1) 첫 요청의 응답
   200 OK
   ETag: "a1b2c3"
   Cache-Control: no-cache

2) 다음 요청 (브라우저가 자동으로 붙임)
   If-None-Match: "a1b2c3"

3) 바뀌지 않았으면
   304 Not Modified   ← 본문 없음. 브라우저는 저장해 둔 파일을 씀
```

`ETag`는 내용으로 만든 지문이고, `Last-Modified` / `If-Modified-Since`는 수정 시각으로 같은 일을 합니다. 304는 요청 한 번은 오가지만 본문이 없어서 가볍습니다.

브라우저의 판단을 단순하게 옮기면 이렇습니다.

```js
function whatBrowserDoes(entry, now) {
  if (entry.noStore) return "저장 안 함 → 새로 받음";
  const age = now - entry.storedAt;
  if (!entry.noCache && age < entry.maxAge) return "fresh → 서버에 묻지 않음";
  return entry.etag ? `stale → If-None-Match: ${entry.etag}로 확인` : "stale → 새로 받음";
}

const html = { storedAt: 0, maxAge: 0, noCache: true, etag: '"a1b2c3"' };
const appJs = { storedAt: 0, maxAge: 31536000 };

console.log(whatBrowserDoes(html, 10)); // stale → If-None-Match: "a1b2c3"로 확인
console.log(whatBrowserDoes(appJs, 86400)); // fresh → 서버에 묻지 않음
```

## Cache-Control이 없으면 브라우저가 알아서 정한다

여기서 흔한 함정이 있습니다. 서버가 `Cache-Control`을 **안 보내면** 캐시하지 않을 거라고 생각하기 쉽습니다. 실제로는 반대입니다. `Last-Modified`만 있으면 브라우저는 **스스로 유효 기간을 추정**합니다(휴리스틱 캐시). 흔히 "마지막 수정 후 지난 시간의 10%" 정도를 씁니다. 열흘 전에 수정된 `index.html`이라면 하루쯤 fresh로 보고 묻지 않습니다.

정적 파일 서버를 기본 설정으로 쓰다가 "배포했는데 그대로"를 만나는 대표적인 원인입니다. **모든 응답에 `Cache-Control`을 명시**하는 게 안전합니다.

## 배포 전략: HTML은 확인하고, 정적 파일은 1년

캐시를 잘 쓰면서도 배포가 바로 반영되게 하는 표준 방법은 이렇습니다.

| 파일 | 이름 | Cache-Control | 이유 |
| --- | --- | --- | --- |
| HTML | `/products` (고정) | `no-cache` 또는 짧은 기간 | 배포하면 바로 새 HTML을 받아야 함 |
| JS·CSS·이미지 | `main.3f9a2c.js` (내용 해시 포함) | `max-age=31536000, immutable` | 내용이 바뀌면 **이름이 바뀜** |

빌드 도구는 파일 내용으로 해시를 만들어 이름에 붙입니다. 내용이 한 글자라도 바뀌면 이름이 `main.8d41e0.js`로 바뀌고, 새 HTML은 새 이름을 가리킵니다. 브라우저 입장에서는 **처음 보는 주소**라 캐시가 있을 수 없으니 새로 받습니다. 옛 파일은 1년 동안 캐시에 남아 있어도 아무도 가리키지 않으니 상관없습니다.

정리하면 **HTML은 "지금 어떤 파일을 쓰는지"를 알려 주는 목차**라서 항상 확인하고, 목차가 가리키는 파일은 이름이 곧 버전이라 영원히 캐시해도 됩니다.

Next.js는 이 전략을 기본으로 씁니다.

- `/_next/static/`의 JS·CSS: `public, max-age=31536000, immutable`. 이름에 해시가 들어 있고, 이 헤더는 바꿀 수 없습니다.
- 정적 페이지: `s-maxage=31536000`. **CDN**에 오래 두고, 다시 빌드하거나 재검증할 때 CDN 쪽을 갱신합니다.
- 동적 페이지: `private, no-cache, no-store, max-age=0, must-revalidate`.

## 배포 직후의 빈 화면: 옛 HTML이 지워진 파일을 찾는다

처음에 말한 `ChunkLoadError`는 반대 방향의 문제입니다.

1. 사용자가 배포 전에 페이지를 열어 둡니다. 이 페이지는 옛 HTML이 가리키는 `chunk.aaa.js`들을 씁니다.
2. 그사이 배포가 되고, 서버에는 `chunk.bbb.js`만 남습니다.
3. 사용자가 다른 메뉴로 이동하면, 페이지는 필요한 코드를 **옛 이름**으로 요청합니다.
4. 서버에 그 파일이 없어 404가 나고 화면이 깨집니다.

캐시 문제가 아니라 **서로 다른 버전이 섞이는 문제**(version skew)입니다. 해결 방법은 이렇습니다.

- **옛 정적 파일을 바로 지우지 않습니다.** CDN이나 저장소에 이전 배포의 파일을 한동안 남겨 둡니다. Vercel처럼 배포마다 별도로 보관하는 플랫폼에서는 이 문제가 덜합니다.
- **버전이 다르면 새로고침합니다.** Next.js는 `deploymentId`를 설정하면 페이지 이동 요청에 배포 id를 붙이고, 서버와 다르면 클라이언트 이동 대신 전체 새로고침을 해서 새 HTML을 받게 합니다.
- **청크 로드 실패를 잡아 새로고침합니다.** 직접 만든 SPA라면 동적 import가 실패했을 때 한 번 새로고침하는 처리를 넣습니다.

## 그래도 옛 화면이 보인다면

캐시는 브라우저 한 곳에만 있지 않습니다. 위에서부터 차례로 확인합니다.

1. **브라우저:** 개발자 도구 Network 탭에서 HTML 요청이 `(disk cache)`인지 `304`인지 `200`인지 봅니다. "Disable cache"를 켜고 다시 열어 보면 브라우저 캐시 문제인지 바로 구분됩니다.
2. **서비스 워커:** PWA나 오프라인 지원을 넣었다면 서비스 워커가 옛 파일을 직접 돌려주고 있을 수 있습니다. Application 탭에서 확인합니다.
3. **CDN:** `s-maxage`로 CDN에 저장된 HTML은 브라우저 캐시를 지워도 그대로입니다. 응답 헤더의 `Age`, `x-cache` 같은 값으로 CDN이 준 응답인지 보고, 필요하면 CDN 캐시를 지웁니다.

## 정리

> "브라우저는 Cache-Control의 max-age 안에 있는 fresh한 파일은 서버에 묻지 않고 바로 쓰고, 기간이 지난 stale한 파일은 ETag를 If-None-Match로 보내 확인해서 바뀌지 않았으면 304를 받습니다. 그래서 HTML에 긴 캐시가 걸려 있거나 Cache-Control 없이 휴리스틱 캐시가 적용되면 배포해도 옛 화면이 보입니다. 표준 전략은 HTML은 no-cache로 매번 확인하고, JS와 CSS는 내용 해시를 파일 이름에 넣어 max-age 1년과 immutable로 캐시하는 것입니다. 내용이 바뀌면 이름이 바뀌어 새로 받게 됩니다. 배포 직후 열려 있던 페이지가 지워진 옛 청크를 요청해 깨지는 건 버전이 섞이는 문제라서, 옛 파일을 한동안 남기거나 버전이 다르면 새로고침하게 해서 막습니다."
