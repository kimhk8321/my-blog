[Jest](/posts/jest-testing)나 [Vitest](/posts/vitest-testing)를 쓰다 보면 전부 "모킹"이라고 부르게 됩니다. 그런데 대역(test double)에는 **역할이 다른 다섯 가지**가 있고, 구분해서 쓰면 테스트가 훨씬 명확해집니다.

## 왜 대역이 필요한가

진짜를 쓸 수 없는 이유는 셋 중 하나입니다.

- **느리다** — 외부 API 호출, 대용량 연산
- **결정적이지 않다** — 현재 시각, 랜덤, 네트워크 상태
- **통제할 수 없다** — 결제 승인, 이메일 발송, 남의 서버 장애

테스트는 **같은 입력에 항상 같은 결과**여야 하는데, 위의 것들이 그걸 깨뜨립니다.

## 다섯 가지 대역

| 이름 | 하는 일 | 언제 |
| --- | --- | --- |
| **더미(Dummy)** | 자리만 채움. 실제로 안 쓰임 | 필수 인자를 채워야 할 때 |
| **스텁(Stub)** | 정해진 값을 돌려줌 | "이런 응답이 왔을 때"를 만들 때 |
| **스파이(Spy)** | 진짜를 쓰되 호출을 기록 | 호출됐는지 확인하고 싶을 때 |
| **목(Mock)** | 호출을 기대하고 검증까지 | 상호작용 자체가 요구사항일 때 |
| **페이크(Fake)** | 간단히 동작하는 진짜 대체품 | 인메모리 DB처럼 |

### 스텁 — 상태를 만든다

"에러가 났을 때 UI가 어떻게 되나"를 보려면 에러를 **만들어야** 합니다.

```ts
// 이 응답이 왔을 때의 화면을 확인하고 싶다
vi.spyOn(api, "getUser").mockResolvedValue({ id: 1, name: "김" });
vi.spyOn(api, "getUser").mockRejectedValue(new Error("서버 오류"));
```

여기서 검증하는 건 **결과 상태**입니다 — "에러 메시지가 보이나".

### 스파이·목 — 상호작용을 본다

반면 "**호출됐는가**" 자체가 요구사항일 때가 있습니다.

```ts
const send = vi.fn();
await signup({ email: "a@b.com" }, { sendWelcomeMail: send });

expect(send).toHaveBeenCalledWith("a@b.com"); // 메일 발송은 눈에 안 보이는 결과
```

이메일 발송처럼 **결과가 화면에 안 남는 부수효과**는 호출을 확인하는 것 말고 방법이 없습니다.

### 페이크 — 가볍게 진짜처럼

인메모리 저장소가 대표적입니다. 스텁처럼 값을 고정하는 게 아니라 **실제로 넣고 빼는 동작**을 합니다.

```ts
class FakeGuestbook {
  private items = [];
  add(entry) { this.items.unshift(entry); }
  list() { return this.items.slice(0, 50); }
}
```

로직이 여러 단계를 거칠 때(썼다가 다시 읽는 등) 스텁보다 훨씬 자연스럽습니다.

## 과잉 모킹의 함정

여기가 진짜 중요한 부분입니다. **모킹을 많이 할수록 테스트는 통과하기 쉬워지고, 동시에 쓸모없어집니다.**

```ts
// 거의 모든 걸 모킹한 테스트 — 무엇을 검증하는 걸까?
vi.mock("./api");
vi.mock("./store");
vi.mock("./formatter");
```

전부 가짜면 **가짜들끼리 잘 맞는지**를 확인할 뿐입니다. 진짜 코드가 바뀌어도 테스트는 계속 초록불이죠. 이걸 "테스트가 구현에 결합됐다"고 합니다 — 리팩터링만 해도 테스트가 깨지고, 정작 버그는 못 잡습니다.

기준은 [백엔드 테스트](/posts/backend-testing)에서 쓴 것과 같습니다.

> **내 것은 진짜로, 남의 것은 가짜로.**

내 DB·내 로직은 되도록 진짜를 쓰고, 결제·메일·외부 API처럼 통제 밖의 것만 대역으로 바꿉니다.

## 시간과 랜덤도 대역이 필요하다

의외로 자주 놓치는 비결정성입니다.

```ts
vi.useFakeTimers();
vi.setSystemTime(new Date("2026-01-01"));
// "3일 전"처럼 상대 시간을 표시하는 로직을 안정적으로 검증
```

"어제 자정에만 실패하는 테스트"의 원인이 대개 이겁니다.

## 대역이 많이 필요하면 설계를 의심하자

테스트를 쓰다가 **모킹할 게 너무 많다면**, 그건 테스트가 아니라 **코드의 문제**인 경우가 많습니다. 한 함수가 너무 많은 것에 의존하고 있다는 신호죠.

의존을 인자로 받게 바꾸면(의존성 주입) 대역을 넣기도 쉬워지고, [설계도 느슨해집니다](/posts/clean-code-refactoring).

```ts
// 바꾸기 어려움: 내부에서 직접 가져다 씀
async function signup(input) { await mailer.send(...); }

// 바꾸기 쉬움: 밖에서 넣어 줌
async function signup(input, { mailer }) { await mailer.send(...); }
```

**테스트하기 어렵다는 건 대개 설계가 굳어 있다는 뜻**입니다.

---

대역의 핵심은 "**무엇을 검증하려는가**"에 맞춰 고르는 것입니다. 상태를 보려면 스텁, 상호작용을 보려면 스파이·목, 여러 단계를 거치면 페이크. 그리고 무엇보다 **필요한 만큼만** 쓰는 것 — 가짜가 많아질수록 테스트는 진실에서 멀어집니다. 다음 글에서는 테스트를 아예 먼저 쓰는 [TDD](/posts/tdd)를 봅니다.
