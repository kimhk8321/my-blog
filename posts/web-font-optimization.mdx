[이미지](/posts/image-optimization) 다음으로 무거운 게 폰트입니다. 특히 한글은 사정이 특별해요. 영문 폰트는 글자(글리프)가 알파벳·숫자·기호 합쳐 **수백 개**면 되지만, 한글은 완성형만 **11,172자**입니다. 그래서 같은 서체라도 한글 폰트는 영문의 **수십 배**가 됩니다. 몇 MB짜리도 흔해요.

## 폰트가 늦으면 생기는 두 가지 사고

폰트 파일이 도착하기 전, 브라우저는 선택을 해야 합니다.

- **FOIT**(Flash of Invisible Text): 글자를 **안 보여주고** 기다린다 → 화면이 텅 빔
- **FOUT**(Flash of Unstyled Text): 대체 폰트로 **일단 보여준다** → 나중에 글자가 확 바뀜

둘 다 거슬리지만 성격이 다릅니다. FOIT는 "내용을 못 읽는" 문제고, FOUT는 "읽다가 튀는" 문제죠. 어느 쪽을 감수할지는 `font-display`로 고릅니다.

## font-display — 무엇을 감수할지 고르기

```css
@font-face {
  font-family: "Pretendard";
  src: url("/fonts/pretendard.woff2") format("woff2");
  font-display: swap;
}
```

| 값 | 동작 |
| --- | --- |
| `block` | 최대 3초 글자 숨김(FOIT). 웬만하면 피할 것 |
| `swap` | 즉시 대체 폰트로 보여주고, 도착하면 교체(FOUT) |
| `fallback` | 아주 짧게만 숨기고, 늦게 오면 **교체하지 않음** |
| `optional` | 거의 즉시 판단. 늦으면 **이번 방문엔 안 씀** |

**본문은 `swap`** 이 무난합니다. 읽을 수 있는 게 우선이니까요. 다만 `swap`은 뒤에서 볼 **레이아웃 밀림**을 만듭니다. 브랜드 서체가 아니라면 `optional`도 좋은 선택이에요 — 느린 네트워크에선 아예 포기하고 시스템 폰트로 깔끔하게 갑니다.

## 서브셋 — 안 쓰는 글자를 빼자

한글 폰트 최적화의 핵심입니다. 11,172자를 다 넣지만, **실제로 쓰는 글자는 훨씬 적습니다.**

- **KS X 1001 상용 2,350자**만 담으면 대부분의 한국어 문서를 커버하면서 용량이 크게 줄어듭니다.
- 글자가 고정된 곳(로고, 정해진 카피)이라면 **그 글자만** 담을 수도 있어요.

여기에 **WOFF2** 포맷을 쓰면 또 30% 정도 줄어듭니다. 요즘은 WOFF2 하나만 제공해도 충분해요(구형 포맷을 함께 두면 그만큼 낭비).

## unicode-range — 필요한 조각만 받게

더 나아가, 폰트를 여러 조각으로 쪼개고 **어떤 글자 범위를 담당하는지** 알려줄 수 있습니다. 그러면 브라우저는 **페이지에 실제로 쓰인 글자가 속한 조각만** 내려받습니다.

```css
@font-face {
  font-family: "MyFont";
  src: url("/fonts/mine-korean-1.woff2") format("woff2");
  unicode-range: U+AC00-D7A3;   /* 한글 음절 */
}
@font-face {
  font-family: "MyFont";
  src: url("/fonts/mine-latin.woff2") format("woff2");
  unicode-range: U+0000-00FF;   /* 라틴 기본 */
}
```

구글 폰트가 한글 폰트를 100개 넘는 조각으로 쪼개 제공하는 게 바로 이 방식입니다. 영문만 있는 페이지라면 한글 조각은 **아예 받지 않죠.**

## preload — 발견을 앞당기기

폰트는 **CSS를 파싱하고, 그 폰트를 쓰는 요소를 만나야** 비로소 요청됩니다. 발견이 늦은 리소스예요. 그래서 확실히 쓸 폰트는 미리 알려줍니다.

```html
<link rel="preload" href="/fonts/pretendard.woff2" as="font" type="font/woff2" crossorigin />
```

`crossorigin`은 빠뜨리면 **두 번 받게 되니** 꼭 넣어야 합니다(폰트는 익명 CORS 모드로 요청되기 때문). 그리고 preload는 **정말 첫 화면에 쓰는 것만** 하세요. 남발하면 다른 중요한 리소스와 대역폭을 다투게 됩니다.

## 폰트가 바뀔 때 생기는 밀림 줄이기

`swap`을 쓰면 대체 폰트 → 실제 폰트로 교체되는데, 두 폰트의 글자 폭·높이가 다르면 **줄 수가 바뀌고 레이아웃이 밀립니다**([CLS](/posts/core-web-vitals)).

이걸 줄이는 방법은 **대체 폰트의 크기를 실제 폰트에 맞춰 보정**하는 겁니다.

```css
@font-face {
  font-family: "Pretendard-fallback";
  src: local("Apple SD Gothic Neo"), local("Malgun Gothic");
  size-adjust: 105%;      /* 대체 폰트를 살짝 키워 폭을 맞춤 */
  ascent-override: 90%;
  descent-override: 22%;
}
```

교체 전후의 글자 크기가 비슷해지면 밀림이 눈에 띄게 줄어듭니다. 그리고 **대체 폰트 스택을 시스템 폰트로 잘 짜두는 것**만으로도 절반은 해결돼요.

## 가변 폰트

굵기별로 파일을 따로 받는 대신(Regular·Medium·Bold…), **한 파일에 굵기 축을 담은** 가변 폰트를 쓰면 여러 굵기를 쓸 때 총량이 줄어듭니다. 다만 한 굵기만 쓴다면 단일 폰트가 더 가볍습니다. **몇 가지 굵기를 쓰느냐**로 판단하세요.

## 프레임워크가 해주는 것

Next.js의 `next/font`는 폰트 파일을 **빌드 시점에 자체 호스팅**으로 가져오고, `@font-face`와 preload를 자동으로 넣고, 대체 폰트 크기 보정까지 자동으로 계산해 줍니다. 외부 요청이 사라져 개인정보·성능 양쪽에 이득이고요.

```jsx
import { Geist } from "next/font/google";
const geist = Geist({ subsets: ["latin"], display: "swap" });
```

이 블로그도 이 방식으로 폰트를 씁니다. `subsets`를 지정하는 게 곧 위에서 본 서브셋이에요.
