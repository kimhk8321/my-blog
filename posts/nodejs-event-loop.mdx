프론트엔드에서 [자바스크립트의 이벤트 루프](/posts/js-deep-dive-async)는 이미 봤습니다. 그런데 서버로 오면 같은 이벤트 루프가 완전히 다른 의미를 갖습니다. **"싱글 스레드인 Node.js가 어떻게 수천 개의 동시 요청을 감당하지?"** — 이게 백엔드 관점의 핵심 질문입니다.

## 역설 — 싱글 스레드인데 동시성?

Node.js의 JS 실행은 **한 스레드**입니다. 상식적으론 요청을 하나씩만 처리할 것 같죠. 그런데 실제론 수천 개를 동시에 처리합니다. 비밀은 **대부분의 서버 작업이 '기다림'** 이라는 데 있습니다.

DB 조회, 파일 읽기, 외부 API 호출 — 이들은 CPU를 쓰는 게 아니라 **결과를 기다리는** 일입니다. 이 기다림 동안 스레드를 놀리지 않는 게 핵심이에요.

## 논블로킹 I/O

전통적 서버는 요청마다 스레드를 하나씩 배정하고, I/O를 기다리는 동안 그 스레드는 **블로킹(멈춤)** 됩니다. 요청이 많으면 스레드가 폭증하죠.

Node는 다릅니다. I/O를 **논블로킹**으로 요청하고 **"끝나면 알려줘"** 하고는 **바로 다음 일**로 넘어갑니다.

```js
// 이 줄에서 멈추지 않는다. DB에 "조회 요청"만 하고 즉시 다음으로.
db.query("SELECT ...", (err, rows) => {
  // 결과가 준비되면 이 콜백이 이벤트 루프에 의해 나중에 실행됨
});
doNextThing(); // ← 위 조회를 기다리지 않고 바로 실행
```

한 스레드가 "요청 접수 → I/O 위임 → 다음 요청 접수 → I/O 위임…"을 계속 돌며, 완료된 I/O의 콜백만 순서대로 처리합니다. 이 조율자가 **이벤트 루프**이고, 실제 I/O 대기·스레드 풀은 그 아래 **libuv**가 담당합니다.

## 그래서 — 이벤트 루프를 막으면 안 된다

여기서 백엔드의 가장 중요한 규칙이 나옵니다. **CPU를 오래 붙잡는 동기 작업은 이벤트 루프 전체를 멈춘다.**

```js
app.get("/heavy", (req, res) => {
  const result = fibonacci(45); // 동기 계산 — 몇 초간 CPU 점유
  res.json({ result });
});
```

이 요청이 도는 동안 **다른 모든 요청이 대기**합니다. 스레드가 하나뿐이니까요. 프론트에서 [무거운 계산이 UI를 얼리던 것](/posts/web-workers)과 똑같은 문제가, 서버에선 **모든 사용자의 응답 지연**으로 나타납니다.

해법도 비슷합니다.

- **CPU 바운드 작업은 `worker_threads`** 로 별도 스레드에 넘긴다 (프론트의 Web Worker에 대응).
- 무거운 배치는 **큐**에 넣어 별도 워커 프로세스가 처리.
- 큰 데이터는 한 번에 말고 **스트림**으로 흘려보낸다.

## 이벤트 루프의 단계 (간단히)

이벤트 루프는 매 반복마다 정해진 단계를 돕니다(타이머 → 대기 콜백 → poll(I/O) → check(`setImmediate`) → close). 그리고 각 단계 사이에 **마이크로태스크**(Promise 콜백, `process.nextTick`)를 먼저 비웁니다. [JS 이벤트 루프 글](/posts/js-deep-dive-async)에서 본 매크로/마이크로태스크 우선순위가 서버에서도 그대로 적용돼요.

## 언제 Node가 강하고, 언제 약한가

- **강함**: I/O 중심 — API 서버, 실시간(채팅), 프록시, BFF. "기다림"이 많아 논블로킹의 이점이 큼.
- **약함**: CPU 중심 — 대규모 이미지·영상 처리, 복잡한 수치 연산. 이벤트 루프를 막기 쉬워, 이런 건 워커·별도 서비스로 뺀다.

---

Node.js의 동시성은 "**스레드를 늘리는 게 아니라, 기다리는 동안 놀지 않는 것**"입니다. 논블로킹 I/O와 이벤트 루프가 그걸 가능하게 하고, 그래서 "이벤트 루프를 막지 마라"가 절대 규칙이 됩니다. 프론트에서 메인 스레드를 비워 두던 감각이, 서버에선 이벤트 루프를 비워 두는 것으로 이어지죠. 다음 글에서는 그 서버가 데이터를 안전하게 지키는 [트랜잭션과 격리 수준](/posts/transactions-isolation)을 봅니다.
