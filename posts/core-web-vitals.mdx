성능을 "빠르다/느리다"로만 말하면 고칠 수가 없습니다. **무엇을 재는지** 정해야 하죠. 구글이 정리한 **Core Web Vitals**는 사용자 체감을 세 갈래로 나눕니다.

| 지표 | 재는 것 | 좋음 |
| --- | --- | --- |
| **LCP** | 주요 내용이 **언제 보이나** | 2.5초 이하 |
| **INP** | 조작에 **얼마나 빨리 반응하나** | 200ms 이하 |
| **CLS** | 화면이 **얼마나 안 튀나** | 0.1 이하 |

"로딩 / 반응성 / 안정성" — 사용자가 짜증 내는 세 가지를 그대로 옮긴 셈입니다. [성능 최적화 개요](/posts/frontend-performance-optimization)에서 목록만 짚었으니, 여기선 각각을 어떻게 고치는지 봅니다.

## LCP — 가장 큰 것이 언제 보이나

화면에서 **가장 큰 요소**(대개 대표 이미지나 큰 제목)가 그려진 시점입니다. "이 페이지가 로딩됐다"고 느끼는 순간에 가장 가깝죠.

LCP가 나쁜 이유는 대개 넷 중 하나입니다.

1. **서버 응답이 느리다** — 첫 바이트까지 오래 걸림. [캐싱](/posts/http-caching)·CDN으로 개선
2. **리소스 발견이 늦다** — CSS를 파싱해야 비로소 이미지를 요청하는 경우. `preload`와 `fetchpriority="high"`로 앞당김
3. **리소스가 무겁다** — [이미지 최적화](/posts/image-optimization)로 포맷·해상도 조정
4. **렌더링을 막는 것이 있다** — 동기 스크립트나 무거운 CSS가 파싱을 막음

특히 흔한 실수: **첫 화면 이미지에 `loading="lazy"`를 걸어두는 것**. 좋은 의도가 정확히 반대로 작용합니다.

## INP — 눌렀을 때 얼마나 빨리 반응하나

예전 지표 **FID**를 대체한 것입니다. FID는 "첫 상호작용의 **지연 시간**"만 봤는데, INP는 **모든 상호작용**을 보고 **응답이 화면에 그려질 때까지** 전체를 잽니다. 훨씬 정직한 지표죠.

INP는 **메인 스레드가 막혀 있으면** 나빠집니다.

- **긴 작업(long task)** — 50ms 넘게 스레드를 붙잡는 자바스크립트
- 상호작용 때마다 도는 **무거운 렌더링**
- 과한 리렌더 ([리렌더 최적화](/posts/rerender-optimization))

고치는 방법:

```js
// 나쁨: 클릭 한 번에 무거운 계산 → 화면이 멈춘다
button.onclick = () => { const r = heavyWork(items); render(r); };
```

- **작업을 쪼갠다** — 긴 루프를 나눠 사이사이 브라우저에 양보
- **워커로 보낸다** — [Web Worker](/posts/web-workers)에서 계산하고 결과만 받기
- **급하지 않은 갱신을 뒤로** — React라면 [useTransition](/posts/concurrent-rendering)으로 우선순위를 낮춤
- **입력에 즉시 반응부터** — 무거운 일 전에 눌린 상태 표시라도 먼저 그리기

## CLS — 화면이 얼마나 튀나

읽고 있는데 광고가 로드되며 글이 아래로 밀리는 그 경험. 누적된 밀림의 양을 점수화한 게 CLS입니다. 원인은 거의 항상 **"자리를 안 잡아둔 것"** 입니다.

- **이미지에 크기가 없다** → `width`/`height` 또는 `aspect-ratio` ([이미지 최적화](/posts/image-optimization))
- **폰트가 교체되며 글이 밀린다** → `size-adjust`로 대체 폰트 보정 ([웹 폰트 최적화](/posts/web-font-optimization))
- **동적 배너·광고가 위에 삽입된다** → 자리를 미리 비워두기
- **애니메이션이 레이아웃을 바꾼다** → `transform`으로 대체 ([렌더링 파이프라인](/posts/rendering-pipeline))

사용자 조작 직후 500ms 안의 변화는 점수에 포함되지 않습니다. "내가 눌러서 바뀐 것"은 밀림으로 느끼지 않으니까요.

## 실험실 측정 vs 실사용자 측정

여기서 많이들 헷갈립니다.

- **실험실(Lab)** — Lighthouse처럼 **내 컴퓨터에서 조건을 고정**해 재는 것. 재현 가능하고 디버깅에 좋음. 다만 INP는 **실제 조작이 필요**해서 제대로 안 나옵니다(그래서 Lighthouse는 대신 TBT를 봅니다).
- **실사용자(RUM/필드)** — 진짜 방문자들의 기기·네트워크에서 수집한 값. 검색 순위에 쓰이는 건 이쪽입니다.

**"Lighthouse 100점인데 실제로는 느리다"** 는 흔한 일입니다. 내 노트북과 좋은 인터넷에서 잰 값이니까요. 그래서 실사용자 값도 같이 봐야 합니다.

```js
// web-vitals로 실제 방문자 값 수집하기
import { onLCP, onINP, onCLS } from "web-vitals";

onLCP(send);
onINP(send);
onCLS(send);
```

수집한 값은 평균이 아니라 **75 백분위수**로 봅니다. 평균은 소수의 아주 느린 경험을 가려버리거든요. [서버 모니터링에서 p95를 보던 것](/posts/observability)과 같은 이유입니다.

---

Core Web Vitals의 쓸모는 "**막연한 빠름을 고칠 수 있는 항목으로 바꿔준다**"는 데 있습니다. LCP는 무엇이 늦게 오는지, INP는 무엇이 스레드를 막는지, CLS는 무엇이 자리를 안 잡았는지 — 세 질문으로 좁혀지죠. 그리고 점수 자체보다 **실제 방문자의 값**이 진짜입니다.
