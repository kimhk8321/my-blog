서버가 한 대일 때는 프로세스 안의 mutex로 동시에 실행되는 작업을 줄일 수 있습니다. 서버를 여러 대로 늘리면 각 프로세스가 자기 락만 봅니다. A 서버가 잠갔다는 사실을 B 서버는 모르므로 모두가 접근할 수 있는 저장소에 락을 둬야 합니다.

Redis 분산 락은 간단해 보입니다. 키가 없을 때만 저장하는 `SET NX`로 한 요청만 통과시키면 됩니다. 실제로 어려운 부분은 **잠그는 순간보다 풀어야 하는 순간**에 있습니다.

## 가장 작은 락

```ts
const acquired = await redis.set(
  `lock:stock:${productId}`,
  "locked",
  { nx: true, ex: 10 },
);

if (!acquired) throw new Error("다른 요청이 처리 중입니다.");

try {
  await decreaseStock(productId);
} finally {
  await redis.del(`lock:stock:${productId}`);
}
```

`NX`는 키가 없을 때만 저장하고, `EX 10`은 10초 뒤 자동 만료시킵니다. 만료가 없으면 락을 잡은 서버가 죽었을 때 누구도 다시 처리할 수 없습니다.

## 남의 락을 지우는 시간차

1. 요청 A가 10초 락을 잡는다.
2. 작업이 느려 락이 만료된다.
3. 요청 B가 같은 키로 새 락을 잡는다.
4. A가 작업을 끝내고 `DEL`을 실행한다.
5. A가 B의 락을 지워 버린다.

값에 요청마다 다른 토큰을 저장하고, **내 토큰일 때만 삭제**해야 합니다.

```ts
const token = crypto.randomUUID();
const key = `lock:stock:${productId}`;
const acquired = await redis.set(key, token, { nx: true, ex: 10 });
```

확인과 삭제도 분리하면 안 됩니다. 값을 확인한 직후 키가 만료될 수 있기 때문입니다. Lua 스크립트로 두 작업을 원자적으로 묶습니다.

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
end
return 0
```

## TTL과 멈췄다가 살아난 작업

TTL이 작업 시간보다 짧으면 작업 중 락이 풀리고, 너무 길면 장애 뒤 다른 요청이 오래 기다립니다. 작업 중 주기적으로 소유권을 확인하며 TTL을 연장할 수도 있지만, 락을 오래 유지해야 한다면 작업 구조부터 다시 볼 신호입니다.

락을 가진 프로세스가 긴 GC 정지로 멈춘 사이 락이 만료될 수도 있습니다. 새 작업자가 들어온 뒤 예전 프로세스가 깨어나 쓰지 못하게 하려면 증가하는 **fencing token**을 발급하고 실제 저장소가 더 작은 토큰의 쓰기를 거절해야 합니다.

```text
A의 토큰 41 → 오래 멈춤
B의 토큰 42 → 저장 성공
A가 다시 쓰기 시도 → 저장소가 41을 거절
```

정확성이 중요한 작업은 Redis 락 하나가 아니라 데이터가 저장되는 곳에서도 순서를 검증해야 합니다.

## 락보다 먼저 볼 것

### 원자 연산

```sql
UPDATE products
SET stock = stock - 1
WHERE id = ? AND stock > 0;
```

영향받은 행이 0이면 품절입니다. DB가 원자적으로 판단하므로 애플리케이션 락이 필요 없습니다.

### UNIQUE 제약과 version

한 사용자당 쿠폰 한 장이라면 `(coupon_id, user_id)`에 UNIQUE 제약을 둡니다. 충돌이 드물다면 [version 조건부 저장](/posts/optimistic-concurrency-control)으로 감지하고 재시도하는 편이 락 대기보다 효율적입니다.

### 메시지 큐

같은 자원의 작업을 한 소비자가 순서대로 처리할 수 있다면 락 경쟁을 큐의 직렬 처리로 바꿀 수 있습니다. 처리량과 지연 사이의 선택은 필요합니다.

## Redis 락이 맞는 자리

- 여러 서버에서 같은 정기 작업이 중복 실행되지 않게 할 때
- 캐시 만료 순간 한 요청만 값을 다시 채우게 할 때
- 외부 API 호출처럼 DB 트랜잭션으로 묶기 어려운 짧은 작업을 조정할 때
- 중복 실행의 영향이 제한적이고 실패 시 복구할 수 있을 때

반대로 결제 원장이나 재고의 최종 무결성을 Redis 락에만 맡기면 안 됩니다. 락은 경쟁을 줄이는 조정 장치이고, 데이터베이스 제약과 트랜잭션은 잘못된 상태의 저장을 막는 마지막 선입니다.

---

분산 락의 핵심은 `SET NX` 한 줄이 아니라 **소유자만 해제하고, 만료 뒤 살아난 작업도 안전하게 거절하는 것**입니다. 락이 정말 필요하다면 검증된 라이브러리를 사용하고 TTL 초과와 획득 실패를 관측 지표로 남기는 데까지가 구현의 일부입니다.
