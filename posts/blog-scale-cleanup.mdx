글이 156편이 됐습니다. 오늘은 뭘 할지 고르려고 블로그부터 재봤어요. 테스트는 24개 다 초록불, 린트도 깨끗, 빌드도 통과. 급한 불은 없어 보였습니다.

그런데 빌드 산출물을 열어 봤더니 이렇더군요.

```bash
$ ls -l .next/server/app/index.html
-rw-r--r-- 1 root root 1090319 ...   # 1.1MB
```

**홈 HTML 한 장이 1.1MB.** 글 목록 하나가 이럴 일인가 싶었습니다.

## 한 편에 6.6KB씩

원인은 짐작이 갔습니다. `src/app/page.tsx`가 `getAllPosts()`로 156편을 통째로 받아 목록에 넘기고 있었거든요. 화면에는 스무 편쯤 보이는데, 나머지 136편도 값은 똑같이 치르고 있던 셈입니다.

짐작만으로 고치기 전에 **바닥값부터 재 봤습니다.** 스무 편만 넘기도록 한 줄 고치고 빌드한 거죠.

| 렌더한 글 | index.html |
| --- | --- |
| 156편 | 1,090KB |
| 20편 | 191KB |

한 편당 **약 6.6KB**. 여기서 "스무 편만 그리면 190KB쯤 되겠구나" 하고 [페이지네이션](/posts/blog-search)을 붙였습니다. 정렬을 먼저 하고 자르는 순서만 지키면 되는 간단한 일이었어요 — 순서가 바뀌면 "제목순"이 스무 편 안에서만 도니까요.

```ts
// 정렬이 먼저, 자르기가 나중
const sorted = sortPosts(posts, sort);
const { items, page, totalPages } = paginate(sorted, current, 20);
```

그리고 다시 빌드했습니다.

```bash
845097   # ...845KB?
```

**20%밖에 안 줄었습니다.** 190KB를 기대했는데요.

## 타입은 `PostMeta`인데, 값은 `Post`였다

렌더하는 글을 156편에서 20편으로 줄였는데 크기가 그대로라면, 커진 건 **그린 것**이 아니라 **들고 간 것**입니다.

글 목록은 정렬 드롭다운 때문에 클라이언트 컴포넌트입니다. 서버 컴포넌트가 클라이언트 컴포넌트에 props를 넘기면, 그 값은 **전부 직렬화돼 HTML에 실려** 갑니다. 화면에 그리든 안 그리든요.

그래서 무엇을 넘기고 있었는지 봤습니다.

```ts
export function getAllPosts(): PostMeta[] {
  return getAllPostsWithContent();   // ← 여기
}
```

`PostMeta`는 본문이 없는 타입입니다. `Post`는 본문이 있는 타입이고요. `Post`는 `PostMeta`를 상속하니까 **타입 검사는 통과합니다.** 하지만 돌려주는 객체에는 `content` 필드가 그대로 붙어 있죠.

> 타입이 좁아진다고 값이 좁아지지는 않습니다. TypeScript는 필드를 **가려 줄 뿐 지워 주지 않아요.**

즉 홈을 열 때마다 **블로그 글 156편의 마크다운 전문**이 HTML에 직렬화돼 내려가고 있었습니다. 목록에는 제목과 한 줄 설명만 쓰는데 말이죠.

고치는 건 한 함수였습니다.

```ts
function toMeta(post: Post): PostMeta {
  return { slug: post.slug, title: post.title, /* …본문만 뺀 나머지 */ };
}

export function getAllPosts(): PostMeta[] {
  return getAllPostsWithContent().map(toMeta);
}
```

`...rest`로 떼어낼 수도 있지만, **무엇을 넘기는지 눈에 보이는 쪽**이 나중에 필드를 더할 때 안전하겠더군요.

| 단계 | index.html |
| --- | --- |
| 처음 | 1,090KB |
| 페이지네이션만 | 845KB |
| 본문까지 뺀 뒤 | **149KB** |

**86% 감소.** 정작 크게 줄인 쪽은 페이지네이션이 아니라 한 줄짜리 타입 문제였습니다. 순서를 반대로 했으면(먼저 프로파일링) 더 빨리 찾았겠죠.

## 태그가 345개, 그중 249개는 한 편짜리

같은 눈으로 나머지를 훑었습니다. 빌드 로그가 태그 페이지를 **345개** 찍고 있었어요. 세어 보니 그중 **249개(72%)가 글 한 편짜리**였습니다. 눌러 봐야 글 하나 나오고 끝나는 막다른 페이지죠.

세다가 진짜 버그도 하나 나왔습니다.

```
posts/dev-environment-setup.mdx:  tags: [..., "Webpack", ...]
posts/mini-bundler.mdx:    tags: [..., "webpack", ...]
```

**대문자 W와 소문자 w.** 사람 눈에는 같은 태그인데 `Map`의 키로는 다른 값이라, `/tags/Webpack`과 `/tags/webpack`이 각각 한 편씩 들고 따로 서 있었습니다.

파일을 고치는 걸로 끝낼 수도 있었지만, 그러면 다음에 또 납니다. 그래서 **"같은 태그인지"를 판단하는 키**를 따로 뒀어요.

```ts
export function tagKey(tag: string): string {
  return tag.trim().toLowerCase().replace(/\s+/g, " ");
}
```

화면에 보여 줄 표기는 **더 많이 쓴 쪽**을 고르고, 한 번씩 비기면 사전순으로 정해 결과를 고정했습니다. 빌드마다 표기가 바뀌면 곤란하니까요. 주소로 들어오는 `/tags/webpack`도 같은 키로 찾게 해서 예전 링크가 죽지 않게 했고요.

같은 키로 묶고 보니 대소문자만 문제가 아니었습니다. `a11y`와 `접근성`, `타입스크립트`와 `TypeScript`, `가상 DOM`과 `Virtual DOM`, `정규식`과 `정규표현식`… **같은 것을 다르게 적은 태그가 25쌍** 있었어요. 이것도 표 하나로 합쳤습니다.

```ts
const TAG_ALIASES: Record<string, string> = {
  a11y: "접근성",
  타입스크립트: "TypeScript",
  "가상 dom": "Virtual DOM",
  // …
};
```

글 파일은 건드리지 않았습니다. **표를 지우면 원래대로 돌아오는 쪽**이 낫다고 봤어요. `/tags/a11y`로 들어와도 제목과 canonical 주소는 `/tags/접근성`을 가리킵니다.

태그가 **345개에서 319개**로, 한 편짜리는 **214개**가 남았습니다.

### 나머지 214개는 그냥 뒀다 — 지우려다 만 이야기

남은 한 편짜리를 더 줄여 보려고 기준을 하나 세웠습니다.

> 한 편에만 붙은 태그는, 그 글에 더 넓은 태그가 남아 있고 지운 뒤에도 두 개 이상 남으면 지운다.

그럴듯해 보여서 **적용하기 전에 결과부터 찍어 봤습니다.** 태그 344개가 129개로, 한 편짜리는 247개에서 24개로 줄더군요. 숫자만 보면 대성공입니다. 그런데 무엇이 지워지는지를 봤더니,

```
big-o-notation   [알고리즘, 시간복잡도, Big-O, CS] → [알고리즘, CS]
bff-pattern      [BFF, 아키텍처, Next.js]         → [아키텍처, Next.js]
abort-controller [AbortController, 경쟁 상태, …]   → [fetch, 비동기, 데모]
```

Big-O 글에서 `Big-O`가, BFF 글에서 `BFF`가 사라집니다. **한 편짜리 태그가 그 글의 정체성 그 자체**였던 거죠. 남는 건 어느 글에나 붙는 넓은 태그뿐이고요.

생각해 보면 당연했습니다. 넓은 태그는 여러 글에 붙으니 자연히 숫자가 크고, 그 글에만 해당하는 말일수록 숫자가 1입니다. **"1편짜리"는 없애야 할 낭비가 아니라 구체적이라는 표시**였어요.

그래서 접었습니다. 태그 목록에서는 자주 쓰는 태그(2편 이상, 105개)를 펼치고 한 편짜리는 접어 두는 것으로 충분했습니다. 두 번째 글이 생기면 그때 저절로 짝을 찾을 테니까요.

> 200개를 지우기 직전에 멈춘 건 기준이 틀려서가 아니라, **적용 전에 결과를 찍어 봤기 때문**입니다. 마이그레이션은 항상 이렇게 해야겠더군요.

## RSS는 156편을 매번 실어 보내고 있었다

`feed.xml`이 128KB였습니다. 피드는 구독한 뒤로 올라온 글을 보여 주는 물건인데, 2026년 6월 글까지 매번 같이 내려가고 있었어요. 최근 20편으로 잘라 **18KB**가 됐습니다.

## 덤 — 같은 문자열을 344번 내려보내고 있었다

태그 페이지도 290KB였습니다. 이번엔 본문이 아니라 **클래스 이름**이었어요.

```
class="inline-flex items-center gap-2 rounded-full border border-black/10
       px-4 py-1.5 text-sm text-foreground/70 transition-colors …"
```

칩 하나에 약 190자. 태그가 344개니 마크업에 한 번, RSC 페이로드에 한 번 — 같은 문자열이 **700번 가까이** 실려 나갑니다. 유틸리티 클래스는 편하지만, 반복이 수백 번이면 이야기가 다르더군요. 자주 쓰는 조합만 클래스로 뽑았습니다.

```css
@layer components {
  .tag-chip { @apply inline-flex items-center gap-2 rounded-full …; }
}
```

**290KB → 153KB.**

그리고 글 목록을 읽는 함수에 메모이제이션을 붙였습니다. 검색 색인은 진작 그렇게 해 뒀는데, 정작 글을 읽는 쪽은 **부를 때마다 156편을 다시 파싱**하고 있었어요. 빌드 한 번에 수백 번 불리는 함수인데 말이죠. 빌드가 **26초 → 19초**가 됐습니다.

## 확인은 여태 손으로만 하고 있었다

`.github` 디렉터리가 아예 없었습니다. 방금 제가 손으로 돌린 린트·테스트·빌드가 **자동으로는 한 번도 안 돌고 있던** 거죠. [지난 글](/posts/blog-testing)에서 "빌드만 확인하고 린트는 안 돌렸다"며 25건을 정리했던 게 그래서였습니다.

돌려 보니 셋 다 빠릅니다.

| | 시간 |
| --- | --- |
| 빌드(156편 + OG 이미지 156장) | 43초 |
| 테스트 | 2초 |
| 린트 | 7초 |

1분이면 끝나는 확인을 사람 기억에 맡기고 있었던 셈입니다. push와 PR에 셋을 거는 [워크플로](/posts/ci-cd)를 넣었습니다.

## 테스트 24 → 64

[지난번](/posts/blog-testing)에는 순수 함수 넷만 골랐습니다. 파일을 읽는 함수는 [대역이 필요해서](/posts/test-doubles) 미뤘죠. 이번엔 그 대역을 만들어 봤습니다.

```ts
vi.mock("@/lib/posts", () => ({
  getAllPostsWithContent: () => fixturePosts,
  getAllPosts: () => fixturePosts,
}));
```

진짜 `posts/` 폴더를 읽게 두면 **글을 한 편 쓸 때마다 점수가 흔들려** 테스트가 깨집니다. 그래서 "닮은 두 편 + 상관없는 두 편"만 둔 가짜 글로 바꿔 끼우고, **그 관계가 유지되는지**만 봤어요. 추천이 몇 점인지가 아니라, React 글의 짝이 React 글인지를요.

그리고 [지난번에 배운 대로](/posts/tdd) 버그를 심어 봤습니다.

| 심은 버그 | 결과 |
| --- | --- |
| 페이지 범위 보정 제거 | 1개 실패 |
| 태그 키의 소문자화 제거 | 3개 실패 |
| 1편짜리 시리즈도 묶기 | 1개 실패 |

셋 다 빨간불이 켜졌습니다. 초록불이 의미가 있는 초록불이더군요.

## 배운 것

- **재고 나서 고치자** — 페이지네이션은 "당연히 이게 문제겠지"였고, 실제 범인은 한 함수였습니다. 20편만 렌더한 실험 하나가 방향을 정해 줬어요.
- **타입이 맞다고 값이 그런 건 아니다** — `PostMeta`로 선언해 놓고 `Post`를 넘기고 있었습니다. 서버에서 클라이언트로 넘기는 경계에서는 **타입이 아니라 실제 객체**가 직렬화됩니다.
- **오타는 고치고, 오타가 나는 자리는 막자** — `webpack` 한 글자를 고치는 데 1분, 다시 안 나게 하는 데 10분이었습니다.
- **지우기 전에 찍어 보자** — 태그 200개를 지우는 기준이 그럴듯했는데, 결과를 미리 찍어 보니 글의 정체성을 지우고 있었습니다.
- **규모가 작을 땐 안 보인다** — 128편일 땐 몰랐던 게 156편이 되니 드러났습니다. 앞으로도 **가끔 재 보는 일정**이 필요하겠어요.

---

정작 오늘 한 일 중에 새 기능은 하나도 없습니다. 그런데 홈이 1.1MB에서 136KB가 됐고, 확인은 자동이 됐고, 테스트는 69개가 됐습니다. **글을 쌓는 것만큼 쌓인 글을 감당하는 것도 일**이라는 걸, 156편째에 배웠습니다.
