디자인 시스템을 만들다 보면 같은 고민에 부딪힙니다. **드롭다운, 탭, 모달, 툴팁** 같은 컴포넌트는 프로젝트마다 겉모습은 제각각인데, 안쪽 동작은 늘 똑같습니다. 열림/닫힘 상태, 포커스 관리, 키보드 조작, ARIA 속성… 이 "동작"을 매번 새로 짜는 건 낭비이고, 짤 때마다 접근성을 빼먹기 쉽습니다.

**헤드리스(headless) 컴포넌트**는 여기서 나온 답입니다. 이름 그대로 **머리(스타일)를 떼어낸** 컴포넌트죠. 상태·로직·접근성만 제공하고, 어떻게 생겼는지는 전적으로 사용하는 쪽에 맡깁니다. Radix UI, Headless UI, React Aria가 모두 이 철학 위에 서 있습니다.

이 탭은 클릭뿐 아니라 **화살표 키로도** 이동합니다. `role="tablist"`, `aria-selected`, 로빙 탭인덱스까지 들어 있죠. 그런데 색과 여백은 그냥 우리가 Tailwind로 입힌 것뿐입니다 — 동작과 스타일이 분리돼 있다는 뜻입니다.

## 왜 동작을 떼어내는가

버튼 세 개를 만들고 클릭하면 내용이 바뀌게 하는 건 쉽습니다. 진짜 어려운 건 **접근성**입니다. 제대로 된 탭이라면 이걸 다 만족해야 합니다.

- 탭 목록은 `role="tablist"`, 각 탭은 `role="tab"`, 내용은 `role="tabpanel"`
- 선택된 탭은 `aria-selected="true"`
- `Tab` 키로는 탭 그룹에 **한 번만** 진입하고, 그룹 안에서는 **화살표 키**로 이동 (로빙 탭인덱스)
- 스크린 리더가 "탭 2 / 3, 선택됨"처럼 읽어줄 것

이걸 컴포넌트마다 새로 구현하면 어딘가는 반드시 빠집니다. 헤드리스는 이 지식을 한곳에 응축합니다.

## 로직을 훅으로 뽑기

헤드리스 설계의 핵심은 **상태와 규칙을 커스텀 훅으로** 밀어 넣는 것입니다. 렌더링은 밖으로 내보내고요.

```jsx
function useTabs(count) {
  const [active, setActive] = useState(0);

  const onKeyDown = (e) => {
    if (e.key === "ArrowRight") setActive((a) => (a + 1) % count);
    if (e.key === "ArrowLeft") setActive((a) => (a - 1 + count) % count);
  };

  // 각 탭에 뿌릴 속성을 만들어 주는 '프롭 게터'
  const getTabProps = (i) => ({
    role: "tab",
    "aria-selected": active === i,
    tabIndex: active === i ? 0 : -1, // 선택된 탭만 Tab 대상
    onClick: () => setActive(i),
    onKeyDown,
  });

  const getPanelProps = () => ({ role: "tabpanel" });

  return { active, getTabProps, getPanelProps };
}
```

여기 등장하는 **프롭 게터(prop getter)** 패턴이 헤드리스의 상징입니다. 컴포넌트가 마크업을 그리는 대신, "이 요소엔 이 속성들을 붙이세요"라는 **속성 묶음**을 돌려줍니다.

## 스타일은 사용하는 쪽이

이제 쓰는 쪽은 마크업과 스타일에만 집중합니다. 접근성은 게터가 이미 챙겼습니다.

```jsx
function Tabs({ items }) {
  const { active, getTabProps, getPanelProps } = useTabs(items.length);

  return (
    <>
      <div role="tablist" aria-label="설정">
        {items.map((item, i) => (
          <button key={item.label} {...getTabProps(i)} className="내-맘대로">
            {item.label}
          </button>
        ))}
      </div>
      <div {...getPanelProps()}>{items[active].body}</div>
    </>
  );
}
```

같은 `useTabs`로 완전히 다르게 생긴 탭을 몇 개든 만들 수 있습니다. **동작은 공유하고 외형은 자유**, 이게 헤드리스가 파는 가치입니다.

## 합성(compound) 컴포넌트로 다듬기

라이브러리들은 여기서 한 걸음 더 나아가 API를 이렇게 노출합니다.

```jsx
<Tabs>
  <Tabs.List>
    <Tabs.Tab>개요</Tabs.Tab>
    <Tabs.Tab>사용법</Tabs.Tab>
  </Tabs.List>
  <Tabs.Panel>…</Tabs.Panel>
</Tabs>
```

`Tabs`가 Context로 `active`와 게터를 내려주고, `Tabs.Tab`이 그걸 꺼내 쓰는 **합성 컴포넌트** 구조입니다. 사용자는 게터를 직접 만질 필요 없이 선언적으로 조립만 하면 되죠. 유연함과 편의성 사이의 균형점입니다.

## 언제 직접 만들고, 언제 가져다 쓰나

솔직히 말하면, 프로덕션 모달·콤보박스의 접근성을 완벽히 구현하는 건 생각보다 훨씬 깊은 우물입니다. 포커스 트랩, `aria-activedescendant`, 스크롤 잠금, 화면 밖 요소 `inert` 처리… 그래서 실무에선 Radix나 React Aria 같은 검증된 헤드리스 라이브러리를 **동작 엔진**으로 깔고 스타일만 입히는 경우가 많습니다. 그래도 원리를 알아야 그 라이브러리를 제대로 쓰고, 필요할 때 커스텀할 수 있습니다.
