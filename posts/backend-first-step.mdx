프론트엔드만 파온 지 여러 해. 화면과 상호작용, 성능과 접근성은 손에 익었지만, 늘 **"서버 너머"** 는 반쯤 블랙박스였습니다. API를 호출하고 응답을 그리긴 하지만, 그 응답이 **어떻게 만들어지는지** — 데이터가 어디에 어떻게 저장되고, 요청이 어떤 계층을 거치고, 왜 그런 상태 코드가 오는지 — 는 남의 일이었죠.

이제 그 블랙박스를 열어보려 합니다. 프론트엔드를 떠나는 게 아니라, **경계를 넓히는** 겁니다.

## 왜 지금 백엔드인가

- **디버깅의 절반은 경계에서 일어난다.** "왜 이 요청이 401이지", "왜 이 데이터가 캐시됐지" 같은 문제는 프론트만 봐선 안 풀립니다. 서버를 이해해야 원인을 짚습니다.
- **풀스택이 곧 문제 해결 범위다.** 작은 기능은 API 설계부터 저장소까지 혼자 끝낼 수 있으면 훨씬 빠릅니다. 이 블로그의 [조회수](/posts/nextjs-caching) 기능이 그랬죠.
- **프론트 지식이 헛되지 않는다.** [Next.js의 서버 액션·라우트 핸들러](/posts/nextjs-route-handlers), [Promise·이벤트 루프](/posts/implementing-promise), [HTTP 캐싱](/posts/http-caching) — 이미 아는 것들이 백엔드에서 다시 만납니다. 절반은 이미 배운 셈입니다.

## 무엇을, 어떤 순서로

프론트엔드 개발자에게 익숙한 것부터, 낯선 것으로:

1. **HTTP·REST API 설계** — 이미 매일 호출하니 절반은 안다. 이번엔 **만드는** 쪽에서.
2. **데이터 저장소** — 키-값(Redis)부터 관계형(SQL)까지. 데이터 모델링의 사고방식.
3. **인증·인가** — 세션 vs 토큰(JWT), 쿠키, OAuth. [웹 보안](/posts/web-security)에서 프론트 관점으론 봤으니, 이번엔 서버 관점.
4. **검증·에러 처리·레이트 리밋** — 신뢰할 수 없는 입력을 다루는 법. 프론트 검증은 UX용, 서버 검증은 **보안용**.
5. **운영** — 로깅, 모니터링, 배포. [CI/CD](/posts/cicd-kubernetes)와 연결.

## 방식 — 글보다 먼저, 만든다

지금까지 이 블로그가 그랬듯, **개념을 글로만 정리하지 않고 직접 만들어 씁니다.** 마침 조회수 기능으로 [Upstash Redis](/posts/nextjs-caching)가 이미 붙어 있으니, 여기에 진짜 백엔드 기능을 하나씩 얹어가려 합니다.

그 첫 번째가 **방명록**입니다. 단순해 보이지만 백엔드의 핵심이 다 들어 있어요 — API 설계(GET/POST), 데이터 모델링, 입력 검증, XSS 방어, 레이트 리밋. 다음 글 [방명록을 만들며 배우는 백엔드](/posts/guestbook-backend)에서 그 과정을 정리했고, 완성본은 [방명록 페이지](/guestbook)에서 직접 써볼 수 있습니다.
