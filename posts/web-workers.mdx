자바스크립트는 싱글 스레드입니다. UI 렌더링, 이벤트 처리, 여러분의 코드가 **모두 하나의 메인 스레드**에서 돕니다. 그래서 무거운 계산을 동기적으로 돌리면 그동안 화면이 통째로 얼어붙습니다. 버튼도 안 눌리고, 애니메이션도 멈추고, 스크롤도 안 되죠.

**Web Worker**는 이 문제의 정공법입니다. 계산을 **별도 스레드**로 넘겨, 메인 스레드는 UI에만 집중하게 합니다.

## 왜 UI가 얼어붙는가

브라우저의 메인 스레드는 한 번에 하나의 작업만 처리합니다. 이벤트 루프가 큐에서 작업을 꺼내 실행하고, 끝나야 다음으로 넘어가죠. 소수 세기 같은 계산이 1초 걸린다면, 그 1초 동안 이벤트 루프는 **다른 어떤 것도** 처리하지 못합니다. 클릭 이벤트도, 리렌더도, 애니메이션 프레임도 전부 뒤에서 밀립니다.

```js
// 이 함수가 도는 동안 페이지는 완전히 멈춘다
function countPrimes(n) {
  let count = 0;
  for (let i = 2; i < n; i++) {
    if (isPrime(i)) count++;
  }
  return count;
}
```

`async`/`await`를 쓴다고 해결되지 않습니다. 비동기는 **기다리는** 작업(네트워크 등)엔 유효하지만, 위처럼 CPU를 실제로 태우는 계산은 결국 메인 스레드를 점유하니까요.

## Web Worker의 기본형

워커는 별도 파일의 스크립트를 **다른 스레드**에서 실행합니다. 메인 스레드와는 오직 **메시지**로만 소통합니다.

```js
// worker.js
self.onmessage = (e) => {
  const result = countPrimes(e.data); // 무거운 계산
  self.postMessage(result); // 결과를 메인으로 전송
};
```

```js
// main.js
const worker = new Worker("./worker.js");

worker.postMessage(1_000_000); // 계산 요청
worker.onmessage = (e) => {
  console.log("결과:", e.data); // 계산이 끝나면 여기로
};
// 이 사이에도 메인 스레드는 멀쩡히 UI를 처리한다
```

`postMessage`로 보내고 `onmessage`로 받습니다. 이게 전부입니다. 계산이 워커 스레드에서 도는 동안 메인 스레드는 자유롭습니다.

## 메모리를 공유하지 않는다는 규칙

워커가 안전한 이유이자 제약이 여기 있습니다. 워커는 메인 스레드와 **메모리를 공유하지 않습니다.** `postMessage`로 주고받는 데이터는 **복사**됩니다(구조화된 복제, structured clone). 그래서 경쟁 상태나 데드락 같은 전통적 멀티스레딩 골칫거리가 없습니다.

대신 두 가지를 기억해야 합니다.

- **DOM에 접근할 수 없다.** 워커 안에서 `document`, `window`는 없습니다. 순수 계산만 합니다.
- **큰 데이터는 복사 비용이 든다.** 수십 MB를 넘기면 복제 자체가 부담입니다. 이럴 땐 소유권을 넘겨 복사를 없애는 **Transferable**을 씁니다.

```js
// ArrayBuffer의 소유권을 워커로 '이전' — 복사 없이 넘어감(대신 메인에선 못 씀)
worker.postMessage(buffer, [buffer]);
```

## React에서 쓸 때

컴포넌트에서는 워커를 `useEffect`에서 만들고 정리하는 게 정석입니다. 렌더마다 새로 만들지 않도록 `ref`에 담아 두고, 언마운트 때 `terminate`합니다.

```jsx
function usePrimeWorker() {
  const workerRef = useRef(null);

  useEffect(() => {
    workerRef.current = new Worker(
      new URL("./prime.worker.js", import.meta.url),
    );
    return () => workerRef.current?.terminate(); // 정리 필수
  }, []);

  return workerRef;
}
```

`new URL("./prime.worker.js", import.meta.url)` 패턴은 webpack·Vite 같은 번들러가 워커 파일을 알아서 처리하도록 하는 표준 관용구입니다. (위 데모는 별도 파일 없이 `Blob`으로 워커를 만들었는데, 그것도 같은 원리입니다.)

## 언제 쓰고, 언제 안 쓰나

워커는 공짜가 아닙니다. 생성 비용과 메시지 왕복(직렬화) 비용이 있죠. 그래서 **정말 무거운 CPU 작업**에만 값을 합니다.

- 잘 맞는 경우: 이미지·비디오 처리, 대용량 데이터 파싱/정렬, 암호화, 물리 시뮬레이션, 구문 분석
- 안 맞는 경우: 그냥 네트워크 대기(그건 `async`로 충분), 자잘한 계산(왕복 비용이 더 큼)

여러 작업을 자주 넘긴다면 워커를 매번 만들지 말고 **워커 풀**을 두고 재사용하는 게 좋습니다.

핵심은 하나입니다. **메인 스레드는 UI를 위해 비워 둔다.** 사용자가 체감하는 "버벅임"의 상당수는 메인 스레드를 오래 붙잡는 작업에서 옵니다. 무거운 계산을 워커로 옮기는 것만으로 앱이 살아나죠. 다음 글에서는 포인터 이벤트로 [드래그 앤 드롭](/posts/drag-and-drop)을 직접 구현해 봅니다.
