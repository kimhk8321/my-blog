목록을 렌더할 때 key를 안 넣으면 경고가 뜨니까, 습관처럼 `key={index}`를 넣곤 합니다. 대부분은 문제없이 동작하다가, 어느 날 항목을 맨 앞에 추가했더니 **입력해 둔 값이 다른 항목으로 옮겨 가는** 버그를 만납니다. 이번 글은 이 현상이 왜 생기는지, React가 화면을 비교하는 방식부터 정리합니다.

## 재조정: 이전 화면과 새 화면을 비교하기

state가 바뀌면 컴포넌트가 다시 실행되고 새 화면(React 요소 트리)이 만들어집니다. React는 이 **새 트리를 이전 트리와 비교해서 바뀐 부분만** 실제 DOM에 반영합니다. 이 비교 과정을 **재조정(Reconciliation)** 이라고 합니다.

두 트리를 완벽하게 비교하는 알고리즘은 요소가 n개일 때 대략 n³번의 계산이 필요해서, 화면이 조금만 커져도 너무 느립니다. 그래서 React는 **두 가지 가정**을 두고 n번 정도로 비교를 끝냅니다.

1. **타입이 다르면 완전히 다른 트리다.** 비교하지 않고 통째로 버리고 새로 만든다.
2. **목록에서는 key로 같은 항목인지 판단한다.** key가 같으면 같은 항목으로 본다.

이 두 규칙이 key 문제의 전부입니다.

## state는 트리의 위치에 붙는다

먼저 알아야 할 사실이 하나 있습니다. **state는 컴포넌트 함수가 아니라, 화면 트리의 "그 자리"에 붙어 있습니다.**

```jsx
function App({ isAdmin }) {
  return isAdmin ? <Counter /> : <Counter />;
}
```

`isAdmin`이 바뀌어도 두 경우 모두 **같은 자리에 같은 타입(`Counter`)** 이 있으니, React는 같은 컴포넌트로 보고 **state를 그대로 유지**합니다.

```jsx
function App({ isAdmin }) {
  return isAdmin ? <AdminCounter /> : <Counter />;
}
```

이번에는 같은 자리지만 **타입이 다릅니다.** 1번 규칙에 따라 이전 컴포넌트를 버리고 새로 만들기 때문에 **state가 초기화**됩니다. `<div>`가 `<section>`으로 바뀌는 것도 마찬가지로, 그 아래 전체가 새로 만들어집니다.

## 목록에서는 key로 짝을 짓는다

목록은 항목이 추가·삭제·정렬되면서 자리가 바뀝니다. 그래서 React는 목록에서는 자리 대신 **key로 이전 항목과 새 항목을 짝짓습니다.** key를 안 주면 index가 key 역할을 합니다.

과일 목록 맨 앞에 "포도"를 추가하는 상황을 봅시다. 각 항목에는 수량을 입력하는 칸(state)이 있습니다.

```js
const before = ["사과", "바나나"];
const after = ["포도", "사과", "바나나"];   // 맨 앞에 추가

function matchByIndex(prev, next) {
  return next.map((item, i) => `${item}: ${i < prev.length ? `${prev[i]}의 상태` : "새 상태"}`);
}

function matchByKey(prev, next) {
  return next.map((item) => `${item}: ${prev.includes(item) ? `${item}의 상태` : "새 상태"}`);
}

console.log(matchByIndex(before, after).join(" / ")); // 포도: 사과의 상태 / 사과: 바나나의 상태 / 바나나: 새 상태
console.log(matchByKey(before, after).join(" / ")); // 포도: 새 상태 / 사과: 사과의 상태 / 바나나: 바나나의 상태
```

### index를 key로 쓰면

| 새 목록 | key | React가 짝지은 이전 항목 | 결과 |
| --- | --- | --- | --- |
| 포도 | 0 | key 0 = 사과 | **포도 칸에 사과의 입력값** |
| 사과 | 1 | key 1 = 바나나 | **사과 칸에 바나나의 입력값** |
| 바나나 | 2 | 없음 | 바나나는 새 칸(입력값 사라짐) |

React 입장에서는 "key 0, 1은 그대로 있고 key 2가 새로 생겼다"로 보입니다. 그래서 **글자(props)는 새 데이터로 바뀌는데 입력칸의 state는 자리에 남아서**, 입력값이 한 칸씩 밀린 것처럼 보입니다. 사용자가 사과에 3개를 입력해 뒀다면, 그 3이 포도 옆에 나타납니다.

### 고유 id를 key로 쓰면

| 새 목록 | key | React가 짝지은 이전 항목 | 결과 |
| --- | --- | --- | --- |
| 포도 | grape | 없음 | 새로 만듦 |
| 사과 | apple | key apple = 사과 | 사과의 입력값 유지 |
| 바나나 | banana | key banana = 바나나 | 바나나의 입력값 유지 |

React는 "grape가 새로 생겼고, apple과 banana는 한 칸씩 이동했다"고 정확히 판단합니다. 기존 DOM과 state를 그대로 옮기고 새 항목만 만들기 때문에, 입력값도 제자리에 있고 DOM 작업도 최소로 끝납니다.

```jsx
{fruits.map((fruit) => (
  <FruitRow key={fruit.id} fruit={fruit} />
))}
```

## index key가 괜찮은 경우

index를 key로 써도 되는 조건은 세 가지가 **모두** 맞을 때입니다.

- 목록이 바뀌지 않는다(추가·삭제·정렬 없음).
- 항목에 state나 입력칸 같은 **비제어 상태**가 없다.
- 항목에 고유 id가 없다.

반대로 항목에 입력칸, 체크박스, 펼침 상태, 애니메이션이 있으면서 순서가 바뀔 수 있으면 반드시 고유 id를 씁니다.

## 하지 말아야 할 key

```jsx
<Item key={Math.random()} />   // 렌더마다 key가 바뀜
```

key가 매번 바뀌면 React는 **매 렌더마다 전부 새 항목**으로 보고, 모든 항목을 버리고 새로 만듭니다. state가 초기화되고, 입력 중이던 포커스가 사라지고, 성능도 나빠집니다. key는 **같은 데이터에 대해 항상 같아야** 합니다. 데이터에 id가 없으면 데이터를 만들 때(서버나 추가 시점) id를 붙여 둡니다.

key는 **형제 사이에서만** 고유하면 됩니다. 다른 목록과 겹쳐도 상관없습니다.

## key로 state를 일부러 초기화하기

key의 성질을 거꾸로 쓰면, 목록이 아니어도 **컴포넌트를 새로 만들게** 할 수 있습니다.

```jsx
<ProfileEditor key={userId} userId={userId} />
```

다른 사용자를 선택하면 `userId`가 바뀌고, key가 바뀌니 React는 이전 `ProfileEditor`를 버리고 새로 만듭니다. 이전 사용자의 입력값이 남지 않습니다. `useEffect`로 "userId가 바뀌면 입력값을 초기화"하는 코드를 쓰는 것보다 간단하고, 초기화되기 전의 화면이 잠깐 보이는 문제도 없습니다.

## 정리

| 상황 | React의 판단 | state |
| --- | --- | --- |
| 같은 자리, 같은 타입 | 같은 컴포넌트 | 유지 |
| 같은 자리, 다른 타입 | 다른 컴포넌트 | 초기화 |
| 목록에서 같은 key | 같은 항목 (자리가 바뀌면 이동) | 유지 |
| 목록에서 새 key | 새 항목 | 새로 만듦 |
| key를 바꿈 | 다른 컴포넌트 | 초기화 |

> "React는 재조정할 때 타입이 다르면 다른 트리로 보고 새로 만들고, 목록에서는 key로 이전 항목과 새 항목을 짝짓습니다. state는 컴포넌트가 아니라 트리의 그 자리에 붙어 있어서, index를 key로 쓰면 항목을 맨 앞에 추가하거나 순서를 바꿀 때 데이터는 바뀌는데 state는 원래 자리에 남아 입력값이 다른 항목으로 옮겨 간 것처럼 보입니다. 그래서 순서가 바뀔 수 있는 목록은 데이터의 고유 id를 key로 쓰고, 반대로 key를 바꾸면 컴포넌트를 의도적으로 초기화할 수 있습니다."
