[인덱스는 미리 정렬해둔 자료구조](/posts/query-performance)라고 정리했었죠. InnoDB에서는 여기에 한 가지 특징이 더해집니다 — **모든 것이 기본키를 중심으로 돕니다.**

## 클러스터링 인덱스 — 데이터가 곧 인덱스

InnoDB에서 테이블의 **데이터 자체가 기본키 순서로 정렬되어 저장**됩니다. 이걸 클러스터링 인덱스라고 합니다.

즉 기본키 인덱스는 "어디에 있는지 알려주는 표"가 아니라 **데이터 그 자체**입니다. 기본키로 찾으면 인덱스를 타고 내려가는 순간 데이터에 도착하죠. 그래서 **기본키 조회가 가장 빠릅니다.**

기본키를 지정하지 않으면 MySQL이 유니크 키나 내부 키를 대신 씁니다. 즉 **클러스터링 인덱스는 없을 수가 없습니다.**

## 세컨더리 인덱스는 기본키를 가리킨다

그 외의 인덱스(세컨더리 인덱스)는 값과 함께 **기본키를 저장**합니다. 그래서 조회가 두 단계로 일어납니다.

```
email 인덱스에서 찾기 → 기본키를 얻음 → 클러스터링 인덱스에서 실제 행 읽기
```

이 두 번째 단계를 이해하면 여러 가지가 설명됩니다.

- **기본키가 크면 모든 세컨더리 인덱스가 커집니다.** 전부 기본키를 품고 있으니까요. 그래서 긴 문자열을 기본키로 쓰지 말라고 하는 겁니다.
- 세컨더리 인덱스로 찾은 뒤 **행을 읽으러 한 번 더 가는 비용**이 있습니다. 이걸 없애는 게 다음에 볼 커버링 인덱스죠.

## 커버링 인덱스 — 데이터까지 안 가도 될 때

쿼리에 필요한 컬럼이 **인덱스 안에 전부 들어 있으면**, 실제 행을 읽으러 갈 필요가 없습니다.

```sql
-- (email, name) 인덱스가 있다면
SELECT name FROM users WHERE email = ?;   -- 인덱스만으로 해결
SELECT phone FROM users WHERE email = ?;  -- phone 때문에 행을 읽으러 가야 함
```

실행 계획에 **`Using index`** 가 뜨면 커버링 인덱스가 동작한 것입니다. 효과가 꽤 커서, 자주 쓰는 조회에 맞춰 인덱스에 컬럼을 하나 더 넣기도 합니다.

> 이래서 [`SELECT *`를 피하라](/posts/query-performance)는 조언이 단순히 "네트워크 절약"만은 아닙니다. 필요 없는 컬럼 하나 때문에 커버링이 깨지거든요.

## 다중 컬럼 인덱스는 순서가 전부다

`(a, b, c)` 인덱스는 **a로 먼저 정렬하고, 같으면 b로, 또 같으면 c로** 정렬된 것입니다. 전화번호부가 성 → 이름 순으로 정렬된 것과 같죠.

그래서 **왼쪽부터 이어져야** 쓸 수 있습니다.

| 조건 | 인덱스 사용 |
| --- | --- |
| `WHERE a = 1` | 사용 |
| `WHERE a = 1 AND b = 2` | 사용 |
| `WHERE a = 1 AND c = 3` | a까지만 사용 |
| `WHERE b = 2` | **사용 못 함** |

성을 모른 채 이름만으로 전화번호부를 뒤질 수 없는 것과 같습니다.

그리고 **범위 조건이 나오면 그 뒤로는 정렬이 깨집니다.**

```sql
-- (a, b) 인덱스: a가 범위라 b는 정렬 순서를 보장하지 못함
WHERE a > 10 AND b = 5
```

그래서 **동등 조건을 앞에, 범위 조건을 뒤에** 두는 게 인덱스 설계의 기본입니다.

## 인덱스를 못 쓰게 만드는 것들

인덱스를 걸어놨는데 안 타는 흔한 이유들입니다.

```sql
-- 컬럼을 가공하면 못 쓴다 (인덱스는 원래 값으로 정렬돼 있으니까)
WHERE YEAR(created_at) = 2026        -- 나쁨
WHERE created_at >= '2026-01-01'     -- 좋음

-- 타입이 다르면 변환이 일어나 못 쓸 수 있다
WHERE phone = 01012345678            -- 문자열 컬럼에 숫자를 넣음

-- 앞에 와일드카드가 있으면 못 쓴다
WHERE name LIKE '%김'                 -- 나쁨
WHERE name LIKE '김%'                 -- 좋음
```

공통점은 **"정렬된 순서를 활용할 수 없게 만든다"** 는 것입니다. 인덱스가 정렬이라는 걸 기억하면 대부분 예측할 수 있어요.

## 카디널리티 — 값이 다양해야 쓸모 있다

값의 종류가 적은 컬럼(성별, 상태값)은 인덱스를 걸어도 효과가 적습니다. 절반을 걸러내 봐야 여전히 절반이 남으니, 옵티마이저가 **차라리 전체를 훑는 편이 낫다**고 판단하기도 하죠.

MySQL은 통계 정보를 보고 이 판단을 합니다. 그래서 **인덱스가 있어도 안 탈 수 있고, 그게 맞는 판단일 수 있습니다.**

InnoDB 인덱스의 핵심은 "**데이터가 기본키 순으로 정렬돼 있고, 나머지 인덱스는 기본키를 가리킨다**"입니다. 여기서 기본키 크기의 중요성, 커버링 인덱스의 이점, 다중 컬럼 순서 규칙이 전부 따라 나오죠. 다음 편은 [트랜잭션과 잠금](/posts/real-mysql-lock)입니다.
