[쿼리 성능 편](/posts/query-performance)에서 "추측하지 말고 `EXPLAIN`으로 확인하라"고 썼는데, 정작 결과를 읽는 법은 안 다뤘습니다. 이번 편이 그 이야기입니다.

## 옵티마이저는 비용을 추정한다

먼저 알아둘 게 있습니다. MySQL은 여러 실행 방법 중 **비용이 가장 적을 것 같은 것**을 고릅니다. "같을 것 같은"이 아니라 **추정**입니다.

추정의 근거는 **통계 정보**(각 인덱스의 값이 얼마나 다양한지 등)인데, 이게 실제와 어긋나면 **잘못된 계획**을 고릅니다. "인덱스가 있는데 왜 안 타지?"의 상당수가 여기서 나옵니다.

## 무엇부터 볼 것인가

`EXPLAIN` 결과에서 실무상 중요한 건 네 가지입니다.

### 1. type — 어떻게 접근하는가

가장 중요한 항목입니다. 좋은 것부터 나열하면:

| type | 뜻 |
| --- | --- |
| `const` / `eq_ref` | 기본키·유니크로 **한 건**만 |
| `ref` | 인덱스로 **여러 건** |
| `range` | 인덱스 **범위** 스캔 |
| `index` | 인덱스 **전체** 훑기 |
| `ALL` | **테이블 전체** 훑기(풀 스캔) |

**`ALL`이 보이면 일단 의심**합니다. 다만 작은 테이블이면 풀 스캔이 더 빠를 수도 있어서, 무조건 나쁜 건 아닙니다.

`index`도 주의해야 합니다. 이름 때문에 좋아 보이지만 **인덱스를 처음부터 끝까지 읽는 것**이라 풀 스캔과 별 차이 없을 때가 많습니다.

### 2. key — 어떤 인덱스를 썼나

실제로 선택된 인덱스입니다. `possible_keys`에는 있는데 `key`가 `NULL`이면, **후보는 있었지만 옵티마이저가 안 쓰기로 했다**는 뜻이죠. 이때 통계나 조건 형태를 의심해 봅니다.

### 3. rows — 몇 건을 읽을 것으로 보는가

**추정치**입니다. 실제 결과 건수가 아니라 **읽어야 할 것으로 예상되는 행 수**죠. 최종 결과가 10건인데 `rows`가 100만이면, 100만 건을 훑어 10건을 골라낸다는 뜻입니다.

실제 값을 보려면 **`EXPLAIN ANALYZE`** 를 씁니다. 쿼리를 실제로 실행하고 **추정 대비 실제**를 보여줘서, 통계가 틀어졌는지 바로 알 수 있습니다.

### 4. Extra — 진짜 정보는 여기 있다

| 표시 | 의미 |
| --- | --- |
| `Using index` | **커버링 인덱스** — 데이터를 안 읽음. 좋음 |
| `Using where` | 읽어온 뒤 걸러냄 |
| `Using filesort` | **별도 정렬 작업**이 필요 |
| `Using temporary` | **임시 테이블**을 만듦 |

뒤의 둘이 성능 문제의 단골입니다.

## Using filesort — 인덱스로 정렬을 못 할 때

이름이 오해를 부르는데, **파일에 쓴다는 뜻이 아닙니다.** "인덱스 순서를 그대로 쓸 수 없어서 **따로 정렬 작업을 한다**"는 뜻이고, 대개 메모리에서 처리됩니다(크면 디스크를 씁니다).

[인덱스는 정렬된 자료구조](/posts/real-mysql-index)라, `ORDER BY`가 인덱스 순서와 맞으면 **정렬을 아예 안 해도** 됩니다.

```sql
-- (user_id, created_at) 인덱스가 있을 때
WHERE user_id = 1 ORDER BY created_at DESC   -- 인덱스 순서 그대로 → 정렬 없음
WHERE user_id = 1 ORDER BY title             -- 인덱스로 안 됨 → filesort
```

특히 **`ORDER BY` + `LIMIT` 페이징**에서 차이가 큽니다. 정렬이 인덱스로 해결되면 앞의 몇 건만 읽고 멈출 수 있지만, filesort면 **조건에 맞는 걸 다 읽어 정렬한 뒤** 잘라내야 하거든요.

## Using temporary — 중간 결과를 쌓을 때

`GROUP BY`나 `DISTINCT`, 복잡한 조인에서 중간 결과를 담을 **임시 테이블**을 만듭니다. 메모리에 안 들어가면 디스크로 내려가고, 그러면 급격히 느려집니다.

`GROUP BY` 컬럼이 인덱스 순서와 맞으면 임시 테이블 없이 처리할 수 있습니다.

## 페이징이 뒤로 갈수록 느려지는 이유

실행 계획을 읽을 줄 알면 이 현상이 설명됩니다.

```sql
SELECT * FROM posts ORDER BY id DESC LIMIT 20 OFFSET 100000;
```

`OFFSET`은 **건너뛸 행을 실제로 읽고 버립니다.** 10만 건을 읽어 버리고 20건을 반환하죠. 뒤로 갈수록 선형으로 느려집니다.

그래서 **커서 기반 페이징**을 씁니다.

```sql
SELECT * FROM posts WHERE id < ? ORDER BY id DESC LIMIT 20;
```

마지막으로 본 `id`부터 이어가면 **몇 페이지든 같은 속도**입니다. [무한 스크롤](/posts/infinite-scroll)처럼 "다음"만 필요한 UI에 특히 잘 맞죠.

---

실행 계획 읽기의 요령은 "**`type`으로 접근 방식을, `Extra`로 숨은 작업을 본다**"입니다. 그리고 `rows`는 추정이라는 걸 잊지 않는 것 — 추정이 틀리면 계획도 틀리니까요. 마지막 편은 [쿼리 작성과 최적화](/posts/real-mysql-optimization)입니다.
