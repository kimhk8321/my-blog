클라이언트가 주문 생성 요청을 보낸 뒤 응답을 받지 못했습니다. 서버가 처리하지 않은 것인지, 처리했지만 응답만 사라진 것인지 알 수 없습니다. 새 요청을 보내면 주문이 중복될 수 있고, 포기하면 사용자의 주문이 사라질 수 있습니다.

Idempotency Key는 두 요청이 **같은 논리적 작업의 재시도**라는 사실을 서버에 알려줍니다.

키가 없으면 서버는 다섯 요청을 서로 다른 주문으로 봅니다. 같은 키를 보내면 첫 요청만 처리하고 나머지는 저장해 둔 결과를 돌려줍니다.

## 키는 작업마다 한 번 만든다

클라이언트는 버튼을 누르는 시점에 키를 만들고, 같은 작업을 재시도할 때 재사용합니다.

```ts
const idempotencyKey = crypto.randomUUID();

async function createOrder(input: OrderInput) {
  return fetch("/api/orders", {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "Idempotency-Key": idempotencyKey,
    },
    body: JSON.stringify(input),
  });
}
```

렌더할 때마다 키를 새로 만들면 재시도가 새 작업처럼 보입니다. 한 번의 제출 흐름 동안 같은 키를 유지해야 합니다. 사용자가 내용까지 바꿔 새 주문을 시작했다면 새 키를 만듭니다.

## 서버가 기억할 상태

```ts
type IdempotencyRecord =
  | { status: "processing"; requestHash: string }
  | {
      status: "completed";
      requestHash: string;
      statusCode: number;
      body: unknown;
    };
```

- `processing`: 같은 키의 요청이 현재 처리 중임을 알립니다.
- `completed`: 이미 처리한 응답을 그대로 재현합니다.
- `requestHash`: 같은 키에 다른 본문을 보내는 오용을 막습니다.

같은 키인데 주문 금액이 다르면 이전 응답을 돌려줘서는 안 됩니다. 요청 본문의 해시를 비교해 `409 Conflict`나 `422 Unprocessable Content`로 거절하는 편이 안전합니다.

## get-then-set의 경쟁 상태

```ts
const cached = await redis.get(key);
if (cached) return cached;

const result = await createOrder(input);
await redis.set(key, result);
return result;
```

두 요청이 동시에 `get`을 통과하면 둘 다 주문을 만듭니다. 확인과 선점이 분리돼 있기 때문입니다. Redis의 `SET NX`처럼 **없을 때만 쓰는 원자 연산**으로 처리 권한을 가져와야 합니다.

```ts
const acquired = await redis.set(
  `idempotency:${key}`,
  { status: "processing", requestHash },
  { nx: true, ex: 60 },
);

if (!acquired) {
  return readExistingResult(key, requestHash);
}
```

첫 요청만 처리합니다. 나머지는 진행 중이면 잠시 후 같은 키로 재시도하게 하거나, 짧게 기다렸다 완료된 응답을 읽을 수 있습니다.

## 처리와 결과 저장 사이의 틈

```text
Redis processing 저장 → DB 주문 생성 → 서버 종료 → Redis completed 기록 실패
```

재시도한 요청은 `processing`만 보지만 주문은 이미 존재합니다. 이를 막으려면 DB에 idempotency key를 UNIQUE 컬럼으로 저장하고 주문 생성과 함께 커밋합니다.

```sql
CREATE UNIQUE INDEX orders_idempotency_key_unique
ON orders (idempotency_key);
```

Redis는 빠른 응답 캐시로 쓰고, 최종 중복 판단은 데이터가 실제로 저장되는 DB에 맡기는 구조입니다. 돈이나 재고처럼 정확성이 중요한 작업일수록 두 기록을 같은 트랜잭션 경계에 둬야 합니다.

## TTL과 실패 응답

키를 영원히 보관하면 저장소가 계속 커집니다. 너무 빨리 지우면 사용자가 늦게 재시도했을 때 중복 작업이 생깁니다. TTL은 클라이언트의 최대 재시도 시간, 외부 서비스의 재전송 정책, 사용자가 결과를 확인하는 시간을 고려해 정합니다.

입력 검증처럼 확정적인 4xx는 같은 요청으로 결과가 바뀌지 않으므로 저장할 수 있습니다. 일시적인 500 오류를 완료 결과로 오래 저장하면 복구 뒤에도 실패만 재생합니다. 보통 **업무 처리가 확정된 결과**를 저장하고 재시도 가능한 장애는 짧게 만료합니다.

---

Idempotency Key의 핵심은 요청을 차단하는 게 아니라 여러 번 도착한 요청을 **하나의 작업으로 식별하고 같은 결과로 수렴시키는 것**입니다. Redis의 원자적 선점은 입구를 지키고, DB의 UNIQUE 제약과 트랜잭션은 처리와 기록 사이의 틈을 막습니다. 다음 글에서는 요청이 중복된 게 아니라 데이터가 그사이 바뀐 경우를 다룹니다.
