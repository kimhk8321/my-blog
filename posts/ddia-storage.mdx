[InnoDB가 B-Tree를 쓴다](/posts/real-mysql-index)는 건 봤는데, **왜 B-Tree인가**, 그리고 **다른 선택지는 없나**를 다루는 게 DDIA 3장입니다. 여기서 완전히 다른 접근을 만나게 됩니다.

## 가장 단순한 DB — 그냥 덧붙이기

책은 두 줄짜리 DB로 시작합니다. 쓰기는 파일 끝에 덧붙이고, 읽기는 파일 전체를 훑어 마지막 값을 찾는 것.

- **쓰기는 아주 빠릅니다** — 순차 쓰기만 하니까요
- **읽기는 최악입니다** — O(n)

이 출발점이 좋았습니다. **쓰기를 빠르게 하는 가장 단순한 방법은 "고치지 말고 덧붙이는 것"** 이라는 걸 먼저 보여주거든요.

여기에 인덱스를 붙이면 읽기가 해결되고, 그게 아래 두 갈래로 발전합니다.

## LSM 트리 — 덧붙이고 나중에 정리

**로그 구조 병합 트리**의 흐름은 이렇습니다.

1. 쓰기는 **메모리의 정렬된 구조**(멤테이블)에 넣는다
2. 일정 크기가 되면 **디스크에 정렬된 파일**(SSTable)로 통째로 내린다
3. 파일이 쌓이면 **백그라운드에서 병합·정리**한다(컴팩션)

핵심은 **디스크에 쓸 때 항상 순차 쓰기**라는 점입니다. 이미 있는 자리를 고치지 않고 새 파일을 만들죠.

읽기는 최신 파일부터 차례로 뒤집니다. 없는 키를 찾을 때 모든 파일을 뒤져야 해서 느린데, 이걸 **블룸 필터**로 거릅니다("이 파일에 없는 건 확실하다"를 빠르게 판단).

## B-Tree — 제자리에서 고치기

반대로 B-Tree는 **정해진 자리를 찾아가 덮어씁니다.**

- 페이지 단위로 나뉘고, 트리를 타고 내려가 해당 페이지를 수정
- 페이지가 꽉 차면 쪼개고, 트리 깊이를 유지

그런데 제자리 갱신에는 위험이 있습니다. **페이지를 쪼개는 도중에 죽으면** 트리가 망가지죠. 그래서 [리두 로그 같은 WAL](/posts/real-mysql-architecture)이 필요합니다 — **먼저 로그에 적고 실제 페이지를 고치는** 그 구조가 여기서 나옵니다.

## 무엇을 맞바꾸는가

| | LSM 트리 | B-Tree |
| --- | --- | --- |
| 쓰기 | 빠름(순차) | 느림(임의 + WAL) |
| 읽기 | 느릴 수 있음(여러 파일) | 예측 가능 |
| 공간 | 압축률 좋음 | 파편화로 낭비 |
| 특징 | 컴팩션이 배경에서 돌음 | 키가 한 곳에만 존재 |

**쓰기 증폭**이라는 개념이 좋았습니다. 한 번의 논리적 쓰기가 디스크에는 여러 번 쓰이는 현상이죠. B-Tree는 WAL과 페이지를 둘 다 쓰고, LSM은 컴팩션에서 반복해서 다시 씁니다.

LSM의 함정은 **컴팩션이 사용자 요청과 디스크 대역폭을 두고 경쟁**한다는 점입니다. 쓰기가 몰리면 컴팩션이 밀리고, 밀리면 읽어야 할 파일이 늘어 읽기가 느려지죠. 반면 B-Tree는 **한 키가 한 곳에만 있어서** 잠금으로 트랜잭션을 구현하기가 자연스럽습니다.

> 그래서 [트랜잭션이 중요한 RDB는 B-Tree](/posts/real-mysql-index), 쓰기가 아주 많은 시계열·로그 저장소는 LSM 쪽을 택하는 경향이 있습니다. Cassandra, RocksDB, LevelDB가 LSM이고요.

## 저장소도 캐시와 같은 고민을 한다

읽다 보니 [서버 캐싱](/posts/server-caching)에서 본 것과 같은 긴장이 반복됩니다 — **읽기를 빠르게 할 것인가, 쓰기를 빠르게 할 것인가.** 어느 쪽을 택하든 다른 쪽이 비싸지고, 중간에서 균형을 잡을 뿐이죠. [인기 글 랭킹을 만들며](/posts/blog-toc-popular) "쓸 때 정렬해 두자"고 정한 것도 같은 선택이었습니다.

## OLTP와 OLAP — 아예 다른 일

3장 후반은 갈림길을 하나 더 보여줍니다.

- **OLTP** — 사용자 요청 처리. **적은 행을 키로** 찾고, 쓰기가 잦음
- **OLAP** — 분석. **아주 많은 행을 훑어** 집계하고, 읽기 위주

둘은 접근 패턴이 반대라 같은 DB로 다 하기 어렵습니다. 그래서 분석용 데이터를 따로 모으는 **데이터 웨어하우스**가 생겼죠.

여기서 **열 지향 저장소**가 나옵니다. 행 단위가 아니라 **컬럼 단위로 모아** 저장하는 방식인데,

- 집계에 필요한 **몇 개 컬럼만** 읽으면 됩니다(나머지는 디스크에서 안 읽음)
- 같은 컬럼은 값이 비슷해 **압축이 아주 잘 됩니다**

"어떻게 저장하느냐"가 "무엇을 잘하느냐"를 정한다는 게 이 장 전체의 메시지 같았습니다.
