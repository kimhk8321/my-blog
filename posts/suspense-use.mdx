데이터를 불러오는 컴포넌트는 늘 같은 삼종 세트를 달고 다닙니다.

```jsx
const [data, setData] = useState(null);
const [loading, setLoading] = useState(true);
const [error, setError] = useState(null);

if (loading) return <Spinner />;
if (error) return <Error />;
return <Profile data={data} />;
```

컴포넌트마다 이 분기가 반복됩니다. 로딩·에러 처리 코드가 정작 보여주려는 UI보다 길어지기 일쑤죠. **Suspense**는 이 구조를 뒤집습니다. "기다리는 상태"를 컴포넌트가 스스로 처리하는 대신, **부모가 선언적으로** 감싸게 합니다.

버튼을 누르면 데이터가 도착할 때까지 "로딩 중…"이 뜹니다. 그런데 이 로딩 표시는 데이터를 읽는 컴포넌트가 그리는 게 아니라, 그걸 감싼 `<Suspense>`가 대신합니다.

## use() — 프라미스를 그냥 읽는다

React 19의 `use()` 훅은 프라미스를 **동기 코드처럼** 읽게 해줍니다.

```jsx
import { use } from "react";

function Profile({ userPromise }) {
  const user = use(userPromise); // 확정될 때까지 여기서 '멈춤'
  return <h1>{user.name}</h1>;
}
```

`use(promise)`를 만나면, 프라미스가 아직 pending인 동안 React는 이 컴포넌트의 렌더링을 **중단(suspend)** 합니다. 그리고 가장 가까운 `<Suspense>`의 `fallback`을 대신 보여주죠. 프라미스가 확정되면 컴포넌트가 다시 렌더되고, `use`는 그 값을 반환합니다.

`loading`, `error` 같은 상태 변수가 사라진 걸 보세요. 컴포넌트는 "데이터가 있다"는 가정 하에 **성공 경로만** 씁니다.

## Suspense가 경계를 친다

`use`로 중단된 컴포넌트를 받아 주는 게 `<Suspense>`입니다.

```jsx
function Page() {
  const userPromise = fetchUser(); // 프라미스 (아직 안 기다림)

  return (
    <Suspense fallback={<Spinner />}>
      <Profile userPromise={userPromise} />
    </Suspense>
  );
}
```

`Profile`이 중단되면 `Spinner`가, 확정되면 `Profile`이 뜹니다. 로딩 UI의 **위치와 범위**를 `Suspense`의 경계로 선언하는 겁니다. 여러 컴포넌트를 하나의 경계로 묶으면 "다 준비될 때까지 하나의 스피너"가 되고, 각각 감싸면 준비되는 대로 개별로 뜹니다.

## 에러는 Error Boundary로

로딩을 `Suspense`가 맡는다면, 실패는 누가 맡을까요? **Error Boundary**입니다. `use`한 프라미스가 reject되면 그 에러가 위로 던져지고, 가장 가까운 에러 경계가 잡습니다.

```jsx
<ErrorBoundary fallback={<p>불러오기 실패</p>}>
  <Suspense fallback={<Spinner />}>
    <Profile userPromise={userPromise} />
  </Suspense>
</ErrorBoundary>
```

로딩·성공·에러라는 세 갈래가, 이제 **선언적인 경계 두 개**(Suspense, ErrorBoundary)와 **성공만 다루는 컴포넌트**로 깔끔하게 분리됩니다. ([Error Boundary와 Suspense](/posts/modern-react-error-suspense)를 다룬 글이 있으니 함께 보면 좋습니다.)

## use()가 특별한 이유

`use`는 다른 훅들과 규칙이 다릅니다. **조건문·반복문 안에서 호출할 수 있습니다.**

```jsx
function Note({ show, promise }) {
  if (!show) return null;
  const data = use(promise); // 조건부 호출 OK — 다른 훅은 불가능
  return <p>{data}</p>;
}
```

[훅 규칙](/posts/how-react-hooks-work) 글에서 봤듯 보통의 훅은 호출 순서에 의존해서 조건부 호출이 금지됩니다. `use`는 그 제약에서 자유롭게 설계됐습니다. Context를 조건부로 읽는 것도 되죠.

## 주의 — 프라미스는 캐시되어야 한다

한 가지 함정이 있습니다. `use`에 넘기는 프라미스는 **렌더 사이에 안정적**이어야 합니다. 렌더링 도중에 매번 새 프라미스를 만들면, 리렌더마다 새로 요청이 나가고 무한 루프에 빠질 수 있습니다.

```jsx
// 위험 — 렌더마다 새 프라미스
function Bad() {
  const data = use(fetch("/api").then((r) => r.json()));
}
```

그래서 실전에서는 프라미스를 **캐시**하거나(예: React Query, 프레임워크의 데이터 레이어), 이벤트 핸들러에서 만들어 상태에 담아 둡니다. Next.js App Router의 서버 컴포넌트라면 `async` 컴포넌트에서 직접 `await`하는 방식이 더 자연스럽고, `use`는 주로 **클라이언트에서** 서버가 내려준 프라미스를 읽을 때 빛납니다.

---

Suspense의 사고방식은 "각 컴포넌트가 로딩을 처리한다"에서 "**기다림의 경계를 선언한다**"로의 전환입니다. `use`가 그 마지막 퍼즐을 맞추면서, 데이터 로딩 코드가 눈에 띄게 단순해졌죠. 다음 글에서는 접근성의 핵심인 [포커스 관리](/posts/accessible-modal)를 접근 가능한 모달로 구현해 봅니다.
