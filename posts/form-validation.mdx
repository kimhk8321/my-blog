폼 검증은 프론트엔드의 영원한 숙제입니다. 필수값, 이메일 형식, 비밀번호 길이, 서버 중복 확인… 여기에 "언제 에러를 보여줄까"(입력 중? 포커스 벗어날 때? 제출할 때?)까지 얽히면 금세 지저분해집니다. React Hook Form, Formik, Zod가 괜히 인기 있는 게 아니죠.

그런데 그 안의 핵심 아이디어는 생각보다 단순합니다. **규칙을 데이터로 선언하고, 값에 규칙을 적용해 에러를 뽑는 것.** 직접 만들어 보면 라이브러리 선택도, 커스텀도 쉬워집니다.

## 규칙을 함수로 선언하기

검증 규칙 하나는 **"값을 받아 에러 메시지(또는 null)를 반환하는 함수"** 입니다. 이 단순한 계약이 전부의 기반입니다.

```js
// (값) => 에러 문자열 | null
const required = (v) => (!v ? "필수 항목입니다" : null);
const email = (v) => (v && !/^[^@\s]+@[^@\s]+\.[^@\s]+$/.test(v) ? "이메일 형식이 아닙니다" : null);
const minLen = (n) => (v) => (v && v.length < n ? `${n}자 이상이어야 합니다` : null);
```

`minLen`처럼 **인자를 받아 규칙을 반환**하게 하면 재사용성이 확 올라갑니다. 이제 필드마다 규칙을 배열로 나열합니다.

```js
const schema = {
  email: [required, email],
  password: [required, minLen(8)],
};
```

이게 Zod의 `z.string().email()`, Yup의 `.required().min(8)`이 하는 일의 알맹이입니다 — 규칙의 **선언적 조합**.

## 값에 규칙을 적용하기

한 필드를 검증하는 건 규칙들을 순서대로 돌려 **첫 에러**를 찾는 것입니다.

```js
function validateField(field, value) {
  for (const rule of schema[field]) {
    const error = rule(value);
    if (error) return error; // 첫 실패에서 멈춤
  }
  return null; // 전부 통과
}
```

순서가 의미를 갖습니다. `[required, email]`이면 빈 값일 때 "필수"가 먼저 뜨고, 값이 있는데 형식이 틀리면 "형식" 에러가 뜨죠.

## 상태 세 가지 — values / errors / touched

폼의 UX는 값만으로 안 됩니다. **언제 에러를 보여줄지**를 결정하는 `touched`가 핵심입니다.

```jsx
const [values, setValues] = useState({ email: "", password: "" });
const [touched, setTouched] = useState({});

// errors는 values에서 매 렌더 파생 — 별도 상태로 두지 않는다
const errors = {
  email: validateField("email", values.email),
  password: validateField("password", values.password),
};

const isValid = !errors.email && !errors.password;
```

`errors`를 **파생 값**으로 둔 게 포인트입니다. 값이 바뀌면 에러는 자동으로 다시 계산되니, 에러를 별도 state로 관리하며 동기화할 필요가 없습니다. ([폼 유효성의 단일 출처](/posts/react-hook-form)와 통하는 생각입니다.)

에러를 **보여주는** 조건은 `touched && error`입니다.

```jsx
<input
  value={values.email}
  onChange={(e) => setValues((v) => ({ ...v, email: e.target.value }))}
  onBlur={() => setTouched((t) => ({ ...t, email: true }))}
/>
{touched.email && errors.email && <span className="error">{errors.email}</span>}
```

이렇게 하면 "타이핑 시작하자마자 빨간 에러가 뜨는" 짜증나는 UX를 피하고, **포커스를 벗어난 뒤부터** 검증 결과를 보여줍니다. 제출 시엔 모든 필드를 `touched`로 만들어 남은 에러를 전부 드러내죠.

## 비제어 방식과 성능

위는 **제어 컴포넌트** 방식이라 입력마다 리렌더됩니다. 필드가 수십 개면 부담이 되죠. React Hook Form이 인기인 이유가 여기 있습니다 — `ref` 기반 **비제어**로 입력마다 리렌더하지 않고, 검증 시점에만 값을 읽습니다. 트레이드오프는 "값이 항상 state에 있지 않다"는 점이고요. ([리렌더 최적화](/posts/rerender-optimization)에서 다룬 고민과 같은 결입니다.)

## 스키마 검증기와의 연결

`Zod` 같은 스키마 라이브러리는 여기에 **타입 추론**을 얹은 것입니다. 규칙으로 검증하는 동시에, 그 스키마로부터 TypeScript 타입을 뽑아내죠.

```ts
const schema = z.object({ email: z.string().email(), age: z.number().min(0) });
type Form = z.infer<typeof schema>; // { email: string; age: number }
```

런타임 검증과 컴파일타임 타입을 **하나의 선언에서** 얻는 게 스키마 검증기의 진짜 매력입니다.

폼 검증의 뼈대는 "**규칙 = 함수, 스키마 = 규칙의 조합, 에러 = 값에서 파생**"입니다. 여기에 `touched`로 노출 시점만 잘 다루면 대부분의 폼을 직접 다룰 수 있습니다. 다음 글에서는 비동기의 골칫거리인 [AbortController와 경쟁 상태](/posts/abort-controller)로 넘어갑니다.
