[1편](/posts/oauth-oidc-sso)에서 로그인을 위임하는 흐름을 정리했습니다. 데모에서는 로그인 버튼을 누르고 토큰을 받으면 끝나지만, 실제 서비스에서 문제는 대부분 그 뒤에 생깁니다. 토큰이 만료되는 순간 요청 다섯 개가 동시에 실패하고, 한 탭에서 로그아웃했는데 다른 탭은 여전히 로그인 상태이고, 같은 사람이 카카오와 Apple로 각각 가입합니다.

이 글은 계정·인증에서 자주 만나는 예외 상황을 순서대로 정리합니다.

## 1. 토큰을 어디에 둘까

| 위치 | 장점 | 위험 |
| --- | --- | --- |
| localStorage | 새로고침해도 유지, 구현이 쉬움 | 같은 출처에서 실행된 스크립트가 읽을 수 있다(XSS) |
| 메모리(변수) | 스크립트가 꺼내 가기 어렵다 | 새로고침하면 사라진다 |
| httpOnly 쿠키 | 스크립트가 아예 읽을 수 없다 | 자동으로 전송되므로 CSRF에 대비해야 한다 |

많이 쓰는 조합은 **Access Token은 메모리, Refresh Token은 httpOnly·Secure·SameSite 쿠키**입니다. 새로고침하면 메모리의 Access Token은 사라지지만, 쿠키로 새 Access Token을 받아 이어 갑니다.

한 가지 오해는 정리해 둡니다. httpOnly 쿠키는 XSS로 **토큰을 훔쳐 가는 것**을 막을 뿐, XSS 자체를 막지는 못합니다. 페이지에서 공격 스크립트가 돌면 그 스크립트는 사용자의 쿠키를 실어 API를 직접 호출할 수 있습니다. 저장 위치는 피해 범위를 줄이는 장치이고, XSS 방어는 따로 해야 합니다. 쿠키를 쓸 때는 `SameSite=Lax` 이상과 CSRF 토큰으로 다른 사이트에서 보낸 요청을 막습니다. 자세한 내용은 [웹 보안 — XSS, CSRF, CORS](/posts/web-security)와 [브라우저 저장소](/posts/browser-storage)에 있습니다.

## 2. 401을 받으면 — 동시 갱신 경쟁 상태

Access Token이 만료되면 API가 401을 돌려줍니다. 기본 처리는 간단합니다. Refresh Token으로 새 Access Token을 받고, 실패했던 요청을 한 번 다시 보냅니다.

문제는 화면이 뜰 때 요청 여러 개가 **동시에** 401을 받을 때입니다.

```text
요청 A ─ 401 ─ 갱신 요청 ①(refresh-1 사용) ─ 성공: access-2, refresh-2 발급
요청 B ─ 401 ─ 갱신 요청 ②(refresh-1 사용) ─ 실패: refresh-1은 이미 폐기됨
                                              → 사용자가 갑자기 로그아웃된다
```

Refresh Token을 쓸 때마다 새 것으로 바꾸는 **회전** 방식에서는, 이미 쓴 Refresh Token이 다시 오면 서버가 탈취를 의심해 그 계열의 토큰을 모두 폐기하기도 합니다(RFC 9700). 동시 갱신 하나가 사용자를 로그아웃시키는 이유입니다.

해결은 **진행 중인 갱신을 하나로 모으는 것**입니다. 첫 요청이 갱신을 시작하면, 나머지 요청은 새로 갱신하지 않고 같은 Promise를 기다립니다.

```ts
let refreshing: Promise<string> | null = null;

function refreshAccessToken(): Promise<string> {
  refreshing ??= fetch("/auth/refresh", { method: "POST", credentials: "include" })
    .then((res) => {
      if (!res.ok) throw new Error("refresh failed");
      return res.json() as Promise<{ accessToken: string }>;
    })
    .then((data) => data.accessToken)
    .finally(() => {
      refreshing = null;
    });
  return refreshing;
}

export async function authFetch(url: string, token: { value: string }) {
  const send = () => fetch(url, { headers: { Authorization: `Bearer ${token.value}` } });
  const res = await send();
  if (res.status !== 401) return res;
  token.value = await refreshAccessToken();
  return send(); // 재시도는 한 번만
}
```

두 가지를 함께 지킵니다.

- **재시도는 한 번만.** 갱신한 토큰으로도 401이면 권한 문제이니 다시 갱신하지 않습니다.
- **갱신 요청 자체는 갱신하지 않는다.** `/auth/refresh`가 401을 돌려줄 때 또 갱신을 시도하면 무한 반복이 됩니다. 갱신 실패는 곧 로그아웃입니다.

### 탭이 여러 개라면

위 코드는 한 탭 안에서만 갱신을 모읍니다. 탭 두 개가 동시에 갱신하면 같은 문제가 다시 생깁니다. 브라우저의 Web Locks API로 탭 사이에서도 갱신을 하나씩 실행할 수 있습니다.

```ts
async function refreshAcrossTabs(): Promise<string> {
  return navigator.locks.request("token-refresh", () => refreshAccessToken());
}
```

다른 탭이 잠금을 쥐고 있으면 기다렸다가 실행합니다. 기다리는 동안 다른 탭이 이미 갱신했을 수 있으니, 실행 전에 최신 토큰이 있는지 먼저 확인하는 처리를 더하면 불필요한 갱신을 줄일 수 있습니다. 서버 쪽에서 직전 Refresh Token을 몇 초 동안 허용하는 유예 시간을 두는 방법도 있습니다.

## 3. 만료 전에 미리 갱신하면 되지 않을까

JWT의 `exp`를 읽어 만료 1분 전에 미리 갱신할 수 있습니다. 요청이 401을 받고 다시 보내는 왕복이 줄어듭니다.

하지만 401 처리는 그대로 필요합니다. 사용자 기기의 시계가 틀릴 수 있고, 서버가 토큰을 먼저 폐기할 수도 있습니다. 미리 갱신은 최적화이고, 401 처리가 기본입니다. 서버도 시계 차이를 고려해 `exp` 검증에 몇십 초의 여유를 두는 경우가 많습니다.

## 4. 갱신이 실패하면 — 로그아웃 상태로 정리하기

Refresh Token까지 만료되면 다시 로그인해야 합니다. 이때 토큰만 지우면 부족합니다.

- **이전 사용자의 데이터를 지운다.** 서버 상태 캐시(React Query 등), 메모리 상태, 저장소에 남은 사용자 데이터를 함께 지웁니다. 지우지 않으면 다음에 로그인한 다른 사람에게 이전 사용자의 정보가 잠깐 보일 수 있습니다. 공용 기기나 계정 전환에서 실제로 생기는 문제입니다.
- **돌아갈 주소를 남긴다.** 로그인 후 원래 보던 화면으로 돌려보냅니다. 이 주소의 검증은 6번에서 다룹니다.
- **작성 중인 입력을 잃지 않게 한다.** 긴 글이나 주문서를 쓰는 도중에 세션이 끝나면, 입력을 임시 저장해 두었다가 다시 로그인한 뒤 복원하는 처리를 고려합니다.

## 5. 로그아웃은 어디까지 해야 할까

로그아웃은 버튼 하나지만 범위는 네 겹입니다.

| 범위 | 할 일 |
| --- | --- |
| 현재 탭 | 토큰과 사용자 데이터 캐시·저장소 삭제 |
| 다른 탭 | 같은 브라우저의 다른 탭에도 로그아웃 알림 |
| 서버 | Refresh Token 폐기, 세션 삭제 |
| 인증 서버(SSO·소셜) | 인증 서버 세션을 끝낼지 정책으로 결정 |

다른 탭에는 BroadcastChannel로 알릴 수 있습니다. 메시지는 보낸 탭에는 오지 않으므로 보낸 탭은 직접 정리합니다.

```ts
const channel = new BroadcastChannel("auth");

function clearLocalAuth() {
  sessionStorage.clear();
  // 메모리 토큰, 서버 상태 캐시 등도 여기서 비운다
}

export function logoutEverywhere() {
  clearLocalAuth();
  channel.postMessage({ type: "logout" });
}

channel.onmessage = (event: MessageEvent<{ type: string }>) => {
  if (event.data.type === "logout") clearLocalAuth();
};
```

서버에서 Refresh Token을 폐기해도, 이미 발급된 Access Token은 JWT라면 만료될 때까지 유효합니다. 서버가 상태를 저장하지 않는 대신 생기는 비용입니다. 그래서 Access Token 수명을 짧게 두고, 즉시 끊어야 하는 경우에는 서버가 폐기 목록을 확인합니다.

소셜 로그인이라면 우리 서비스에서 로그아웃해도 카카오 계정 로그인은 그대로입니다. 다음에 “카카오로 시작하기”를 누르면 비밀번호 없이 바로 로그인됩니다. 공용 기기를 고려해 외부 계정까지 로그아웃시킬지는 서비스 정책으로 정합니다. SSO라면 한 서비스의 로그아웃이 다른 서비스까지 끝낼지를 정해야 합니다.

## 6. 리다이렉트 처리의 함정

로그인은 인증 서버를 오가는 리다이렉트로 이뤄집니다. 콜백 페이지에서 자주 생기는 문제를 모았습니다.

**돌아갈 주소를 그대로 믿으면 안 된다.** `?returnTo=` 값을 검증 없이 따라가면, 공격자가 `returnTo=https://evil.example`를 넣은 링크로 사용자를 피싱 사이트에 보낼 수 있습니다. 오픈 리다이렉트라고 부릅니다. 우리 출처의 경로만 허용합니다.

```ts
const APP_ORIGIN = "https://app.example.com";

export function safeReturnTo(value: string | null, fallback = "/"): string {
  if (!value) return fallback;
  try {
    const url = new URL(value, APP_ORIGIN);
    return url.origin === APP_ORIGIN ? url.pathname + url.search + url.hash : fallback;
  } catch {
    return fallback;
  }
}

safeReturnTo("/account?tab=security"); // "/account?tab=security"
safeReturnTo("https://evil.example");   // "/"
safeReturnTo("//evil.example");         // "/" (프로토콜 상대 주소도 다른 출처)
```

문자열이 `/`로 시작하는지만 보면 `//evil.example`이 통과합니다. URL로 해석한 뒤 출처를 비교하는 편이 안전합니다.

**처리한 코드는 주소에서 지운다.** 콜백을 처리한 뒤에도 주소에 `?code=`가 남아 있으면, 새로고침이나 뒤로가기로 같은 코드를 다시 보내 “이미 사용된 코드” 오류가 납니다. 처리 직후 `history.replaceState`로 주소를 정리합니다.

**두 번 실행되지 않게 한다.** 코드 교환을 Effect에서 하면 React 개발 모드의 StrictMode가 Effect를 두 번 실행해, 두 번째 교환이 실패합니다. 실행 여부를 기록해 한 번만 보내거나, 콜백 처리를 서버 라우트에서 합니다.

**오류도 정상 경로처럼 설계한다.** 사용자가 동의 화면에서 취소하면 `?error=access_denied`가 돌아옵니다. 취소, state 불일치, 이미 다른 방식으로 가입한 계정, 서버 오류를 구분해 다음에 무엇을 하면 되는지 안내합니다.

## 7. 로그인 정보가 늦게 오는 환경

앱 웹뷰에서는 앱이 로그인 정보를 페이지 로드보다 늦게 넣어 주는 경우가 있습니다. 페이지가 뜨자마자 “로그인 안 됨”으로 판정하면, 로그인한 사용자도 로그인 화면으로 튕깁니다.

로그인 여부를 참·거짓 두 가지가 아니라 **세 가지 상태**로 다루면 이 문제를 피할 수 있습니다.

```ts
type AuthGate = "pending" | "allowed" | "denied";

export function resolveAuthGate(hasUser: boolean, elapsedMs: number, graceMs = 1500): AuthGate {
  if (hasUser) return "allowed";
  return elapsedMs < graceMs ? "pending" : "denied";
}
```

`pending` 동안에는 로딩을 보여 주고, 유예 시간이 지나도 정보가 없을 때만 차단합니다. 대기를 통과로 취급하지 않는 것이 중요합니다. 앱이 “준비 완료” 이벤트를 보내 줄 수 있다면 시간 대신 그 이벤트를 기다리는 편이 더 정확합니다. 그리고 어느 경우든 실제 권한 확인은 서버 API가 합니다.

## 8. 같은 사람이 두 방식으로 가입하면 — 계정 연결

같은 사람이 카카오로 가입하고, 다음에는 Apple로 로그인을 시도합니다. 두 계정을 이메일로 묶고 싶어지지만 위험합니다.

- 이메일이 인증된 것이 아닐 수 있습니다. 인증되지 않은 이메일로 자동 연결하면, 남의 이메일로 가입한 공격자가 피해자 계정에 들어갈 수 있습니다.
- Apple은 사용자가 이메일을 숨기면 `privaterelay.appleid.com` 중계 주소를 줍니다. 같은 사람이어도 이메일이 다릅니다.
- Apple은 이름을 최초 인증 때 한 번만 보냅니다. 처음 받았을 때 저장하지 않으면 다시 얻을 수 없습니다.

그래서 계정과 로그인 수단을 나눠 저장합니다.

| 테이블 | 키 | 내용 |
| --- | --- | --- |
| 계정 | 우리 서비스의 사용자 ID | 프로필, 권한 |
| 로그인 수단 | 제공자 + 제공자의 사용자 식별자(`iss + sub`) | 어느 계정에 연결됐는지 |

연결은 사용자가 **두 방식 모두로 본인임을 확인한 뒤**에만 합니다. 이미 로그인한 상태에서 “Apple 계정 연결”을 누르게 하는 식입니다. 여러 브랜드나 서비스의 계정을 하나로 통합할 때도 같은 원칙이 적용됩니다.

## 9. 권한은 서버가 확인한다

마지막으로 자주 헷갈리는 부분입니다.

- **JWT를 디코딩하는 것은 검증이 아닙니다.** payload는 암호화가 아니라 인코딩이라 누구나 읽을 수 있습니다. 프론트엔드가 만료 시간이나 이름을 화면에 쓰는 건 괜찮지만, payload의 권한 값으로 기능을 여는 건 화면 편의일 뿐입니다.
- **버튼을 숨기는 건 보안이 아닙니다.** 숨긴 기능의 API는 직접 호출할 수 있습니다. 모든 API가 요청마다 권한을 확인해야 합니다.
- **권한 변경은 토큰에 늦게 반영됩니다.** 권한을 토큰 안에 담았다면 다음 갱신까지 이전 권한이 남습니다. 즉시 반영해야 하는 권한은 서버가 매번 조회합니다.

## 정리

| 상황 | 기본 대응 |
| --- | --- |
| 토큰 저장 | Access는 메모리, Refresh는 httpOnly 쿠키. 저장 위치와 별개로 XSS를 막는다 |
| 동시 401 | 진행 중인 갱신 하나를 같이 기다린다. 탭 사이는 Web Locks |
| 갱신 실패 | 토큰과 사용자 데이터를 함께 지우고, 돌아갈 주소와 입력을 보존한다 |
| 로그아웃 | 현재 탭, 다른 탭, 서버, 인증 서버의 네 범위를 정한다 |
| 콜백 처리 | 돌아갈 주소 검증, 코드 제거, 한 번만 실행, 오류 안내 |
