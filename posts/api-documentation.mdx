[REST API를 설계](/posts/rest-api-design)해서 서버에 올렸다고 끝이 아닙니다. 그걸 쓰는 사람 — 프론트엔드 개발자, 다른 팀, 외부 파트너 — 이 **"이 엔드포인트가 뭘 받고 뭘 주는지"** 를 알아야 하죠. API는 본질적으로 **계약(contract)** 이고, 문서화는 그 계약을 명문화하는 일입니다.

## 문서가 없으면 무슨 일이

프론트 개발자가 새 API를 쓰려는데 문서가 없다면?

- 백엔드 개발자에게 **매번 물어봅니다** ("이 필드 필수예요? 에러는 어떤 형태로 와요?").
- 코드를 직접 뜯어보거나, 응답을 **찍어보며 추측**합니다.
- 백엔드가 조용히 응답 형태를 바꾸면 프론트가 **런타임에 깨집니다**.

이 소통 비용과 어긋남이 팀이 커질수록 폭발합니다. 문서는 "친절"이 아니라 **협업의 인프라**예요.

## OpenAPI — API를 묘사하는 표준

**OpenAPI**(옛 이름 Swagger)는 REST API를 기술하는 **표준 스펙**입니다. 엔드포인트·파라미터·요청/응답 형태·에러를 정해진 형식(YAML/JSON)으로 적죠.

```yaml
paths:
  /api/guestbook:
    post:
      requestBody:
        content:
          application/json:
            schema:
              type: object
              required: [name, message]
              properties:
                name:    { type: string, maxLength: 20 }
                message: { type: string, maxLength: 200 }
      responses:
        "201": { description: 생성됨 }
        "400": { description: 검증 실패 }
        "429": { description: 너무 잦은 요청 }
```

[방명록 API](/posts/guestbook-backend)의 규칙(1~20자, 429 레이트 리밋)이 그대로 **기계가 읽는 계약**이 됩니다.

## 표준이라 도구가 붙는다

OpenAPI가 강력한 건 "표준"이라 **주변 도구가 풍부**하기 때문입니다.

- **Swagger UI**: 스펙을 읽어 **문서 페이지 + 실행 가능한 시험대**를 자동 생성. 브라우저에서 바로 호출해봄.
- **타입 생성**: 스펙에서 프론트용 **TypeScript 타입**을 자동으로 뽑음 — 백엔드 응답 형태와 프론트 타입이 어긋날 일이 없어짐.
- **목 서버**: 스펙만으로 가짜 응답 서버를 띄워, 백엔드 완성 전에 프론트가 **먼저 개발**.
- **계약 테스트**: 실제 응답이 스펙을 지키는지 자동 검증.

## 코드 우선 vs 계약 우선

문서를 만드는 두 방향이 있습니다.

- **코드 우선(code-first)**: 코드에 애노테이션/주석을 달면 문서를 **자동 생성**. 코드와 문서가 안 어긋나는 게 장점.
- **계약 우선(contract-first)**: 스펙을 **먼저** 합의하고, 그에 맞춰 서버·클라이언트를 각자 구현. 프론트·백엔드가 병렬로 일할 수 있음.

어느 쪽이든 핵심은 **문서가 코드와 함께 살아 움직이는 것**입니다. 손으로 쓴 위키 문서는 반드시 낡아요("이 문서 최신 아님" 주석의 저주). 코드에서 생성하거나, 스펙을 단일 출처로 삼아 자동 검증해야 신뢰됩니다.

## 문서화의 범위

엔드포인트 목록만이 문서가 아닙니다.

- **인증 방법**: [토큰을 어떻게](/posts/auth-session-jwt) 실어 보내는지.
- **에러 형식**: [상태 코드](/posts/rest-api-design)와 에러 본문의 일관된 구조.
- **페이지네이션·정렬·필터**: 목록을 어떻게 자르는지.
- **레이트 리밋**: 한도와 초과 시 응답.

---

API 문서화의 핵심은 "**API는 계약이고, 계약은 기계가 읽을 수 있어야 한다**"입니다. OpenAPI로 계약을 표준화하면 문서·타입·목 서버·테스트가 딸려 오고, 프론트와 백엔드가 어긋남 없이 병렬로 달릴 수 있죠. 다음 편에서는 그 API가 의존하는 것들이 실패해도 버티는 [복원력 패턴](/posts/resilience-patterns)을 봅니다.
