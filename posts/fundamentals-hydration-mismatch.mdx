Next.js로 만든 페이지에서 이런 에러를 본 적이 있을 겁니다.

```text
Hydration failed because the server rendered text didn't match the client.
```

서버 로그에는 아무 문제가 없고, 페이지도 일단 보입니다. 그런데 콘솔에는 빨간 에러가 찍히고, 가끔 화면이 한 번 깜빡입니다. 서버에서 잘 렌더된 컴포넌트가 브라우저에서는 왜 문제가 될까요?

## hydration은 HTML을 "이어받는" 과정이다

서버 렌더링 페이지가 뜨는 과정은 두 단계입니다.

1. **서버:** 컴포넌트를 렌더해서 HTML 문자열을 만들어 보냅니다. 브라우저는 이 HTML을 바로 그립니다. 하지만 아직 JavaScript가 없어서 버튼을 눌러도 반응이 없습니다.
2. **브라우저:** JavaScript가 로드되면 React가 **같은 컴포넌트를 한 번 더 렌더**합니다. 그리고 그 결과를 이미 있는 DOM과 맞춰 보면서, DOM을 새로 만들지 않고 **그대로 이어받아** 이벤트 핸들러만 붙입니다.

2번이 **hydration**입니다. 말라 있는 HTML에 물(상호작용)을 붓는다는 뜻입니다. 9편의 재조정을 떠올리면, **"이전 화면" 자리에 서버가 만든 DOM이 있는 재조정**이라고 볼 수 있습니다.

여기에는 전제가 하나 있습니다. **브라우저의 첫 렌더 결과가 서버의 렌더 결과와 같아야 한다.** React는 DOM을 처음부터 다시 만들지 않으려고 "같을 것"이라고 가정하고 이어받습니다. 이 가정이 깨지는 순간이 hydration 에러입니다.

## 결과가 달라지는 대표 원인

컴포넌트 코드는 하나인데 결과가 달라지는 건, **서버와 브라우저가 다른 환경**이기 때문입니다. 아래 다섯 가지는 React의 hydration 에러 메시지에도 그대로 적혀 있는 원인들입니다.

### 1. 브라우저에서만 있는 값으로 분기

```jsx
function Greeting() {
  const isMobile = typeof window !== "undefined" && window.innerWidth < 768;
  return <p>{isMobile ? "모바일" : "데스크톱"}</p>;
}
```

서버에는 `window`가 없으니 항상 "데스크톱"을 렌더합니다. 모바일 브라우저의 첫 렌더는 "모바일"입니다. `localStorage`의 테마, 로그인 여부, 화면 크기처럼 **브라우저에만 있는 값**을 첫 렌더에 쓰면 모두 같은 문제가 생깁니다.

### 2. 렌더할 때마다 달라지는 값

```jsx
<p>현재 시각: {new Date().toLocaleTimeString()}</p>
<div id={`field-${Math.random()}`} />
```

서버가 렌더한 시각과 브라우저가 렌더한 시각은 다릅니다. `Math.random()`도 매번 다릅니다. id가 필요하면 서버와 브라우저에서 같은 값을 만들어 주는 `useId`를 씁니다.

### 3. 지역과 시간대

같은 시각이라도 **어떤 지역 설정과 시간대로 표시하느냐**에 따라 글자가 달라집니다. 서버는 보통 UTC로 돌고, 사용자는 한국 시간입니다.

```js
const date = new Date("2026-06-15T18:00:00Z");

// 서버 (UTC, 영어 지역 설정)
console.log(date.toLocaleDateString("en-US", { timeZone: "UTC" })); // 6/15/2026

// 한국 사용자의 브라우저
console.log(date.toLocaleDateString("ko-KR", { timeZone: "Asia/Seoul" })); // 2026. 6. 16.
```

표기 형식만 다른 게 아니라 **날짜 자체가 하루 다릅니다.** 내 컴퓨터에서는 서버와 브라우저의 시간대가 같아서 개발 중에는 잘 안 보이다가, 배포한 뒤에야 나타나는 경우가 많습니다. 로컬에서 `TZ=UTC LANG=ja_JP.UTF-8 next dev`처럼 서버의 시간대와 지역 설정을 브라우저와 다르게 두고 띄우면 미리 잡을 수 있습니다.

### 4. 잘못된 HTML 중첩

```jsx
<p>
  <div>설명</div>
</p>
```

HTML 규칙상 `<p>` 안에는 `<div>`가 들어갈 수 없습니다. 브라우저는 서버 HTML을 읽으면서 이걸 **스스로 고쳐서**(`<p>`를 먼저 닫음) DOM을 만듭니다. React가 기대한 트리와 실제 DOM의 모양이 달라져 불일치가 납니다. `<a>` 안의 `<a>`, `<button>` 안의 `<button>`도 마찬가지입니다. 이 경우 React는 개발 모드에서 "이 위치에 이 태그가 올 수 없다"는 경고를 먼저 띄워 줍니다.

### 5. 브라우저 확장 프로그램

번역기, 비밀번호 관리자, 문법 검사기 같은 확장 프로그램이 React보다 먼저 DOM에 속성이나 요소를 끼워 넣기도 합니다. 내 코드에는 잘못이 없는데 특정 사용자에게만 에러가 나면 의심해 볼 만합니다. React 19부터는 `<head>`와 `<body>`에 끼어든 예상 밖의 태그를 건너뛰도록 바뀌어 이런 경우가 많이 줄었습니다.

## 불일치가 나면 React는 무엇을 하나

에러 메시지 때문에 페이지가 망가질 것 같지만, React는 복구를 시도합니다.

- **글자나 구조가 다르면:** hydration을 포기하고, 가장 가까운 Suspense 경계(없으면 루트)부터 **브라우저에서 처음부터 다시 렌더**합니다. 서버 HTML을 버리고 새로 그리니 **화면이 깜빡이고**, 서버 렌더링으로 얻은 빠른 첫 화면의 이점이 그 구간에서 사라집니다.
- **속성만 다르면:** 개발 모드에서 경고만 하고, 프로덕션에서 그 속성을 고쳐 준다는 보장이 없습니다. 서버가 넣은 `className`이 그대로 남아 **화면과 state가 어긋난 채로** 동작할 수 있습니다.

그래서 "일단 보이니까 괜찮다"고 넘기면 안 됩니다. 성능 손해이거나, 더 나쁘면 조용한 UI 버그입니다.

## 해결 방법

### 1. 서버와 브라우저가 같은 값을 쓰게 한다

가장 좋은 방법은 **값을 한 곳에서 정해서 넘기는 것**입니다. 현재 시각이 필요하면 서버에서 정한 시각을 props로 넘기고, id는 `useId`로 만들고, 날짜는 시간대를 명시해서 포맷합니다.

```jsx
// 시간대를 고정하면 서버와 브라우저의 결과가 같다
new Intl.DateTimeFormat("ko-KR", { timeZone: "Asia/Seoul" }).format(date);
```

### 2. 브라우저 전용 값은 hydration이 끝난 뒤에 쓴다

브라우저에만 있는 값을 꼭 써야 한다면, **첫 렌더는 서버와 똑같이** 하고 그다음에 바꿉니다. `useSyncExternalStore`는 서버용 값과 브라우저용 값을 따로 받아, hydration 중에는 서버용 값을 쓰고 끝난 뒤 브라우저 값으로 다시 렌더해 줍니다.

```jsx
function subscribe(callback) {
  window.addEventListener("online", callback);
  window.addEventListener("offline", callback);
  return () => {
    window.removeEventListener("online", callback);
    window.removeEventListener("offline", callback);
  };
}

function useOnlineStatus() {
  return useSyncExternalStore(
    subscribe,
    () => navigator.onLine,   // 브라우저에서 읽는 값
    () => true,               // 서버와 hydration 때 쓰는 값
  );
}
```

`useEffect`에서 `setMounted(true)`를 하는 방법도 같은 원리입니다. 다만 두 방법 모두 **서버 값이 먼저 보였다가 바뀌므로**, 테마처럼 눈에 띄는 값은 깜빡임이 남습니다.

### 3. 깜빡이면 안 되는 값은 인라인 스크립트로 먼저 고친다

다크 모드가 대표적입니다. 서버는 사용자의 테마를 모르니 라이트로 렌더하고, 브라우저에서 다크로 바꾸면 한순간 흰 화면이 보입니다. 이럴 때는 HTML을 읽는 도중에 바로 실행되는 **인라인 스크립트**로, 브라우저가 화면을 그리기 전에 DOM을 고칩니다.

```jsx
<html lang="ko" data-theme="light" suppressHydrationWarning>
  <head>
    <script
      dangerouslySetInnerHTML={{
        __html: `try{var t=localStorage.getItem("theme");if(t)document.documentElement.dataset.theme=t}catch(e){}`,
      }}
    />
  </head>
  <body>{children}</body>
</html>
```

스크립트가 `data-theme`을 바꿔 놓았으니 React가 기대한 값(`light`)과 DOM이 달라집니다. 그래서 `<html>`에 `suppressHydrationWarning`을 붙여 **"이 요소는 DOM에 있는 값을 그대로 인정하라"** 고 알려 줍니다. Next.js 문서도 날짜와 테마에 이 방법을 권합니다.

### 4. suppressHydrationWarning은 좁게 쓴다

`suppressHydrationWarning`은 **붙인 요소 한 단계**의 글자와 속성 불일치만 넘어갑니다. 자식 요소까지 덮어 주지 않고, 원인을 고치는 것도 아닙니다. 인라인 스크립트처럼 **다를 수밖에 없다는 걸 알고 일부러 다르게 만든 곳**에만 씁니다.

### 5. 아예 서버에서 그리지 않는다

지도, 차트, 브라우저 API에 강하게 묶인 위젯은 서버에서 그릴 이유가 없습니다. Next.js의 `dynamic(() => import("./Map"), { ssr: false })`로 브라우저에서만 렌더합니다. 이 옵션은 클라이언트 컴포넌트 안에서만 동작합니다. 서버에서 그리지 않는 만큼 그 자리는 빈 칸이나 로딩 표시로 먼저 보입니다.

## 정리

| 원인 | 해결 |
| --- | --- |
| `window`, `localStorage`로 분기 | `useSyncExternalStore`의 서버용 값, 또는 hydration 뒤에 반영 |
| `Date.now()`, `Math.random()` | 서버에서 정한 값을 props로, id는 `useId` |
| 지역·시간대 포맷 | 시간대를 명시해서 포맷하거나 인라인 스크립트 |
| 잘못된 HTML 중첩 | `<p>` 안의 `<div>` 같은 구조를 고침 |
| 깜빡이면 안 되는 테마 | 인라인 스크립트 + 해당 요소에 `suppressHydrationWarning` |
| 브라우저 전용 위젯 | `dynamic(..., { ssr: false })` |

> "hydration은 서버가 만든 HTML을 버리지 않고, 브라우저에서 같은 컴포넌트를 다시 렌더한 결과와 맞춰 보면서 이벤트만 붙여 이어받는 과정입니다. 그래서 브라우저의 첫 렌더가 서버와 같아야 하는데, window나 localStorage 분기, 현재 시각과 난수, 지역·시간대 포맷, 잘못된 HTML 중첩, 확장 프로그램 때문에 결과가 달라지면 hydration 에러가 납니다. 글자나 구조가 다르면 React는 가장 가까운 Suspense 경계부터 브라우저에서 다시 렌더해서 깜빡임과 성능 손해가 생기고, 속성 차이는 고쳐진다는 보장이 없습니다. 값을 한 곳에서 정해 넘기고, 브라우저 전용 값은 useSyncExternalStore로 hydration 뒤에 반영하며, 테마처럼 깜빡이면 안 되는 값은 인라인 스크립트와 suppressHydrationWarning을 함께 씁니다."
