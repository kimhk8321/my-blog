서비스가 잘돼서 사용자가 10배로 늘었습니다. 서버 한 대로는 못 버티죠. 어떻게 늘릴까요? 이 질문의 답이 **확장성(scalability)** 이고, 그 핵심 전제가 **무상태(stateless) 서버**입니다.

## 수직 확장 vs 수평 확장

- **수직 확장(Scale-up)**: 서버 **한 대를 더 좋게** (CPU·메모리 증설). 간단하지만 한계가 있고(물리적 상한), 그 한 대가 죽으면 전체가 멈춤.
- **수평 확장(Scale-out)**: 서버를 **여러 대로** 늘림. 이론상 무한히 확장 가능하고, 한 대가 죽어도 나머지가 버팀.

현대 백엔드는 대부분 **수평 확장**을 지향합니다. 그런데 여기엔 결정적 전제가 있어요.

## 수평 확장의 전제 — 상태를 서버에 두지 마라

서버가 여러 대면, 사용자의 요청이 **매번 다른 서버로** 갈 수 있습니다(로드 밸런서가 분배). 그렇다면 서버가 **자기 메모리에 뭔가를 기억**하면 문제가 생깁니다.

```js
// 나쁜 예: 서버 메모리에 세션 저장
const sessions = {}; // 이 서버에만 있는 상태!

app.post("/login", (req, res) => {
  sessions[sessionId] = user; // 1번 서버 메모리에 저장
});
// 다음 요청이 2번 서버로 가면? sessions에 없음 → 로그인 풀림
```

그래서 원칙은 **"서버는 무상태여야 한다"** 입니다. 서버는 요청을 처리만 하고, **상태는 밖의 공유 저장소**(DB, [Redis](/posts/data-store-selection))에 둡니다. 그러면 어느 서버가 요청을 받든 같은 상태를 보죠.

- **세션** → Redis 같은 공유 세션 스토어에. ([세션 인증](/posts/auth-session-jwt)에서 본 그 이유.)
- **업로드 파일** → 로컬 디스크 대신 오브젝트 스토리지(S3 등).
- **캐시** → 로컬 메모리 대신 [공유 캐시](/posts/server-caching).

> JWT가 확장에 유리하다는 말도 여기서 나옵니다. 토큰 자체에 상태가 담겨 서버가 기억할 게 없으니까요.

## 로드 밸런서 — 요청을 나눠주는 문지기

여러 서버 앞에 **로드 밸런서**가 서서, 들어오는 요청을 각 서버로 분배합니다(라운드 로빈, 최소 연결 등). ([웹 서버 아키텍처](/posts/web-server-architecture)에서 본 그 구조죠.) 한 서버가 죽으면 헬스 체크로 감지해 **살아있는 서버로만** 보냅니다. 이게 수평 확장의 가용성을 만듭니다.

## sticky session의 함정

"서버 메모리에 세션을 두고 싶은데, 같은 사용자를 **항상 같은 서버로** 보내면 되지 않나?" — 이게 **sticky session**입니다. 임시방편은 되지만:

- 그 서버가 죽으면 거기 붙은 사용자들의 세션이 **전부 날아감**.
- 부하가 고르게 안 분산됨(특정 서버에 쏠림).
- 무중단 배포가 어려워짐.

그래서 근본 해법은 sticky가 아니라 **무상태 + 공유 스토어**입니다.

## 확장은 서버만의 문제가 아니다

서버를 100대로 늘려도 **DB가 한 대면** 거기서 병목이 생깁니다. 그래서 확장은 데이터 계층까지 이어집니다 — 읽기 부하는 [캐시](/posts/server-caching)와 읽기 복제본으로, 쓰기 부하는 샤딩으로, 느린 작업은 [메시지 큐](/posts/message-queue)로. "어디가 병목인가"를 찾아 그 지점을 늘리는 게 확장의 실제 모습입니다.

---

확장성의 핵심 한 줄은 "**서버를 무상태로 만들면, 얼마든지 늘릴 수 있다**"입니다. 상태를 밖으로 밀어내는 이 발상이 로드 밸런싱·무중단 배포·장애 대응의 토대가 됩니다. 다음 글에서는 그렇게 공개된 서버를 지키는 [서버 보안 — SQL 인젝션과 입력 검증](/posts/server-security)을 봅니다.
