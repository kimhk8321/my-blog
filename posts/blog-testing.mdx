블로그를 만들며 [검색](/posts/blog-search)·[추천](/posts/blog-related-posts)·[목차](/posts/blog-toc-popular)처럼 로직이 제법 있는 기능들을 붙여 왔습니다. 그때마다 **curl과 브라우저로 손수 확인**했는데, 매번 같은 걸 다시 확인하고 있더군요.

마침 [테스트 글들](/posts/backend-testing)을 정리한 참이라, 그 내용을 제 코드에 적용해 봤습니다.

## 무엇을 테스트할까 — 이게 제일 어려웠다

테스트를 붙이기로 하고 처음 든 생각은 "어디부터?"였습니다. 컴포넌트? API? 페이지?

[테스트 피라미드](/posts/backend-testing)를 다시 떠올렸습니다. **아래층(빠르고 많이)부터**. 그리고 기준을 하나 세웠습니다.

> **"내가 만들면서 헷갈렸던 곳"**

버그는 대개 어려웠던 곳에서 나옵니다. 그래서 개발하며 실제로 고민했던 지점들을 골랐어요.

| 무엇 | 왜 |
| --- | --- |
| 목차의 id 생성 | 렌더러와 **정확히 같아야** 앵커가 동작 |
| 한글 토큰화 | 색인과 검색의 규칙이 **다름** |
| 글 정렬 | 날짜·order 우선순위가 헷갈림 |
| 비밀번호 비교 | 길이가 다르면 **예외가 날 수 있음** |

반대로 **테스트하지 않은 것**도 정했습니다. 컴포넌트 렌더링, API 라우트, 페이지. 이것들은 브라우저에서 눈으로 확인하는 게 아직 더 빠르고, [E2E](/posts/e2e-testing)를 붙일 만큼 흐름이 복잡하지도 않았거든요. **없는 것보다 나쁜 게 의미 없는 테스트**라고 생각했습니다.

## 순수 함수만 골라내니 쉬워졌다

고른 넷은 공통점이 있었습니다. **입력을 주면 출력이 나오는 함수**라는 것.

```ts
extractToc(mdx)                    // 문자열 → 목차 배열
tokenize(text, "index" | "query")  // 문자열 → 토큰 배열
sortPosts(posts, mode)             // 배열 → 정렬된 배열
passwordMatches(input)             // 문자열 → true/false
```

파일을 읽거나 Redis에 붙는 함수들은 뺐습니다. 그런 건 [대역이 필요하고](/posts/test-doubles), 대역이 많아지면 테스트가 흐릿해지니까요.

재밌었던 건 **테스트하기 쉬운 함수가 이미 잘 분리돼 있었다**는 점입니다. 검색을 만들 때 [역색인 모듈을 따로 뺐던](/posts/blog-related-posts) 게 여기서 이득으로 돌아왔어요. 반대로 말하면, 테스트하기 어려웠다면 그건 [설계 신호](/posts/tdd)였겠죠.

## 가장 중요했던 테스트

목차를 만들 때 신경 썼던 미묘한 규칙이 있습니다.

```ts
it("목차에 넣지 않는 단계도 중복 번호 계산에는 넣는다", () => {
  // h4가 슬러그를 먼저 가져가므로, 뒤의 h2는 "정리-1"이 되어야
  // 실제 렌더링(rehype-slug) 결과와 어긋나지 않는다
  const toc = extractToc(["#### 정리", "## 정리"].join("\n"));

  expect(toc.map((item) => item.id)).toEqual(["정리-1"]);
});
```

목차에는 h2·h3만 담지만, **슬러그 계산기는 모든 헤딩을 거쳐야** 합니다. 안 그러면 중복 번호가 어긋나 앵커가 깨지죠.

이건 코드만 봐서는 "왜 이렇게 했지?" 싶은 부분입니다. 테스트가 있으면 **의도가 문서로 남습니다.** 몇 달 뒤의 제가 "이 줄 필요 없는데?" 하고 지우면 빨간불이 켜지겠죠.

## 통과하는 걸 믿지 말고, 실패하는 걸 확인하자

24개가 전부 초록불이 됐을 때, [TDD 글에 쓴 문장](/posts/tdd)이 떠올랐습니다.

> 실패를 꼭 확인해야 합니다 — 테스트가 애초에 잘못 짜여 항상 통과하는 경우를 여기서 걸러내거든요.

그래서 **일부러 버그를 심어 봤습니다.** 위에서 말한 그 규칙을 깨뜨렸죠(h4를 슬러그 계산에서 빼기).

```
❯ src/lib/toc.test.ts (6 tests | 1 failed)
  × 목차에 넣지 않는 단계도 중복 번호 계산에는 넣는다
    → expected [ '정리' ] to deeply equal [ '정리-1' ]
```

**딱 그 테스트 하나만** 실패했습니다. 나머지 23개는 그대로 통과했고요. 원하는 결과였습니다 — 테스트가 실제로 그 동작을 붙잡고 있고, 범위도 정확하다는 뜻이니까요.

되돌리니 다시 24개 초록불. 이 왕복 한 번으로 테스트를 믿을 수 있게 됐습니다.

## 설치에서 두 번 막혔다

정작 시간을 잡아먹은 건 테스트를 쓰는 게 아니라 **환경**이었습니다.

**1. 네이티브 바이너리를 못 찾음**

최신 Vitest를 깔았더니 이렇게 나왔습니다.

```
Error: Cannot find native binding.
  Cannot find module '@rolldown/binding-wasm32-wasi'
```

최신 버전이 새 번들러(rolldown)를 쓰는데, 제 환경(Node 20)과 맞는 바이너리가 없었습니다. 최신을 고집할 이유가 없어서 **한 단계 낮은 안정 버전**으로 내렸습니다.

**2. 설정 파일이 CommonJS로 읽힘**

```
Error [ERR_REQUIRE_ESM]: require() of ES Module ... not supported
```

`vitest.config.ts`를 읽을 때 난 오류입니다. 이 프로젝트의 `package.json`에 `"type": "module"`이 없어서 `.ts`가 CommonJS로 취급된 거죠.

`"type": "module"`을 추가하면 프로젝트 전체에 영향이 갑니다. 대신 **확장자를 `.mts`로** 바꿔서 그 파일만 ESM으로 읽히게 했습니다. 범위가 좁은 쪽을 골랐어요.

두 문제 모두 테스트 코드와는 아무 상관이 없었는데, **처음 도구를 붙일 때는 이런 데서 시간이 갑니다.**

## 덤 — 린트 오류 25건도 정리했다

테스트를 붙이는 김에 `pnpm lint`를 돌렸더니 **25건이 실패**하고 있었습니다. 그동안 빌드만 확인하고 린트는 안 돌렸던 거죠.

살펴보니 성격이 갈렸습니다.

**진짜 문제였던 것** — 방명록 페이지가 `<a>`로 링크를 걸어 **클라이언트 라우팅 대신 전체 새로고침**이 일어나고 있었습니다. 눈으로는 잘 몰랐던 버그였어요.

**고칠 수 있었던 것** — 효과에서 `setState`로 상태를 맞추던 곳들. 테마 토글은 `useSyncExternalStore`로 문서의 class를 직접 구독하게 바꾸니 `mounted` 플래그까지 사라졌습니다. 검색은 `status`를 따로 들고 있지 않고 **가진 값에서 계산**하도록 바꿨고요.

> 여기서 하나 배웠습니다. 검색을 고치다 **회귀를 두 개 만들었어요** — 검색어를 지워도 이전 결과가 남고, 한글 한 글자("훅")에서 로딩 판정이 틀렸습니다. 다행히 예전에 손으로 확인했던 시나리오를 그대로 다시 돌려 잡았는데, **이래서 UI에도 테스트가 필요하구나** 싶더군요. 리팩터링의 안전망이 딱 그 지점에는 없었던 겁니다.

**일부러 그렇게 둔 것** — 미니 훅 엔진, 시그널, 렌더 횟수 데모는 **규칙이 막으려는 동작을 일부러 보여주는 교보재**입니다. "렌더 중에 ref를 건드리지 마라"를 설명하려면 렌더 중에 ref를 건드려야 하죠. 이건 고치면 데모가 사라지니, 파일마다 **왜 예외인지 적어 두고** 규칙을 껐습니다.

린트 경고를 없애는 방법은 둘입니다 — 고치거나, 끄거나. **끌 때 이유를 남기는 것**이 나중의 나에게 할 수 있는 최소한의 배려 같았습니다.

## 배운 것

- **무엇을 테스트할지가 어떻게 테스트할지보다 어렵다** — "헷갈렸던 곳"이 꽤 쓸 만한 기준이었다.
- **테스트가 의도를 문서로 남긴다** — 코드만으로는 "왜 이렇게?"인 줄이 테스트에서는 이름으로 설명된다.
- **초록불을 믿지 말고 빨간불을 확인하자** — 버그를 심어 보는 데 1분 걸렸고, 그걸로 테스트를 믿게 됐다.
- **도구 설치가 테스트 작성보다 오래 걸릴 수 있다** — 최신을 고집하지 않는 것도 방법이다.
- **안전망이 없는 곳을 리팩터링하면 회귀가 난다** — 이번엔 운 좋게 잡았지만, 다음엔 UI 테스트를 먼저 붙이는 게 낫겠다.

---

24개는 적은 수입니다. 하지만 **손으로 반복하던 확인 중 일부가 자동이 됐고**, 무엇보다 "이 코드는 이렇게 동작해야 한다"는 약속이 코드 옆에 남았습니다. 다음엔 [E2E](/posts/e2e-testing)로 검색·방명록 같은 흐름을 덮어 볼 생각이에요 — 방금 회귀를 낸 자리가 정확히 거기니까요.
