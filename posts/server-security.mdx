프론트엔드 보안이 주로 **브라우저 안**([XSS·CSRF](/posts/web-security))의 문제라면, 백엔드 보안은 **"믿을 수 없는 입력이 서버로 들어온다"** 는 전제에서 출발합니다. 공개 API는 누구나, 자동화된 스크립트로도 두드릴 수 있으니까요. 그 첫 관문이 **입력을 다루는 방식**입니다.

## 대원칙 — 서버는 클라이언트를 믿지 않는다

[방명록을 만들며](/posts/guestbook-backend) 가장 크게 배운 것이기도 합니다. 프론트에서 아무리 검증해도, 공격자는 `curl`로 API를 직접 때립니다. **모든 입력은 서버에서 다시 검증**해야 합니다. 프론트 검증은 UX용, 서버 검증은 보안용이에요.

## SQL 인젝션 — 가장 고전적이고 치명적

사용자 입력을 **쿼리 문자열에 그대로 이어 붙이면** 벌어집니다.

```js
// 위험: 입력을 문자열로 조립
const q = `SELECT * FROM users WHERE name = '${input}'`;
```

공격자가 `input`에 `' OR '1'='1` 을 넣으면 쿼리가 이렇게 됩니다.

```sql
SELECT * FROM users WHERE name = '' OR '1'='1'  -- 항상 참 → 전체 유출
```

`'; DROP TABLE users; --` 같은 입력이면 **테이블이 통째로 삭제**될 수도 있죠. 입력이 데이터가 아니라 **코드로 해석**되는 게 문제의 본질입니다. (XSS가 브라우저에서 벌어지는 같은 유형의 사고라면, 인젝션은 DB에서 벌어집니다.)

## 방어 — 파라미터라이즈드 쿼리

해법은 간단하고 확실합니다. **입력을 쿼리 구조와 분리**해서, 값은 언제나 "값"으로만 다루게 하는 것.

```js
// 안전: 값을 파라미터로 전달 (플레이스홀더)
const rows = await db.query(
  "SELECT * FROM users WHERE name = ?",
  [input] // 이 값은 절대 SQL 구조로 해석되지 않음
);
```

DB 드라이버가 `input`을 **순수한 값**으로 처리하므로, 무엇이 들어와도 쿼리 구조가 바뀌지 않습니다. ORM이나 쿼리 빌더도 내부적으로 이 방식을 씁니다. **문자열 조립만 피하면** SQL 인젝션의 대부분이 막힙니다.

## 입력 검증 — allowlist가 기본

"무엇을 막을까(blocklist)"보다 **"무엇만 허용할까(allowlist)"** 가 안전합니다. 나쁜 패턴을 일일이 나열하는 건 언제나 빠뜨리기 마련이니까요.

- **타입·길이·형식**을 명시적으로 검사(이메일 형식, 1~200자 등).
- 정해진 값 집합은 **열거된 것만** 허용(`status`는 `active`/`inactive`만).
- 검증 실패는 [`400 Bad Request`](/posts/rest-api-design)로 명확히.

## 최소 권한과 시크릿 관리

- **최소 권한**: 애플리케이션 DB 계정에 딱 필요한 권한만. 웹 서버 계정이 `DROP TABLE` 권한을 가질 이유는 없죠. 사고가 나도 피해를 좁힙니다.
- **시크릿은 코드 밖으로**: DB 비밀번호·API 키·토큰을 소스에 하드코딩하지 않습니다. **환경변수**로 주입하고, `.env`는 커밋에서 제외(gitignore)합니다. 이 블로그도 Upstash 토큰을 `.env.local`에 두고 배포 플랫폼의 환경변수로만 넣었어요.
- **에러 메시지에 내부 노출 금지**: 스택 트레이스·쿼리문을 그대로 사용자에게 돌려주지 않기.

## 그 밖의 기본 방어선

- **레이트 리밋**: 무차별 대입·도배를 막음([방명록](/posts/guestbook-backend)에서 구현).
- **HTTPS**: 전송 구간 암호화(기본).
- **인증·인가 분리**: "누구인가([인증](/posts/auth-session-jwt))"와 "무엇을 할 수 있나(인가)"를 각각 확인.
