코드를 고칠 때마다 손으로 테스트 돌리고, 빌드하고, 서버에 올리고… 이걸 매번 사람이 하면 **느리고, 빠뜨리고, 실수합니다**. CI/CD는 이 반복 과정을 **자동 파이프라인**으로 만들어, "코드를 push하면 알아서 검증되고 배포되게" 합니다.

## CI — 지속적 통합

**CI(Continuous Integration)** 는 "코드가 합쳐질 때마다 **자동으로 검증**한다"입니다. 누군가 push하거나 PR을 열면:

1. 코드를 받아온다
2. 의존성 설치
3. **[테스트](/posts/backend-testing) 실행** + 린트/타입 체크
4. 빌드(또는 [이미지](/posts/docker-containers) 생성)

하나라도 실패하면 **빨간불** — 합치기 전에 문제를 잡습니다. "내 로컬에선 됐는데 남의 변경과 합치니 깨짐"을 조기에 발견하는 게 핵심이에요.

## CD — 지속적 배포

**CD(Continuous Delivery/Deployment)** 는 CI를 통과한 결과물을 **자동으로 배포**까지 잇는 것입니다.

- **Delivery**: 배포 **직전까지** 자동, 마지막 "배포 버튼"만 사람이.
- **Deployment**: 그 버튼도 자동 — 통과하면 **곧바로 운영에** 나감.

"테스트 통과 = 배포 가능"이라는 신뢰가 있어야 성립합니다. 그래서 [테스트](/posts/backend-testing)가 CI/CD의 토대예요.

## 파이프라인의 모습

```yaml
# 개념적 예시 (push → 검증 → 배포)
on: push
jobs:
  test:  [ 설치 → 린트 → 테스트 ]
  build: [ 이미지 빌드 → 레지스트리 푸시 ]   # test 통과 시
  deploy:[ 운영에 롤아웃 ]                    # build 통과 시
```

각 단계는 **앞 단계가 성공해야** 다음으로 넘어갑니다. 실패 지점에서 멈추고 알림이 오죠.

## 무중단 배포 전략

새 버전을 내보낼 때 서비스가 끊기면 안 됩니다. 그래서 **점진적으로** 교체합니다.

- **롤링(Rolling)**: 인스턴스를 몇 개씩 순차 교체. 구·신 버전이 잠시 공존.
- **블루-그린(Blue-Green)**: 새 버전(그린)을 통째로 띄워두고, 준비되면 트래픽을 **한 번에 스위치**. 문제 시 즉시 롤백.
- **카나리(Canary)**: 새 버전에 트래픽을 **5% → 50% → 100%** 로 조금씩. 이상하면 조기 중단.

이게 가능하려면 서버가 [무상태](/posts/scalability-stateless)여야 하고, [헬스 체크](/posts/observability)로 "새 인스턴스가 정말 준비됐는지"를 알아야 합니다.

## 왜 좋은가

- **빠른 피드백**: 문제를 몇 분 안에, 작을 때 발견.
- **사람 실수 감소**: 배포 절차가 코드로 고정 — "그 단계 깜빡"이 없음.
- **자주, 작게 배포**: 큰 배포 한 번보다 작은 배포 여럿이 안전하고 되돌리기 쉬움.

## 이 블로그의 경우

사실 이 블로그도 CI/CD 위에 있습니다. `main`에 [push하면](/posts/blog-view-counter) **Vercel이 자동으로** 빌드하고, 성공하면 새 버전을 배포하고, 실패하면 이전 버전을 유지하죠. 앞서 [Node 버전 빌드 에러](/posts/blog-view-counter)를 본 것도 이 파이프라인의 검증 단계였습니다. 플랫폼이 파이프라인을 대신 제공하는 형태예요.

---

CI/CD의 핵심은 "**push 한 번에 검증과 배포가 자동으로 흐르게**"입니다. 사람은 코드에 집중하고, 반복·위험한 절차는 기계가 정확히 반복하죠. 그런데 배포한 뒤 "잘 돌고 있나?"는 어떻게 알까요 — 다음 편 [로깅과 모니터링](/posts/observability)에서 봅니다.
