[성능 최적화 개요](/posts/frontend-performance-optimization)에서 이미지를 한 줄로 짚고 넘어갔는데, 사실 여기만 제대로 해도 체감 속도가 가장 크게 바뀝니다. 보통 페이지 전송량의 **절반 이상이 이미지**고, 화면에서 가장 큰 요소도 대개 이미지라 **LCP를 결정**하거든요.

## 1. 포맷 — 같은 그림을 더 적은 바이트로

가장 쉬운 절약입니다. 화질을 눈에 띄게 잃지 않고 용량만 줄일 수 있어요.

| 포맷 | 특징 |
| --- | --- |
| JPEG | 사진용 전통 강자. 호환성 최고 |
| PNG | 무손실·투명. 사진에는 무겁다 |
| WebP | JPEG 대비 **25~35% 절감**. 사실상 모든 브라우저 지원 |
| AVIF | WebP보다 **또 20~30% 절감**. 인코딩이 느림 |

`picture`로 지원하는 브라우저에만 신형 포맷을 주고, 아니면 자동으로 물러나게 합니다.

```html
<picture>
  <source srcset="hero.avif" type="image/avif" />
  <source srcset="hero.webp" type="image/webp" />
  <img src="hero.jpg" alt="설명" />
</picture>
```

브라우저는 위에서부터 **지원하는 첫 번째**를 고릅니다. 순서가 곧 우선순위예요.

## 2. 해상도 — 폰에 4000px 이미지를 보내지 말자

포맷보다 낭비가 큰 지점입니다. 데스크톱용 원본을 그대로 모바일에 내려보내면, 화면엔 400px로 줄여 그리면서 **데이터는 다 받습니다.**

`srcset`으로 여러 크기를 주고 `sizes`로 "이 이미지가 화면에서 얼마나 넓게 쓰이는지"를 알려주면, 브라우저가 알아서 고릅니다.

```html
<img
  src="photo-800.jpg"
  srcset="photo-400.jpg 400w, photo-800.jpg 800w, photo-1600.jpg 1600w"
  sizes="(max-width: 768px) 100vw, 800px"
  alt="설명"
/>
```

- `400w`는 **이미지의 실제 픽셀 너비**입니다(표시 크기가 아님).
- `sizes`는 "768px 이하에서는 화면 전체 너비, 그보다 크면 800px로 표시된다"는 뜻.
- 브라우저가 화면 크기와 **DPR(고밀도 디스플레이 배율)** 까지 계산해서 고릅니다.

`sizes`를 빼먹으면 브라우저는 `100vw`로 가정해 필요보다 큰 걸 받습니다. [반응형 레이아웃](/posts/responsive-web)을 쓴다면 여기도 같이 맞춰야 해요.

## 3. 지연 로딩 — 단, LCP 이미지는 예외

화면 밖 이미지를 처음부터 받을 이유가 없죠.

```html
<img src="below.jpg" loading="lazy" alt="" />
```

**하지만 첫 화면 이미지에 `lazy`를 붙이면 오히려 느려집니다.** 지연 로딩은 "레이아웃이 잡힌 뒤에 판단"하므로 발견이 늦어지거든요. 그래서 이렇게 나눕니다.

- **첫 화면(above the fold) 이미지**: `loading="eager"` + `fetchpriority="high"`
- **나머지**: `loading="lazy"`

```html
<!-- LCP 후보: 빨리, 먼저 -->
<img src="hero.avif" fetchpriority="high" alt="대표 이미지" />
```

`fetchpriority="high"`는 "다른 리소스보다 이걸 먼저 받아라"는 신호입니다. LCP 개선에 효과가 즉각적이에요.

## 4. 레이아웃 밀림 막기 — 자리를 미리 잡아준다

이미지가 늦게 도착하면 그 자리가 **0 높이**였다가 갑자기 벌어지면서 아래 내용이 밀립니다. 읽던 줄이 튀는 그 현상 — [CLS](/posts/core-web-vitals)죠.

해법은 간단합니다. **크기를 미리 알려주면** 브라우저가 자리를 비워둡니다.

```html
<!-- width/height를 쓰면 브라우저가 종횡비를 계산해 자리를 잡는다 -->
<img src="photo.jpg" width="800" height="450" alt="" />
```

```css
img {
  height: auto;      /* 반응형으로 늘어나되 */
  aspect-ratio: 16 / 9;  /* 비율은 유지 */
}
```

"반응형이니까 width/height는 빼야지"는 오해입니다. **속성으로 비율만 알려주고 CSS로 크기를 조절**하는 게 정답이에요.

## 5. 그 밖의 것들

- **SVG**: 아이콘·로고는 벡터라 어떤 해상도에서도 선명하고 대개 더 가볍습니다.
- **디코딩**: 큰 이미지는 `decoding="async"`로 디코딩이 메인 스레드를 막지 않게.
- **CDN**: 이미지 CDN을 쓰면 위 변환(포맷·크기)을 URL 파라미터로 자동 처리해 줍니다.
- **`alt`**: 성능은 아니지만 [접근성](/posts/web-accessibility)과 [SEO](/posts/seo-basics)의 기본입니다. 장식용 이미지는 `alt=""`로 비워 스크린리더가 건너뛰게 하세요.

## 프레임워크가 대신 해주는 것

Next.js의 `next/image`는 위의 상당 부분을 자동화합니다 — 요청한 브라우저에 맞는 **포맷 변환**, `srcset` 자동 생성, 기본 지연 로딩, `width`/`height` 기반 **자리 확보**. `priority`를 주면 `fetchpriority="high"`와 즉시 로딩으로 바뀌고요.

```jsx
import Image from "next/image";

<Image src="/hero.jpg" width={800} height={450} alt="대표" priority />
```

편하지만, **무엇을 대신 해주는지 알고 쓰는 것**과 모르고 쓰는 것은 다릅니다. 위 원리를 알면 왜 `priority`를 첫 화면에만 줘야 하는지, 왜 `sizes`를 신경 써야 하는지가 보이죠.

---

이미지 최적화는 "**필요한 만큼만, 필요한 때에, 자리를 잡고**"로 요약됩니다. 포맷으로 바이트를 줄이고, `srcset`으로 해상도를 맞추고, 첫 화면과 나머지를 구분하고, 크기를 미리 알려 밀림을 막는 것. 다음 글에서는 같은 고민을 [웹 폰트](/posts/web-font-optimization)에 적용해 봅니다 — 한글 폰트는 이미지만큼 무겁거든요.
