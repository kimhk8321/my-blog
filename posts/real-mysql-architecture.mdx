[트랜잭션](/posts/transactions-isolation)과 [인덱스](/posts/query-performance)를 개념으로 정리했으니, 이제 **실제 DB가 그걸 어떻게 구현하는지** 볼 차례입니다. 『Real MySQL 8.0』을 읽으며 정리한 노트를 연재로 남깁니다.

첫 편은 구조입니다. MySQL의 특이한 점부터 짚고 시작하죠.

## 엔진이 둘로 나뉘어 있다

MySQL은 다른 DB와 달리 **두 층**으로 되어 있습니다.

- **MySQL 엔진** — 접속 처리, SQL 파싱, 문법 검사, **옵티마이저**(실행 계획 수립)
- **스토리지 엔진** — 실제로 **디스크에서 데이터를 읽고 쓰는** 부분

위층은 "무엇을 어떻게 가져올지"를 정하고, 아래층은 "실제로 가져오는" 일을 합니다.

왜 이렇게 나눴을까요? **스토리지 엔진을 갈아 끼울 수 있게** 하려고입니다. 테이블마다 다른 엔진을 쓸 수도 있죠. 역사적으로 MyISAM, MEMORY 등이 있었고, 지금은 사실상 **InnoDB**가 표준입니다.

이 구조가 왜 중요하냐면 — **어떤 기능이 어느 층에 있는지**에 따라 동작이 달라지기 때문입니다. 트랜잭션과 잠금은 스토리지 엔진(InnoDB)의 기능이고, 실행 계획은 MySQL 엔진의 몫입니다. MyISAM을 쓰면 트랜잭션이 아예 없는 이유가 이것이죠.

## 버퍼 풀 — 성능의 심장

InnoDB에서 가장 중요한 건 **버퍼 풀(Buffer Pool)** 입니다. 디스크의 데이터와 인덱스를 **메모리에 캐시**해 두는 공간이에요.

- 읽기: 필요한 페이지가 버퍼 풀에 있으면 **디스크에 안 갑니다**
- 쓰기: 변경도 일단 **버퍼 풀에서** 하고, 디스크 반영은 나중에 몰아서

두 번째가 핵심입니다. 디스크 쓰기는 느리니, **바로 쓰지 않고 미룹니다.** 변경된 페이지(더티 페이지)를 모아뒀다가 한꺼번에 기록하죠. [서버 캐싱](/posts/server-caching)에서 본 write-back과 같은 발상입니다.

그래서 **버퍼 풀 크기가 성능을 좌우합니다.** 자주 쓰는 데이터가 전부 메모리에 올라가면 디스크는 거의 안 건드리게 되니까요.

## 그런데 미루면 안 잃어버리나 — 리두 로그

여기서 의문이 생깁니다. 커밋했는데 아직 디스크에 안 썼다면, **지금 서버가 죽으면 그 변경은 사라지는 것 아닌가?**

그래서 **리두 로그(Redo Log)** 가 있습니다. 커밋할 때 데이터 파일 대신 **"무엇을 바꿨다"는 기록만 로그에 먼저** 적습니다.

- 로그는 **순차 쓰기**라 빠릅니다(데이터 파일은 여기저기 흩어진 임의 쓰기)
- 서버가 죽어도 재시작할 때 로그를 다시 실행해 **복구**합니다

이게 [ACID의 지속성(Durability)](/posts/transactions-isolation)을 지키는 방법입니다. **"진짜 데이터를 쓰는 대신 무엇을 쓸지를 먼저 기록한다"** — WAL(Write-Ahead Logging)이라 부르는 이 아이디어는 DB 전반에서 반복됩니다.

## 되돌리려면 — 언두 로그

리두가 "다시 실행"이라면 **언두 로그(Undo Log)** 는 "되돌리기"입니다. 변경 **전의 값**을 보관하죠.

용도가 둘입니다.

1. **롤백** — 트랜잭션을 취소할 때 이전 값으로 되돌림
2. **MVCC** — 다른 트랜잭션이 **변경 전 상태를 읽을 수 있게** 해줌

두 번째가 특히 중요합니다. 누군가 수정 중인 행을 다른 트랜잭션이 읽으려 할 때, 잠겨서 기다리는 게 아니라 **언두 로그에 있는 옛 값을 대신 보여줍니다.** 그래서 **읽기가 쓰기를 막지 않습니다.** 이 부분은 [3편](/posts/real-mysql-lock)에서 자세히 봅니다.

## 정리하면 흐름은 이렇다

`UPDATE` 한 번이 이렇게 처리됩니다.

1. MySQL 엔진이 SQL을 파싱하고 실행 계획을 세운다
2. InnoDB가 대상 페이지를 **버퍼 풀**로 올린다(없으면 디스크에서)
3. 변경 전 값을 **언두 로그**에 적는다
4. 버퍼 풀의 페이지를 고친다(디스크는 아직)
5. 커밋 시 **리두 로그**에 기록하고 응답한다
6. 더티 페이지는 나중에 디스크로 내려간다

**"메모리에서 하고, 로그로 안전을 보장하고, 디스크 쓰기는 미룬다"** — 이 세 문장이 InnoDB의 성능과 안정성을 동시에 설명합니다.
