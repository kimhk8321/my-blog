지난번에 [Idempotency Key의 원리](/posts/idempotency-key)를 글로 쓰고 데모까지 만들었습니다. 그런데 정작 이 블로그의 [방명록](/guestbook)에는 그 원리가 적용돼 있지 않았어요. 설명은 그럴듯하게 해 놓고 실제 코드는 다른 이야기를 하고 있는 셈이었습니다.

방명록에서 네트워크 응답을 못 받으면 어떻게 될까? 글은 이미 저장됐을 수 있습니다. 사용자는 실패한 줄 알고 다시 누릅니다. 이전 구현은 이 요청을 **같은 작성 시도의 재전송**으로 알아보지 못했습니다.

## 30초 제한이 재시도를 막고 있었다

방명록에는 IP당 30초에 한 번만 작성할 수 있는 제한이 있습니다. 순서는 이랬습니다.

```text
작성 제한 키 선점 → 글 저장 → 응답
```

서버가 글을 저장한 뒤 응답만 사라지면, 사용자가 다시 보낸 요청은 작성 제한에 걸려 `429`가 됩니다. 클라이언트는 글이 남았는지 알 수 없고, 기다렸다 다시 누르면 이번에는 **같은 글이 하나 더 생길 수 있습니다.**

버튼을 전송 중에 비활성화해도 이 경우는 해결되지 않습니다. 지난번 글의 데모를 방명록에 붙이려면, 작성 제한보다 먼저 **이미 처리한 요청인지** 확인해야 했습니다.

## 한 번의 작성에 하나의 키

브라우저가 제출할 때 UUID를 만들고 `Idempotency-Key` 헤더에 담습니다. 실패한 뒤 이름과 메시지를 그대로 두고 다시 누르면 키를 재사용합니다. 내용을 고쳐 새 작성 시도를 시작하면 새 키를 만듭니다.

```tsx
const pending = useRef<{
  key: string;
  name: string;
  message: string;
} | null>(null);

if (
  pending.current?.name !== name.trim() ||
  pending.current?.message !== message.trim()
) {
  pending.current = {
    key: crypto.randomUUID(),
    name: name.trim(),
    message: message.trim(),
  };
}

await fetch("/api/guestbook", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "Idempotency-Key": pending.current.key,
  },
  body: JSON.stringify({
    name: pending.current.name,
    message: pending.current.message,
  }),
});
```

화면에서 같은 글을 두 번 그리지 않도록 응답의 `entry.id`도 확인합니다. 첫 응답이 늦게 도착했거나 목록에 이미 반영된 경우에도 중복 카드를 만들지 않기 위해서입니다.

## 서버의 세 가지 판단

같은 키가 다시 들어왔을 때 서버가 할 일은 단순합니다.

1. **키가 있고 내용도 같으면:** 기존 글과 같은 결과를 돌려준다.
2. **키가 있는데 내용이 다르면:** 키를 재사용한 실수로 보고 `409`를 반환한다.
3. **처음 보는 키라면:** IP 작성 제한을 확인한 뒤 글을 저장한다.

내용 비교에는 다듬은 이름과 메시지의 해시를 씁니다. `name + message`처럼 그냥 이어 붙이면 `A`·`BC`와 `AB`·`C`를 구별할 수 없으니, 두 필드를 배열로 직렬화한 다음 해시를 계산했습니다.

```ts
createHash("sha256")
  .update(JSON.stringify([name, message]))
  .digest("hex");
```

재시도는 IP 작성 제한보다 먼저 판정합니다. 이미 받아 둔 같은 글을 돌려주는 일은 **새 글 작성이 아니기 때문**입니다. 키는 24시간 후 만료되게 했습니다.

## `GET` 다음 `SET`으로는 부족했다

처음에는 Redis에서 키를 읽고, 없으면 글을 저장한 뒤 키를 기록하면 될 것 같았습니다.

```ts
const previous = await redis.get(key);
if (previous) return previous;

await redis.lpush("guestbook", entry);
await redis.set(key, entry);
```

두 요청이 동시에 첫 줄을 통과하면 둘 다 `LPUSH`합니다. `SET NX`로 키를 먼저 선점해도, 글을 저장한 뒤 완료 기록을 남기기 전에 서버가 멈추면 이번에는 **글은 있는데 키에는 처리 중이라고만 남는 틈**이 생깁니다.

이번 방명록의 목록과 키는 모두 같은 Redis에 있습니다. 그래서 키 확인, 작성 제한 확인, 목록에 추가, 결과 기록을 **한 Lua 스크립트에서 실행**했습니다.

```lua
local previous = redis.call('GET', KEYS[1])
if previous then
  local record = cjson.decode(previous)
  if record.hash ~= ARGV[1] then
    return cjson.encode({ status = 'conflict' })
  end
  return cjson.encode({ status = 'replayed', entry = record.entry })
end

if redis.call('EXISTS', KEYS[2]) == 1 then
  return cjson.encode({ status = 'rate_limited' })
end

local entry = cjson.decode(ARGV[2])
redis.call('LPUSH', KEYS[3], ARGV[2])
redis.call('LTRIM', KEYS[3], 0, tonumber(ARGV[3]) - 1)
redis.call('SET', KEYS[1], cjson.encode({ hash = ARGV[1], entry = entry }),
  'EX', tonumber(ARGV[4]))
redis.call('SET', KEYS[2], '1', 'EX', tonumber(ARGV[5]))
```

Redis는 스크립트가 실행되는 동안 다른 요청을 끼워 넣지 않습니다. 같은 키로 동시에 들어온 요청 중 하나가 저장을 마치면 나머지는 위쪽의 `previous`에서 결과를 읽습니다. 이 구조에서는 기존의 방명록 List를 다른 저장소로 옮길 필요도 없었습니다. [Upstash의 EVAL 문서](https://upstash.com/docs/redis/sdks/ts/commands/scripts/eval)와 [Redis 스크립트 실행 설명](https://redis.io/docs/latest/develop/programmability/eval-intro/)을 참고했습니다.

스크립트의 원자성은 **요청이 끼어들지 못한다**는 뜻이지, 중간 명령이 오류를 낼 때 앞선 쓰기가 자동으로 롤백된다는 뜻은 아닙니다. 그래서 입력 JSON은 쓰기 전에 파싱하고, 저장소 오류가 나면 성공이라고 응답하지 않도록 했습니다.

## 실제 저장소와 브라우저에서 확인했다

테스트는 운영 방명록 키를 건드리지 않도록 별도 접두어를 붙인 임시 키에서 실행했습니다. 같은 키로 **동시 요청 5개**를 보냈습니다.

| 상황 | 결과 |
| --- | --- |
| 같은 키·같은 내용으로 동시 요청 5개 | 저장 1회, 기존 결과 재사용 4회 |
| 같은 키·다른 내용 | `conflict` |
| 새 키·같은 IP로 30초 안에 작성 | `rate_limited` |
| 브라우저에서 첫 응답 실패 후 재시도 | 두 요청의 키가 같고, 화면에는 글 1개 |

브라우저 테스트는 API 응답만 가짜로 바꿔 실제 방명록에 테스트 글을 남기지 않았습니다. 첫 요청은 실패한 것처럼 보여 주고, 두 번째 요청에 같은 글을 반환하게 했어요. 화면에 입력이 남는지, 헤더의 키가 같은지, 글 카드가 한 번만 나타나는지를 확인했습니다. 기존 검색·시리즈·모바일 테스트까지 **Playwright 6개가 모두 통과**했습니다.

## 어디까지 보장하나

키는 24시간 저장됩니다. 그 이후에 같은 키로 다시 보내면 새 작성으로 처리될 수 있습니다. 브라우저도 새로고침하면 메모리에 둔 작성 키를 잃습니다. 이번 구현은 **같은 화면에서의 실패 후 재시도와 동시 요청**을 해결하는 범위입니다.

또 관리자가 글을 삭제하거나 최근 100개 보관 한도에서 밀려나도 이미 저장한 키의 결과는 만료 시각까지 남습니다. 그 사이 같은 키로 다시 요청하면 목록에는 없는 글의 옛 성공 응답을 받을 수 있습니다. 삭제·보관 정책과 재시도의 의미를 더 엄격하게 맞춰야 하는 서비스라면 두 기록을 함께 정리하는 설계가 필요합니다.

---

데모에서 “같은 키면 한 번만 처리”를 보여 주는 건 쉬웠습니다. 실제 방명록에서는 기존 30초 제한, 목록 저장, 응답 유실, 두 요청의 동시 도착을 한데 맞춰야 했어요. 지난 글의 원리를 내 코드에 적용하고 테스트로 확인하니, 어디까지가 보장이고 어디부터가 다음 설계 과제인지도 훨씬 선명해졌습니다.
