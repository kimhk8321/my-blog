프론트엔드에선 API를 **호출**만 했습니다. `GET /users/1`을 부르고 JSON을 받아 그렸죠. 이제 **만드는** 쪽에서 보면, 그 URL과 메서드, 상태 코드 하나하나가 **설계 결정**이었다는 걸 알게 됩니다. REST는 그 결정을 위한 공통 규약입니다.

## 리소스 중심으로 — 동사가 아니라 명사

REST의 출발점은 "**URL은 리소스(자원)를 가리키고, 동작은 HTTP 메서드로 표현**"입니다.

```
✗ /getUser?id=1        /createUser      /deletePost
✓ GET /users/1         POST /users      DELETE /posts/9
```

URL엔 **명사**만 씁니다. "무엇을 할지"는 메서드가 정하죠. 컬렉션(`/users`)과 개별 항목(`/users/1`)을 구분하는 게 기본 뼈대입니다.

## 메서드 — 안전성과 멱등성

메서드 선택의 핵심은 두 성질입니다.

| 메서드 | 용도 | 안전(safe) | 멱등(idempotent) |
| --- | --- | --- | --- |
| GET | 조회 | ✓ (변경 없음) | ✓ |
| POST | 생성 | ✗ | ✗ |
| PUT | 전체 교체 | ✗ | ✓ |
| PATCH | 부분 수정 | ✗ | △ |
| DELETE | 삭제 | ✗ | ✓ |

- **안전(safe)**: 서버 상태를 바꾸지 않는가. `GET`은 몇 번 불러도 데이터가 안 변해야 합니다.
- **멱등(idempotent)**: **같은 요청을 여러 번 보내도 결과가 같은가**. `DELETE /posts/9`를 10번 보내도 최종 상태는 "9번이 없음"으로 동일하죠. 네트워크 재시도가 잦은 환경에서 멱등성은 **안정성의 핵심**입니다.

`POST`가 멱등이 아니라는 게 중요합니다. 결제 요청을 재시도로 두 번 보내면 두 번 결제될 수 있어요. 그래서 실무에선 멱등 키(Idempotency-Key)로 중복을 막습니다.

## 상태 코드 — API의 언어

상태 코드를 대충 `200`/`500`만 쓰면 클라이언트가 상황을 구분할 수 없습니다. 정확한 코드가 곧 API의 언어입니다.

- **2xx 성공**: `200 OK`, `201 Created`(생성), `204 No Content`(삭제 후 본문 없음)
- **4xx 클라이언트 잘못**: `400 Bad Request`(검증 실패), `401 Unauthorized`(인증 안 됨), `403 Forbidden`(권한 없음), `404 Not Found`, `409 Conflict`(중복), `429 Too Many Requests`([레이트 리밋](/posts/guestbook-backend))
- **5xx 서버 잘못**: `500 Internal Server Error`, `503 Service Unavailable`

`401`(누구인지 모름)과 `403`(누군진 아는데 권한 없음)의 구분이 대표적으로 헷갈리는 지점입니다. ([인증과 인가](/posts/auth-session-jwt) 글에서 이어집니다.)

## 목록엔 페이지네이션

목록 API가 데이터를 전부 내려주면 언젠가 터집니다. 처음부터 잘라서 줍니다.

```
GET /posts?limit=20&cursor=abc123   # 커서 기반 (안정적, 대용량)
GET /posts?page=2&size=20           # 오프셋 기반 (간단)
```

커서 기반이 중간에 데이터가 추가·삭제돼도 밀리지 않아 대규모에 유리합니다. ([무한 스크롤](/posts/infinite-scroll)이 이 API를 소비하던 그 반대편입니다.)

## 에러 응답도 일관되게

에러는 예측 가능한 형태로. 상태 코드 + 본문에 기계가 읽을 코드와 사람이 읽을 메시지를 담습니다.

```json
{ "error": { "code": "INVALID_EMAIL", "message": "이메일 형식이 아닙니다" } }
```

## 버저닝

API는 한번 공개하면 마음대로 못 바꿉니다(누군가 쓰고 있으니). 파괴적 변경은 버전으로 격리합니다.

```
/v1/users   →   /v2/users
```

---

REST의 핵심은 "**리소스는 URL로, 동작은 메서드로, 결과는 상태 코드로**"입니다. 프론트에서 매일 받던 그 응답들이, 사실 이런 규약 위에서 설계된 것이었죠. 다음 글에서는 "누구인지"를 다루는 [인증과 인가](/posts/auth-session-jwt)로 넘어갑니다.
