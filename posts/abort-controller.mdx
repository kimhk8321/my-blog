검색창을 만들었는데 가끔 이상합니다. "리액트"를 빠르게 쳤는데 화면엔 "리액"의 결과가 떠 있습니다. 분명 최신 입력으로 요청했는데 왜 옛 결과가 보일까요?

범인은 **경쟁 상태(race condition)** 입니다. 여러 비동기 요청이 **보낸 순서와 다른 순서로 도착**할 수 있기 때문이죠. 이걸 깔끔하게 없애 주는 브라우저 표준이 **AbortController**입니다.

## 왜 순서가 뒤집히는가

네트워크 응답 시간은 일정하지 않습니다. "리액"(요청 A)이 800ms, "리액트"(요청 B)가 200ms 걸린다면:

```
t=0    A 요청("리액")
t=50   B 요청("리액트")
t=250  B 응답 도착 → 화면 "리액트" ✓
t=800  A 응답 도착 → 화면 "리액"  ✗ (옛 결과가 최신을 덮음)
```

나중에 보낸 B가 먼저 오고, 먼저 보낸 A가 나중에 와서 최종 화면을 차지합니다. 요청을 보낸 순서는 우리가 정하지만, **도착 순서는 네트워크가 정합니다.**

## AbortController의 기본형

`AbortController`는 **요청을 밖에서 취소하는 리모컨**입니다. `signal`을 `fetch`에 넘겨 두면, `abort()`를 부르는 순간 그 요청이 취소되고 `AbortError`가 납니다.

```js
const controller = new AbortController();

fetch("/api/search?q=리액", { signal: controller.signal })
  .then((res) => res.json())
  .catch((err) => {
    if (err.name === "AbortError") return; // 취소는 에러가 아니라 정상 흐름
    throw err;
  });

controller.abort(); // → 위 요청 취소
```

여기서 핵심 습관: **취소로 인한 `AbortError`는 무시**합니다. 사용자가 새 검색을 했다는 뜻이지 실패가 아니니까요.

## 검색에 적용 — 이전 요청을 취소

새 검색이 시작될 때마다 **직전 컨트롤러를 abort**하고 새 컨트롤러를 만듭니다. 그러면 옛 요청은 취소돼 응답이 와도 무시되고, 살아남는 건 최신 요청뿐입니다.

```js
let controller = null;

async function search(query) {
  controller?.abort();          // 이전 요청 취소
  controller = new AbortController();

  try {
    const res = await fetch(`/api/search?q=${query}`, {
      signal: controller.signal,
    });
    render(await res.json());     // 최신 요청만 여기 도달
  } catch (err) {
    if (err.name !== "AbortError") throw err;
  }
}
```

이제 아까의 시나리오에서 B 검색이 시작될 때 A가 취소되므로, A의 응답은 화면에 닿지 못합니다. 경쟁 자체가 사라지는 거죠.

## React에서 — useEffect 정리 함수와 찰떡

React에서는 `useEffect`의 **정리(cleanup) 함수**가 AbortController와 완벽하게 맞물립니다. 의존성이 바뀌어 effect가 다시 실행되기 직전, 정리 함수가 이전 요청을 취소합니다.

```jsx
useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/search?q=${query}`, { signal: controller.signal })
    .then((res) => res.json())
    .then(setResults)
    .catch((err) => {
      if (err.name !== "AbortError") setError(err);
    });

  return () => controller.abort(); // query가 바뀌면 이전 요청 취소
}, [query]);
```

`query`가 바뀔 때마다 이전 effect의 정리 함수가 돌아 옛 요청을 끊고, 새 effect가 새 요청을 시작합니다. 언마운트 시에도 자동으로 취소되니 "언마운트된 컴포넌트에 setState" 경고도 사라집니다.

## fetch만이 아니다

`AbortController`는 fetch 전용이 아닙니다. `signal`을 받는 어떤 API든 취소에 쓸 수 있습니다.

```js
// 이벤트 리스너를 한 번에 정리
element.addEventListener("scroll", onScroll, { signal: controller.signal });
controller.abort(); // → 리스너 자동 제거

// 타임아웃도 표준 제공
fetch(url, { signal: AbortSignal.timeout(5000) }); // 5초 후 자동 취소
```

`AbortSignal.timeout()`이나 여러 신호를 합치는 `AbortSignal.any([...])`까지 있어, 취소·타임아웃·정리를 하나의 일관된 방식으로 다룰 수 있습니다.

---

경쟁 상태의 교훈은 "**비동기는 보낸 순서를 지켜주지 않는다**"입니다. 순서가 중요한 화면(검색·자동완성·탭 전환 데이터)에선 최신 요청만 살리는 장치가 필요하고, AbortController가 그 표준 도구입니다. useEffect 정리 함수와 엮으면 코드도 깔끔하죠. 다음 글에서는 [Intl API](/posts/intl-api)로 국제화 포맷팅을 제대로 다뤄 봅니다.
