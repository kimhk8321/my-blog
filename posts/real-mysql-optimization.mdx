## 조인 — 무엇을 먼저 읽느냐가 전부

MySQL의 조인은 기본적으로 **중첩 루프**입니다. 한쪽 테이블을 훑으면서, 각 행마다 다른 테이블을 찾아보죠.

```
for (a of A) {          ← 드라이빙 테이블 (먼저 읽는 쪽)
  for (b of B where b.a_id = a.id) { ... }   ← 드리븐 테이블
}
```

여기서 비용이 갈립니다.

- **드라이빙 테이블은 작을수록** 좋습니다. 바깥 루프 횟수가 줄어드니까요.
- **드리븐 테이블의 조인 컬럼에는 인덱스가 반드시** 있어야 합니다. 없으면 안쪽 루프마다 풀 스캔이 돌아 곱셈으로 비용이 터집니다.

즉 조인 최적화의 핵심은 **"작은 쪽을 먼저 읽고, 큰 쪽은 인덱스로 찾아간다"** 입니다.

순서는 옵티마이저가 정하지만, 통계가 어긋나면 잘못 고를 수 있습니다. `EXPLAIN`의 행 순서가 곧 조인 순서이니 확인해 볼 만합니다.

## 서브쿼리 대신 조인

특히 `IN` 서브쿼리는 예전 MySQL에서 비효율적으로 풀리는 경우가 많았습니다. 요즘은 옵티마이저가 대부분 알아서 변환하지만, **조인으로 쓰는 게 의도가 분명하고 안전**합니다.

```sql
-- 조인으로 (중복 제거 필요할 수 있음)
SELECT p.* FROM posts p
JOIN comments c ON c.post_id = p.id
WHERE c.created_at > ?;

-- 존재 여부만 알면 되면 EXISTS — 한 건 찾으면 멈춘다
SELECT * FROM posts p
WHERE EXISTS (SELECT 1 FROM comments c WHERE c.post_id = p.id);
```

**존재 여부만 필요하면 `EXISTS`** 가 낫습니다. 조건을 만족하는 첫 행을 찾는 즉시 멈추거든요. `COUNT(*) > 0`으로 확인하면 전부 세고 나서 비교하니 낭비입니다.

## 인덱스를 살리는 조건 쓰기

[2편](/posts/real-mysql-index)에서 본 원칙을 실전 형태로 정리하면 이렇습니다.

```sql
-- 컬럼을 가공하지 않는다
WHERE DATE(created_at) = '2026-09-06'                     -- 나쁨
WHERE created_at >= '2026-09-06' AND created_at < '2026-09-07'  -- 좋음

-- OR는 인덱스를 어렵게 만든다. UNION으로 나누는 게 나을 때가 있다
WHERE email = ? OR phone = ?
```

`OR`는 양쪽이 서로 다른 인덱스를 요구해서 옵티마이저가 포기하기 쉽습니다. 각각 인덱스가 있다면 `UNION`으로 나누는 편이 빠를 수 있어요.

## 정렬과 페이징

[filesort](/posts/real-mysql-explain)를 피하려면 `ORDER BY`가 인덱스 순서와 맞아야 합니다. 그리고 페이징은 **커서 방식**이 정석이죠.

다만 현실적으로 **"몇 페이지로 바로 가기"** 가 필요하면 커서 방식을 쓸 수 없습니다. 그럴 땐 이런 절충도 있습니다.

```sql
-- 커버링 인덱스로 id만 먼저 뽑고, 그 20개만 실제로 읽는다
SELECT p.* FROM posts p
JOIN (SELECT id FROM posts ORDER BY id DESC LIMIT 20 OFFSET 100000) t
  ON t.id = p.id;
```

건너뛰는 동안 **넓은 행 전체가 아니라 인덱스만 읽으므로** 부담이 줄어듭니다.

## COUNT는 생각보다 비싸다

`SELECT COUNT(*)` 는 InnoDB에서 **실제로 세어야** 합니다(MVCC 때문에 트랜잭션마다 보이는 행 수가 다르니 미리 저장해 둘 수가 없죠).

수백만 건짜리 테이블에서 전체 개수를 매번 세면 느립니다. 그래서:

- **총 개수를 꼭 보여줘야 하나** 다시 생각해 봅니다(무한 스크롤이면 필요 없죠)
- 필요하면 **[캐시](/posts/server-caching)** 하거나 별도 카운터를 둡니다
- 대략의 수로 충분하면 통계 정보를 씁니다

## 그리고 — 최적화 이전의 질문

책을 읽으며 가장 인상적이었던 건 기술적 요령이 아니라 순서였습니다.

1. **정말 필요한 데이터인가** — 안 가져오면 최적화가 필요 없습니다
2. **적절한 인덱스가 있는가** — 대부분의 문제가 여기서 끝납니다
3. **쿼리를 다시 쓸 수 있는가**
4. **스키마를 바꿔야 하는가**
5. **[캐시](/posts/server-caching)로 아예 DB를 안 가게 할 수 있는가**

기교로 쿼리를 다듬기 전에 **인덱스와 데이터 양**을 먼저 보는 게 거의 항상 효과가 큽니다.
