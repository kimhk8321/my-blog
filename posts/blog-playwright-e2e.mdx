지난주에는 여행을 다녀오느라 기술 블로그를 작성하지 못했습니다. 매주 이어 오던 기록이 한 번 끊기니 다시 책상 앞에 앉는 데 생각보다 힘이 필요하더군요. 2주 만에 쓰는 글이지만, 한 주 비었다는 이유로 흐름까지 놓치지는 않으려고 합니다. 앞으로도 완벽한 주기를 지키는 데 매달리기보다, 쉬었다면 다시 돌아와 꾸준히 작성해 보겠습니다.

다시 블로그 코드를 열고 먼저 확인한 것은 지금까지 만든 테스트가 어디까지 지켜주고 있는지였습니다. 단위 테스트 69개가 검색 점수, 글 정렬, 태그 정규화, 시리즈 순서처럼 중요한 순수 로직을 확인하고 있었습니다.

그런데 사용자가 보는 블로그는 함수의 반환값만으로 완성되지 않습니다. 검색어를 입력했을 때 결과가 화면에 나타나는지, 모바일 메뉴를 열어 이동할 수 있는지, MDX 안의 데모가 클릭에 반응하는지는 브라우저를 띄워야 알 수 있습니다. 그래서 오늘은 Playwright로 그 빈칸을 채웠습니다.

## 무엇을 E2E로 남길지 먼저 골랐다

E2E 테스트는 실제 브라우저를 쓰는 만큼 느리고 관리 비용도 큽니다. 모든 문구와 버튼을 검사하기보다 **여러 계층이 연결돼야만 성공하는 흐름**을 골랐습니다.

| 흐름 | 함께 검증되는 것 |
| --- | --- |
| 검색 | 입력 디바운스, API, 역색인, 결과 렌더링, URL 동기화 |
| 시리즈 이동 | MDX frontmatter, 시리즈 정렬, 링크 이동 |
| Idempotency Key 데모 | MDX 컴포넌트 주입, 클라이언트 상태, 비동기 UI |
| 동시 편집 데모 | 입력, 버전 충돌, 409 상태 표현 |
| 모바일 메뉴 | 반응형 UI, 접근성 이름, 페이지 이동, 가로 오버플로 |

방명록 작성과 관리자 삭제는 제외했습니다. 테스트가 실행될 때마다 공개 Redis에 가짜 글을 만들거나 실제 데이터를 지우는 건 안전하지 않습니다. 외부 상태가 필요한 흐름은 테스트 전용 저장소를 마련하거나 API를 격리한 뒤 추가하는 편이 맞습니다.

## 프로덕션 빌드를 브라우저로 연다

Next.js 개발 모드는 StrictMode와 개발 도구가 개입합니다. 실제 배포 결과를 확인하려고 Playwright가 빌드부터 서버 실행까지 맡게 했습니다.

```ts
export default defineConfig({
  testDir: "./e2e",
  use: {
    baseURL: "http://127.0.0.1:3100",
    trace: "retain-on-failure",
    screenshot: "only-on-failure",
    video: "retain-on-failure",
  },
  webServer: {
    command: "pnpm build && pnpm start --port 3100",
    url: "http://127.0.0.1:3100",
    reuseExistingServer: !process.env.CI,
  },
});
```

로컬에 이미 서버가 떠 있으면 재사용하고, CI에서는 항상 새 빌드로 시작합니다. 실패했을 때만 trace·스크린샷·영상을 남겨 평소 산출물은 가볍게 유지했습니다.

## CSS 선택자 대신 사용자의 언어로 찾는다

검색 테스트는 클래스 이름이나 DOM 깊이를 모릅니다. 사용자가 보는 placeholder를 찾아 입력하고, 결과 제목과 주소를 확인합니다.

```ts
test("검색어와 가장 관련 있는 글을 찾는다", async ({ page }) => {
  await page.goto("/search");

  const input = page.getByPlaceholder(
    "검색어를 입력하세요 (제목·태그·본문)",
  );
  await input.fill("React Compiler");

  const results = page.locator("main ul > li");
  await expect(results.first()).toContainText("React Compiler 실전 적용");
  await expect(page).toHaveURL(/\/search\?q=React(?:%20|\+)Compiler$/);
});
```

스타일을 바꿔도 테스트는 살아 있고, 검색창의 의미나 사용자 흐름이 바뀌면 실패합니다. 구현 세부사항보다 사용자가 찾는 방식에 기대는 쪽이 E2E 테스트의 역할에 맞습니다.

## 첫 실패는 기능 버그가 아니었다

처음 실행한 결과는 5개 중 4개 성공, 모바일 테스트 하나 실패였습니다.

```text
strict mode violation: getByRole('link', { name: '아카이브' })
resolved to 2 elements
```

햄버거 메뉴의 `아카이브` 링크를 찾았는데, 홈의 글 카드 설명에도 “아카이브”라는 단어가 있었습니다. Playwright는 둘 중 어느 것을 클릭할지 임의로 고르지 않고 실패했습니다.

처음에는 `nth(0)`으로 넘길 수 있다고 생각했습니다. 하지만 글 순서가 달라지면 다시 흔들립니다. 사용자가 메뉴를 찾는 맥락까지 선택자에 담았습니다.

```ts
const menu = page.locator("header").getByRole("navigation");
const archiveLink = menu.getByRole("link", {
  name: "아카이브",
  exact: true,
});

await archiveLink.click();
```

이 실패로 기능을 고치지는 않았지만, 테스트가 **어떤 영역의 요소인지 설명하지 못하고 있었다**는 건 고쳤습니다. E2E 선택자도 코드와 마찬가지로 의도가 선명해야 오래 갑니다.

## 모바일은 크기만 줄여 보는 것으로 끝내지 않았다

모바일 프로젝트는 Pixel 7 viewport로 따로 실행합니다. 메뉴를 열고 아카이브로 이동한 뒤, 실제 문서 너비가 화면보다 커지지 않았는지 검사합니다.

```ts
const overflows = await page.evaluate(
  () => document.documentElement.scrollWidth >
    document.documentElement.clientWidth,
);

expect(overflows).toBe(false);
```

예전에 모바일에서 오른쪽 빈 공간과 가로 스크롤이 생겼던 적이 있습니다. 눈으로 한 번 고친 뒤 끝내지 않고, 같은 문제가 다시 나타나면 이제 CI가 알려 줍니다.

## MDX 데모도 글의 일부다

이 블로그의 데모는 장식이 아니라 글의 설명을 직접 확인하는 코드입니다. 컴포넌트가 MDX에 등록되지 않거나 hydration에서 깨지면 본문이 맞아도 글은 완성되지 않습니다.

```ts
await page.getByRole("button", { name: "같은 키로 5번 전송" }).click();
await expect(page.getByText("서버에서 실제 처리한 횟수:"))
  .toContainText("1");
await expect(page.getByText("저장된 응답 재사용")).toHaveCount(4);
```

동시성 제어 데모에서는 편집기 A와 B가 같은 버전을 읽은 상태에서 차례로 저장하게 했습니다. A의 저장은 성공하고, 오래된 B의 저장에는 `409 충돌`이 보여야 합니다. 글에서 설명한 동작과 실제 데모가 어긋나지 않는지 브라우저가 확인합니다.

## CI는 단위 테스트 뒤에 실행한다

E2E는 빌드와 브라우저 설치가 필요해 기존 검증보다 비쌉니다. 그래서 린트·단위 테스트·빌드가 먼저 통과한 뒤 별도 작업으로 실행합니다.

```yaml
e2e:
  needs: verify
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - run: pnpm install --frozen-lockfile
    - run: pnpm exec playwright install --with-deps chromium
    - run: pnpm test:e2e
```

실패한 경우에만 HTML 리포트를 7일간 보관합니다. 로컬에서 재현되지 않아도 CI의 trace를 열면 클릭, 요청, DOM 상태를 시간순으로 따라갈 수 있습니다.

## 실제로 돌려 본 결과

설정을 마친 뒤 린트, 단위 테스트, 프로덕션 빌드, E2E 테스트를 차례로 실행했습니다.

| 검사 | 결과 |
| --- | --- |
| ESLint | 오류 0건 |
| Vitest | 테스트 파일 10개, 단위 테스트 69개 통과 |
| Next.js 프로덕션 빌드 | 성공 |
| Playwright 첫 실행 | 5개 중 4개 통과 |
| 선택자 수정 후 Playwright | **5개 모두 통과** |

첫 실행에서 실패한 하나가 앞서 본 모바일 아카이브 링크 선택자였습니다. 기능은 정상이어도 테스트가 화면의 의미를 정확히 짚지 못하면 실패한다는 걸 바로 확인했습니다. 선택 범위를 모바일 메뉴의 `navigation`으로 좁힌 뒤 전체를 다시 돌렸고, 데스크톱 4개와 모바일 1개가 모두 통과했습니다.

단위 테스트만 통과했을 때보다 확인 범위도 분명해졌습니다. 이제 CI의 초록불은 순수 함수가 맞다는 뜻에 더해, 프로덕션 빌드가 실제 Chromium에서 열리고 핵심 사용자 흐름이 끝까지 이어진다는 뜻이 됐습니다.

## 지금은 Chromium 하나면 충분하다

Playwright는 Firefox와 WebKit도 지원하지만 처음부터 모든 브라우저를 CI에 올리지는 않았습니다. 현재 블로그는 폼이나 미디어처럼 엔진 차이가 큰 기능보다 콘텐츠 탐색이 중심이고, 테스트마다 프로덕션 빌드 비용도 듭니다.

우선 Chromium 데스크톱과 모바일에서 핵심 흐름을 안정시키고, Safari 계열에서 실제 문제가 생기거나 브라우저별 API를 사용할 때 WebKit을 추가할 생각입니다. 테스트 범위는 많을수록 좋은 게 아니라, 실패했을 때 고칠 가치가 분명해야 합니다.

---

단위 테스트 69개는 로직을 빠르게 지키고, E2E 테스트 5개는 그 로직들이 브라우저에서 제대로 이어지는지 확인합니다. 둘은 서로 대체하는 관계가 아니었습니다. 함수가 모두 맞아도 링크가 잘못됐거나 모바일 화면이 넘칠 수 있고, 화면이 잘 열려도 검색 순위 계산이 틀릴 수 있으니까요.

2주 만에 다시 시작한 작업으로 테스트를 고른 것도 마음에 듭니다. 새 기능 하나를 더 얹기보다, 앞으로 계속 바꿀 블로그가 망가지지 않게 바닥을 단단하게 만든 날이었습니다. 다음 주에도 이 안전망 위에서 다시 하나씩 만들고 기록해 보겠습니다.
