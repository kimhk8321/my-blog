[네트워크 심화](/posts/cs-network)에서 HTTP의 진화를 훑었는데, 여기선 "**왜** 바뀌었나"를 파봅니다. 버전이 올라간 이유는 매번 하나였습니다 — **기다리는 시간을 없애려고.**

## HTTP/1.1의 문제 — 줄을 서야 한다

HTTP/1.1은 한 연결에서 **요청 하나를 보내고 응답을 받아야 다음 요청**을 보냅니다. 앞의 응답이 느리면 뒤가 전부 밀리죠. 이걸 **HOL 블로킹(Head-of-Line Blocking)** 이라고 합니다.

브라우저는 이걸 우회하려고 **도메인당 6개쯤 연결을 동시에** 엽니다. 하지만 연결마다 [TCP 핸드셰이크와 TLS 핸드셰이크](/posts/https-tls)를 치러야 하니 그것대로 비쌉니다.

그래서 당시엔 이런 최적화가 정석이었습니다.

- **파일 합치기(concat)** — CSS·JS를 하나로 묶어 요청 수를 줄인다
- **이미지 스프라이트** — 아이콘을 한 장에 몰아넣는다
- **도메인 샤딩** — 도메인을 여러 개 써서 연결 제한을 늘린다

## HTTP/2 — 한 연결에 여러 갈래

HTTP/2는 **하나의 연결 안에서 여러 요청을 동시에** 주고받습니다(멀티플렉싱). 요청·응답을 **프레임**이라는 작은 조각으로 쪼개고, 각 조각에 "몇 번 스트림 소속인지" 표를 붙여 섞어 보냅니다. 받는 쪽이 표를 보고 다시 조립하죠.

- **멀티플렉싱** — 요청 수가 많아도 줄을 서지 않는다
- **헤더 압축(HPACK)** — 매 요청 반복되는 헤더(쿠키 등)를 압축
- **바이너리 프레이밍** — 텍스트 대신 이진 형식이라 파싱이 빠르고 명확

여기서 중요한 결과 — **위에서 말한 옛 최적화들이 오히려 손해가 됩니다.**

- 파일을 하나로 합치면, 한 줄만 바뀌어도 **전체를 다시 받아야** 합니다. 잘게 나누면 바뀐 것만 받죠([캐싱](/posts/http-caching) 효율).
- 도메인 샤딩은 연결을 쪼개 **멀티플렉싱의 이점을 없앱니다.**

"요청 수를 줄여라"가 정석이던 시절의 조언이 아직 돌아다니는데, HTTP/2 위에서는 재고해야 합니다.

> **서버 푸시**는 어떻게 됐나: 요청하기 전에 서버가 미리 보내주는 기능이었는데, 이미 캐시된 걸 또 보내는 등 실익이 적어 **브라우저에서 사실상 폐기**됐습니다. 대신 `preload`나 **103 Early Hints**를 씁니다.

## HTTP/2에 남은 한계 — TCP가 발목을 잡는다

멀티플렉싱으로 HTTP 층의 줄서기는 없앴는데, **한 층 아래 TCP에서 다시 막힙니다.**

TCP는 데이터를 **순서대로** 전달해야 합니다. 그래서 패킷 하나가 유실되면, 그 뒤에 도착한 패킷들이 멀쩡해도 **재전송을 기다리며 전부 대기**합니다. 한 연결에 여러 스트림을 태워 놨으니, **무관한 스트림까지 함께 멈추죠.**

연결을 여러 개 쓰던 HTTP/1.1보다 **손실이 잦은 네트워크(모바일)에서 더 나빠질 수도** 있는 역설입니다. TCP를 고치지 않는 한 풀 수 없는 문제였고요.

## HTTP/3 — TCP를 버리고 QUIC으로

HTTP/3의 결단은 **TCP를 쓰지 않는 것**입니다. 대신 UDP 위에 **QUIC**이라는 전송 계층을 새로 얹었습니다.

- **스트림별 독립** — 한 스트림의 패킷이 유실돼도 **다른 스트림은 그대로 진행**합니다. TCP HOL 블로킹이 사라집니다.
- **연결 수립이 빠름** — TLS가 QUIC에 통합돼 **핸드셰이크가 1왕복**, 재방문은 0-RTT까지 가능합니다.
- **연결 마이그레이션** — 와이파이에서 LTE로 바뀌어 IP가 달라져도 **연결 ID**로 이어갑니다. 이동 중에도 끊기지 않죠.

"왜 하필 UDP냐"는 자연스러운 질문인데, 답은 현실적입니다. TCP는 OS 커널과 전 세계 중간 장비에 박혀 있어 바꿀 수가 없습니다. 반면 UDP는 "그냥 보내는" 최소 기능이라, **그 위에 필요한 걸 직접 구현**할 수 있죠. QUIC은 신뢰성·순서·혼잡 제어를 **애플리케이션 계층에서 새로 만든** 셈입니다.

## 그래서 무엇을 해야 하나

대부분은 **쓰면 켜집니다** — HTTP/2·3은 CDN이나 배포 플랫폼이 알아서 제공하니까요. 우리가 할 일은 **옛 최적화를 걷어내는 것**에 가깝습니다.

- 파일을 억지로 합치지 말고 **적당히 나눠** 캐시 효율을 살린다
- **도메인 샤딩은 하지 않는다**. 오히려 출처 수를 줄인다
- 중요한 리소스는 [`preload`·`preconnect`](/posts/dns-basics)로 앞당긴다
- 프로토콜이 빨라져도 **바이트가 줄어드는 건 아니다** — [이미지](/posts/image-optimization)·[폰트](/posts/web-font-optimization) 최적화는 여전히 유효

HTTP의 진화는 "**어디서 기다리게 되는가**"를 한 층씩 걷어낸 역사입니다. 1.1은 요청 줄서기, 2는 HTTP 층의 줄서기를 없앴고, 3은 그 아래 TCP의 줄서기까지 없애려 전송 계층을 새로 만들었죠. 다음 글에서는 아예 **거리 자체를 줄이는** [CDN과 엣지](/posts/cdn-edge)를 봅니다.
