React 성능을 다루다 보면 `memo`, `useMemo`, `useCallback`이 빠지지 않습니다. 문제는 최적화하려고 넣은 코드가 늘 정확하지는 않다는 겁니다. 의존성 하나를 빠뜨리면 오래된 값을 보고, 매번 새로 만들어지는 객체 하나 때문에 메모이제이션이 통째로 무효가 되기도 합니다.

React Compiler는 이 판단을 빌드 단계로 옮깁니다. 컴포넌트와 훅의 데이터 흐름을 분석해 **어떤 값과 UI를 다시 계산할 필요가 없는지** 자동으로 찾습니다.

## 컴파일러가 바꾸는 것

다음 컴포넌트는 부모가 리렌더될 때마다 필터 결과가 새 배열이 됩니다.

```tsx
function ProductPage({ products, theme }) {
  const visible = products.filter((product) => product.inStock);

  return (
    <div className={theme}>
      <ExpensiveList products={visible} />
    </div>
  );
}
```

손으로 최적화한다면 배열은 `useMemo`, 자식은 `memo`로 감쌀 겁니다.

```tsx
const ExpensiveList = memo(function ExpensiveList({ products }) {
  return products.map((product) => <Product key={product.id} {...product} />);
});

function ProductPage({ products, theme }) {
  const visible = useMemo(
    () => products.filter((product) => product.inStock),
    [products],
  );

  return <ExpensiveList products={visible} />;
}
```

Compiler를 사용하면 첫 번째 코드의 의미를 분석해 필요한 메모이제이션을 생성합니다. 소스에 훅을 추가하는 방식이 아니라, 컴파일 결과에 캐시 슬롯과 재사용 조건을 넣습니다.

## Next.js 16에서 켜기

이 블로그가 사용하는 Next.js 16에서는 플러그인을 설치하고 설정 하나를 추가합니다.

```bash
pnpm add -D babel-plugin-react-compiler
```

```ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  reactCompiler: true,
};

export default nextConfig;
```

Next.js는 SWC로 React 관련 파일을 먼저 골라낸 뒤 Compiler를 적용합니다. 모든 파일을 Babel로 넘기는 것보다 빌드 비용을 줄이기 위한 구조입니다.

처음부터 전체에 켜는 게 부담스럽다면 annotation 모드로 시작할 수 있습니다.

```ts
const nextConfig: NextConfig = {
  reactCompiler: {
    compilationMode: "annotation",
  },
};
```

```tsx
function ProductPage() {
  "use memo";
  // ...
}
```

문제가 있는 컴포넌트에는 `"use no memo"`로 적용을 잠시 피할 수도 있습니다. 다만 지시어를 곳곳에 넣기보다 컴포넌트의 순수성을 고치는 편이 장기적으로 낫습니다.

## memo를 전부 지우면 될까

기존 코드를 한꺼번에 걷어내는 건 권하지 않습니다. 수동 메모이제이션을 제거하면 Compiler가 만드는 결과도 달라질 수 있고, 참조 동일성 자체가 동작 조건인 코드도 있기 때문입니다.

특히 다음 경우에는 여전히 의도를 분명히 해야 합니다.

- Effect 의존성으로 쓰는 객체나 함수의 참조를 고정해야 할 때
- 외부 라이브러리가 참조 동일성을 API 계약으로 요구할 때
- Compiler가 최적화하지 못한 구간을 프로파일링으로 확인했을 때

`useMemo`는 의미를 보장하는 장치가 아니라 성능 최적화입니다. Compiler를 쓰더라도 이 원칙은 변하지 않습니다.

## 적용 전에 순수성부터 확인한다

Compiler는 React의 규칙을 잘 지키는 코드에서 가장 효과적입니다. 렌더 중 외부 값을 바꾸거나 props를 직접 수정하는 코드는 자동 최적화 이전에 동작부터 불안정합니다.

```tsx
function BadCounter({ model }) {
  model.count += 1;
  return <span>{model.count}</span>;
}
```

렌더는 같은 입력에 같은 결과를 내야 합니다. StrictMode가 개발 환경에서 렌더를 반복하는 것도 이런 코드를 찾기 위해서입니다.

## 효과는 사용자 경험으로 잰다

Compiler를 켜고 DevTools에서 렌더 표시가 줄었다고 끝내면 안 됩니다. 먼저 느린 상호작용을 정하고 같은 조건에서 비교해야 합니다.

1. React Profiler로 느린 커밋과 컴포넌트를 찾는다.
2. Compiler 적용 전 프로파일을 저장한다.
3. 점진적으로 활성화하고 같은 동작을 반복한다.
4. 커밋 시간, 긴 작업, INP 변화를 비교한다.
5. 빌드 시간과 번들 크기도 함께 기록한다.

렌더 한 번을 줄여도 그 렌더가 0.1ms라면 체감은 없습니다. 반대로 무거운 목록의 파생 계산을 재사용하면 한 번만 줄어도 차이가 큽니다.

---

React Compiler의 장점은 `useMemo` 몇 줄을 지우는 데 있지 않습니다. 사람이 놓치기 쉬운 메모이제이션을 일관된 분석에 맡기고, 개발자는 순수한 컴포넌트와 실제 병목에 집중할 수 있다는 데 있습니다. 적용 순서는 **규칙 점검, 일부 활성화, 프로파일 비교, 범위 확대**가 안전합니다.
