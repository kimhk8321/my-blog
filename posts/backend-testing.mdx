프론트에서 [Jest·Vitest로 컴포넌트를 테스트](/posts/react-testing)해봤다면 테스트의 기본은 익숙할 겁니다. 그런데 서버로 오면 결이 조금 다릅니다. 백엔드 테스트의 어려움은 대부분 **"바깥 세계"** — DB, 외부 API, 파일시스템 같은 의존성 — 에서 옵니다. 이걸 어떻게 다루느냐가 핵심이에요.

## 테스트 피라미드

테스트는 세 층으로 나뉘고, **아래로 갈수록 많고 빠르게, 위로 갈수록 적고 느리게** 두는 게 정석입니다.

- **단위(Unit)**: 함수·모듈 하나. 의존성 없이 순수 로직. 빠르고 많이.
- **통합(Integration)**: 여러 조각이 실제로 맞물리는지(예: 서비스 + 진짜 DB). 중간.
- **E2E**: API를 실제로 호출해 요청→응답 전체를 검증. 느리고 적게.

피라미드가 뒤집히면(느린 E2E만 잔뜩) 테스트가 느려 아무도 안 돌리게 됩니다.

## 단위 테스트 — 순수 로직을 격리

가장 가치가 큰 건 **비즈니스 규칙**입니다. "주문 금액이 5만 원 이상이면 무료배송" 같은 규칙은 DB 없이 순수 함수로 뽑아 테스트하면 빠르고 안정적이죠. [계층형 아키텍처](/posts/backend-layered-architecture)에서 도메인 로직을 분리해두면 이게 쉬워집니다.

```js
test("5만 원 이상이면 무료배송", () => {
  expect(shippingFee(50000)).toBe(0);
  expect(shippingFee(49999)).toBe(3000);
});
```

## 통합 테스트 — 진짜 DB와 함께

여기가 백엔드의 핵심입니다. "이 쿼리가 정말 맞는 데이터를 넣고 빼는가"는 **실제 DB에 붙여봐야** 압니다. 모킹으로는 [N+1](/posts/query-performance)이나 제약조건 위반을 못 잡죠.

- **테스트 전용 DB**를 띄운다(로컬 컨테이너나 인메모리 DB).
- 각 테스트 전후로 **깨끗한 상태**를 만든다 — 흔한 방법은 [트랜잭션](/posts/transactions-isolation)으로 감싸고 끝나면 **롤백**해서 서로 간섭을 없애는 것.

```js
beforeEach(() => db.begin());   // 트랜잭션 시작
afterEach(() => db.rollback()); // 테스트가 남긴 데이터 원복
```

## E2E(API) 테스트 — 요청부터 응답까지

실제로 HTTP 요청을 보내 상태 코드·본문을 검증합니다. 검증 로직, 인증, 직렬화까지 **전 계층이 함께** 동작하는지 확인하죠.

```js
const res = await request(app)
  .post("/api/guestbook")
  .send({ name: "", message: "hi" });
expect(res.status).toBe(400); // 빈 이름 → 검증 실패
```

[방명록](/posts/guestbook-backend)의 검증·레이트 리밋 같은 규칙은 이 층에서 확인하기 좋습니다.

## 외부 의존성은 모킹

내가 통제할 수 없는 것 — 결제 API, 이메일 전송, **현재 시각**, 랜덤 — 은 모킹하거나 고정합니다. 테스트는 **결정적(deterministic)** 이어야 하니까요. 실제 결제 서버를 부를 순 없죠. 다만 "전부 모킹"하면 통합의 의미가 사라지니, **내 DB는 진짜로, 남의 서비스는 가짜로**가 좋은 기준입니다.

## 무엇을 테스트할까

- **꼭**: 비즈니스 규칙, 경계값(빈 값·최대 길이), 에러 경로(권한 없음·잘못된 입력).
- **적당히**: 해피 패스 E2E 몇 개로 "전체가 붙는지".
- **굳이 안 해도**: 프레임워크·라이브러리 자체 동작.

커버리지 숫자보다 **"이게 깨지면 사용자가 아프다"는 것부터** 덮는 게 실용적입니다.

---

백엔드 테스트의 핵심은 "**순수 로직은 단위로 빠르게, DB가 얽힌 건 통합으로 진짜처럼, 전체 흐름은 E2E 몇 개로**"입니다. 이렇게 안전망을 깔아두면 다음 편에서 볼 [자동 배포(CI/CD)](/posts/ci-cd)에서 "테스트 통과 = 배포 가능"이라는 신뢰가 생깁니다. 그 전에, 그 배포의 단위가 되는 [컨테이너와 Docker](/posts/docker-containers)를 먼저 봅니다.
