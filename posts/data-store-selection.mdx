프론트에선 데이터를 그냥 "API가 주는 것"으로 받았습니다. 백엔드로 오면 **"이 데이터를 어디에 어떻게 저장할까"** 가 첫 설계 결정이 됩니다. 저장소는 하나가 아니고, 각각 성격이 달라요. [방명록을 만들 때](/posts/guestbook-backend) 관계형 DB가 아니라 Redis List를 고른 것도 이 판단이었죠.

## 관계형 DB (RDB) — 관계와 일관성

MySQL·PostgreSQL 같은 것. 데이터를 **표(테이블)** 로 나누고, 표 사이를 **관계(외래 키)** 로 잇습니다.

- **스키마 고정**: 컬럼과 타입이 정해져 있어 데이터가 정형적.
- **조인(JOIN)**: 여러 표를 엮어 조회. "이 사용자의 모든 주문과 그 상품들"을 한 쿼리로.
- **트랜잭션(ACID)**: 여러 작업을 **전부 성공 아니면 전부 취소**. 계좌 이체처럼 일관성이 생명인 곳의 핵심. ([CS의 트랜잭션·인덱스](/posts/cs-database) 편과 이어집니다.)

관계가 복잡하고 **정확성·일관성이 중요**하면(결제·재고·회원) 기본값은 RDB입니다.

## 문서형 NoSQL — 유연한 스키마

MongoDB 같은 것. 데이터를 **JSON 같은 문서**로 통째로 저장합니다.

```json
{ "id": 1, "name": "형기", "posts": [{ "title": "..." }, ...] }
```

- **유연한 스키마**: 문서마다 필드가 달라도 됨. 요구사항이 자주 바뀌거나 형태가 제각각인 데이터에 유리.
- **조인 약함**: 관련 데이터를 문서 안에 **중첩**하거나 앱에서 조합. 관계가 얽히면 오히려 불리.
- 한 문서를 통째로 읽는 패턴(예: 상품 상세)엔 빠르고 편함.

"스키마가 자주 바뀐다 / 관계보다 문서 단위 조회가 많다"면 문서형이 맞을 수 있습니다.

## 키-값 (KV) — 단순하고 빠름

Redis 같은 것. **키 하나에 값 하나**. 메모리 기반이라 극도로 빠릅니다.

- **초고속·단순**: `GET`/`SET` 수준. 복잡한 쿼리는 없음.
- **자료구조 제공**: 문자열뿐 아니라 List·Set·Hash·Sorted Set. [방명록](/posts/guestbook-backend)에서 List로 최신순·개수 제한을 공짜로 얻었죠.
- **휘발성 주의**: 기본이 메모리라 영속 저장이 필요하면 설정·백업이 필요.

**캐시, 세션 저장소, 조회수·[레이트 리밋](/posts/guestbook-backend) 카운터, 큐, 랭킹** 같은 곳에 딱입니다. 이 블로그의 조회수·방명록이 전부 KV(Upstash Redis)예요.

## 선택 기준

| 질문 | 저장소 |
| --- | --- |
| 관계가 복잡하고 일관성이 생명? | **관계형(RDB)** |
| 스키마가 유연해야 하고 문서 단위 조회? | **문서형 NoSQL** |
| 빠른 캐시·카운터·세션·큐? | **키-값(Redis)** |

## 하나만 고를 필요 없다 — Polyglot Persistence

현실 서비스는 **여러 저장소를 함께** 씁니다. 핵심 데이터는 RDB, 세션·캐시·조회수는 Redis, 검색은 전용 엔진(Elasticsearch)… 각 데이터의 성격에 맞는 도구를 섞어 쓰는 걸 **폴리글랏 퍼시스턴스**라고 합니다. "무조건 MySQL"이 아니라, **데이터마다 맞는 그릇**을 고르는 감각이 백엔드의 성숙도예요.

---

저장소 선택의 핵심 질문은 "**이 데이터는 어떤 성격인가**"입니다. 관계·일관성이면 RDB, 유연함이면 문서형, 속도·단순함이면 KV. 방명록에 무거운 RDB 대신 Redis List를 쓴 것처럼, 도구를 데이터에 맞추면 코드가 단순해집니다. 다음 글에서는 그 서버가 요청을 어떻게 동시에 처리하는지 [Node.js 이벤트 루프](/posts/nodejs-event-loop)를 봅니다.
